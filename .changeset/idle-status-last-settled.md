An IDLE checkout no longer presents a stale phase as the current one (phase 322, rec-20261004-002). `settle` returns the loop to IDLE but leaves `state.activePhase` set, and `state.json` is per-checkout, so a primary checkout whose phases are built and settled in worktrees kept showing the last phase settled *in that checkout* as its phase. On IDLE, `cadence status` no longer prints `phase: <activePhase>`; it prints `last settled: <phase>`, the latest settled phase derived best-effort from the `.cadence/phases/` directories in the working tree (the highest-numbered one whose `*-SUMMARY.json` carries `stateAtSettle`, which only a successful settle writes, so a refused settle never counts). When no settled phase can be derived, for example in histories whose SUMMARY files predate `stateAtSettle`, it prints `last phase in this checkout: <activePhase>` instead. `cadence status --json` keeps `activePhase` unchanged and adds a `lastSettledPhase` field (string or `null`). `.cadence/STATE.md` now renders `**Active phase:** (none — loop is IDLE)` followed by `**Last phase in this checkout:** <activePhase or (none)>`, and the SessionStart hook banner reads `Active phase: (none — loop is IDLE)` plus `Latest settled phase: <phase>`, or `Last phase in this checkout: <activePhase>` when none is found. The lookup never fails a command or hook, and every non-IDLE output is unchanged.

The MCP `cadence_status` tool and `cadence://state` resource follow `cadence status` and STATE.md. Not changed: `cadence handoff`'s `active_phase:` pre-fill, `cadence resume`, the MCP `cadence://state.json` resource, `cadence inspect`, and the intelligence context packet still carry the raw `activePhase`, and neither a checkout left in DRAFT/BUILD after its slice settled elsewhere nor `cadence progress`'s IDLE suggestion is affected.
