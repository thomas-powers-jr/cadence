New `verification.fallback` config setting lets a repo refuse instead of silently settling on a mock verdict (phase 343; dec-20261030-060, dec-20261030-061, dec-20261030-062). Until now, when a verifier seam could not reach its configured real provider (a missing Anthropic key, an unset local endpoint, a host CLI binary that will not launch, a timeout, or the claude self-invocation guard), it printed a loud notice and continued on mock. That is still the behavior when the key is absent or set to `"mock"`, and `cadence init` does not write the key. Set `verification.fallback` to `"refuse"` and the call fails instead, with an error naming the seam, the setting and the cause. `deep-verify`, `code-review` and `security-audit` turn it into a gate refusal, so `cadence settle run` exits non-zero; their existing bypasses still apply as before (`--allow-verifier-failure` for deep-verify; `--allow-code-review-failure`, `--allow-security-audit-failure` or `--force` for code-review and security-audit). `per-task-verify`, `plan-review`, `spec-review` and `ui-spec-review` make `cadence build task`, `cadence draft approve` or `cadence spec approve` exit 1 without changing loop state. Refusal is lazy, so a gate that does not fire never refuses, and a seam configured as `mock`, explicitly or by default, is unaffected. `cadence doctor` has a new informational `verification-fallback` check reporting the effective value, and under `"refuse"` its `verification-readiness` warnings say a seam will refuse rather than fall back to mock. The setting is meant for automated consumers, such as CI or Cadence Studio, that must never settle on a mock by accident. The types package's `CadenceConfigZ` gains the optional `verification.fallback` field; existing configs keep parsing unchanged.
