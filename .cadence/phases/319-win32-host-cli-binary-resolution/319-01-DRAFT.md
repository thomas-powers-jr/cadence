# 319-01 — win32 host-cli binary resolution

## Objective

Make the host-cli provider launch npm-installed host CLIs on Windows. `packages/core/src/verify/host-cli-client.ts`'s `realSpawn` calls `spawn(bin, args)` with no shell. On win32 a bare `codex` resolves only to npm's `codex.cmd` launcher (plus an extension-less POSIX sh script and usually a `.ps1`), so `spawn('codex')` fails `ENOENT` and `spawn('codex.cmd')` throws `EINVAL` (Node's CVE-2024-27980 hardening). Both surface as a loud fallback to `mock`, so the documented `CADENCE_HOST_CLI_BIN=codex` workflow never produces a real review on Windows. Reproduced 2026-09-27 on Node v24.20.0 through the built `hostCliJSON`: bare `codex` → `not-found`; the native `codex.exe` path → `{"ok":true}` in 8.6s; `process.execPath` + the shim's `codex.js` target → `{"ok":true}` in 9.0s. The fix resolves the configured bin on win32 the way the shell would (PATH × PATHEXT), then launches an `.exe`/`.com` directly or runs an npm `.cmd` launcher's JavaScript target with Node — never `shell: true` (DEP0190 / injection surface). Resolution happens only inside the real spawn seam, so family inference, the self-invocation guard, and error messages keep using the configured bin. Source: `rec-20260926-005`.

## Acceptance Criteria

### AC-1: bare name resolves through PATH and PATHEXT to a native executable
Given platform `win32`, a bin with no path separator and no extension (e.g. `codex`), an env whose PATH key is spelled `Path` (any case), and PATH directories where one contains `codex` (extension-less sh script), `codex.ps1`, and `codex.exe`
When the pure resolver runs
Then it returns that `codex.exe` absolute path as the command with no argv prefix; skips extension-less and non-PATHEXT candidates; searches PATH directories in order and, within each, PATHEXT extensions in order; reads PATH/PATHEXT by case-insensitive key; falls back to `.COM;.EXE;.BAT;.CMD` when PATHEXT is unset; ignores empty PATH segments, strips surrounding double quotes from a segment, tolerates a trailing separator, joins UNC directories correctly (via `path.win32`), and skips any segment that is not fully qualified (drive-rooted `X:\…` or UNC) — so `.`, `bin`, drive-relative `C:tools`, and root-relative `\tools` segments never resolve a binary

### AC-2: npm .cmd launcher runs its JavaScript target with Node, no shell
Given platform `win32` and a PATH directory containing `codex` (sh script), `codex.ps1`, and a canonical npm cmd-shim `codex.cmd` whose invoking line is `... "%_prog%"  "%dp0%\node_modules\@openai\codex\bin\codex.js" %*` (and separately the legacy `"%~dp0\node.exe"  "%~dp0\…\codex.js" %*` form)
When the pure resolver runs for the bare name `codex`, for bare `codex.cmd`, and for an absolute path to that `codex.cmd`
Then a bin that already ends in `.exe`/`.com`/`.cmd`/`.bat` is probed as-is (never re-suffixed, e.g. no `codex.cmd.COM`) even when PATHEXT omits that extension; the result is command = `<shim dir>\node.exe` when that file exists else `process.execPath`, argv prefix `[<shim dir>\node_modules\@openai\codex\bin\codex.js]` for a `.js`/`.cjs`/`.mjs` target; a canonical shim whose target is an `.exe` returns that `.exe` as the command with no prefix; and the real spawn seam passes the underlying spawn options with piped stdio and no `shell` key

### AC-3: an unrecognised or escaping launcher is refused loudly, never shelled
Given platform `win32` and a resolved `.cmd`/`.bat` that does not match the canonical cmd-shim invoking line, whose target uses any `%…%` expansion other than `%dp0%`/`%~dp0`, whose normalized target falls outside the shim's own directory (including a sibling-prefix escape such as `..\npm-evil\payload.js` from `C:\npm`), or whose target is neither a JavaScript file nor an `.exe`
When `hostCliJSON` is called with that bin through the real spawn seam
Then it rejects with a `HostCliError` whose reason is the existing `spawn-error` (no new `HostCliErrorReason` value), whose message names the configured bin and tells the operator to point `CADENCE_HOST_CLI_BIN` at the native executable, and the underlying spawn is never called

### AC-4: the configured bin still drives family, guard, and error text; the current directory is never searched
Given platform `win32`, bin `codex` resolving to an npm `.cmd` launcher, and a fake underlying spawn
When `hostCliJSON` runs through the real spawn seam
Then the underlying spawn receives the Node command with argv `[<codex.js>, 'exec', '--json', '--skip-git-repo-check', '-']` (codex family inferred from the configured bin, not from `node.exe`); an injected `spawnImpl` still receives the configured bin unchanged; a bare bin found in the current working directory but on no PATH directory (including via `Path=.;C:relative`) is not resolved from the cwd; and every exhausted lookup — a bare name, an already-suffixed name like `codex.cmd`, and a separator-bearing path such as a nonexistent `C:\…\codex.exe` — rejects with reason `not-found` naming the configured bin, raised by the resolver rather than by passing the bin to `spawn` (which would let libuv search the cwd)

### AC-5: non-Windows behavior is unchanged
Given platform `linux` or `darwin` and any bin
When the pure resolver runs
Then it returns the bin unchanged with no argv prefix and performs no file-system probing

### AC-6: operator docs describe the Windows resolution
Given `docs/providers.md`'s host-cli section
When an operator reads how `CADENCE_HOST_CLI_BIN` is resolved and how the prompt reaches the child
Then it states that on Windows a bare name is resolved via PATH/PATHEXT (never the current directory), npm `.cmd` launchers run through Node without a shell, unrecognised launchers are refused, and names the native-executable path override as the fallback; and it no longer claims stdin "is not piped" or shows the prompt passed in argv — the invocation examples read `claude -p --output-format json` and `codex exec --json --skip-git-repo-check -`, and the text says the prompt is written to the child's stdin, then closed

## Tasks

### T1: Pure win32 command resolver
- files: `packages/core/src/verify/win32-command.ts`, `packages/core/tests/verify/win32-command.test.ts`
- action: TDD a pure, dependency-injected `resolveHostCliCommand(bin, facts)` where `facts` = `{ platform, env, fileExists, readFile, execPath }`, returning `{ command, prefixArgs }` or throwing. Non-win32 returns the bin untouched without calling `fileExists`/`readFile`. On win32, using `path.win32` throughout: if the bin already ends in `.exe`, `.com`, `.cmd`, or `.bat` (case-insensitive), probe it exactly as given regardless of PATHEXT's contents (directly when it contains a separator, else in each PATH dir); PATHEXT is used only to suffix a bin with none of those extensions, in PATHEXT order. Include a test where PATHEXT omits `.CMD` and bare `codex.cmd` / an absolute `…\codex.cmd` still resolve. Search only the bin's own path (when it contains a separator; an explicit operator-configured path is used as given) or PATH directories — never the cwd. PATH/PATHEXT by case-insensitive key; default PATHEXT `.COM;.EXE;.BAT;.CMD`; skip empty segments; strip surrounding `"`; skip any segment that is not fully qualified, using an explicit drive-rooted-or-UNC predicate (`/^[A-Za-z]:[\\/]/` or `\\server\share`), not `path.win32.isAbsolute` (which accepts root-relative `\tools`). `.exe`/`.com` hit → `{ command: <abs path>, prefixArgs: [] }`. `.cmd`/`.bat` hit → match only the canonical cmd-shim invoking line (`"%_prog%"  "%dp0%\<rel>" %*`, legacy `"%~dp0\node.exe"  "%~dp0\<rel>" %*`, or exe form `"%dp0%\<rel>.exe" %*` / `"%~dp0\<rel>.exe" %*`); reject `<rel>` containing `%`; resolve with `path.win32.resolve(shimDir, rel)` and require the result to stay under `shimDir` via a separator-aware check (`path.win32.relative(shimDir, target)` compared case-insensitively must be non-empty, not start with `..`, and not be absolute) — never a string-prefix check; `.js`/`.cjs`/`.mjs` → `{ command: <shimDir>\node.exe if it exists else execPath, prefixArgs: [target] }`; `.exe` → `{ command: target, prefixArgs: [] }`; anything else → throw a plain `Error` naming the bin and the native-exe override. Every exhausted lookup (bare, already-suffixed, or separator-bearing bin) → throw an `Error` with `code: 'ENOENT'` (so `toHostCliError` maps it to `not-found`); plain uncoded `Error`s are reserved for unsafe/unrecognised launchers. ## Boundaries

- DO NOT search the current working directory when resolving a bare bin on win32.
- DO NOT use `shell: true` (or `cmd.exe /c`) anywhere in the host-cli spawn path, and DO NOT fall back to it for an unrecognised launcher.
- DO NOT add a runtime dependency (no `cross-spawn`, `which`, or `cmd-shim` packages).
- DO NOT add a new `HostCliErrorReason` value; reuse `spawn-error` / `not-found`.
- DO NOT change `inferFamily`, the self-invocation guard, `buildInvocation`, or the timeout default.
- DO NOT touch `packages/core/src/doctor/run.ts` (false "blocked by session" warning is `rec-20260927-001`).
- DO NOT address the 180s code-review timeout (`rec-20260927-002`).
- DO NOT touch `packages/host-claude-code`'s win32 shim `shell: true` (`rec-20260926-004`) or `packages/core/src/services/retro.ts`'s `gh` spawn.
- DO NOT weaken or rewrite existing `host-cli-client.test.ts` tests to fit the new seam.
