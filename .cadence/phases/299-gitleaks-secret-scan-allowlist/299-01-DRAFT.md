# 299-01 — Gitleaks secret-scan false-positive allowlist

## Objective

Eliminate gitleaks secret-scan's 22 false positives (test fixtures shaped like real credentials) that fail the weekly Security schedule scan, by annotating every currently-unannotated or misplaced fixture occurrence with the established same-line gitleaks:allow comment and adding a .gitleaksignore for the historical commits that predate those annotations, per dec-20260915-003's finding that inline comments alone cannot retroactively clear a full-history scan.

## Acceptance Criteria

### AC-1: Reapply/annotate the two files with a stranded fix
Given summary-render.test.ts:449 and summary-writer.test.ts:337,343,347 contain unannotated fake AWS-key/GitHub-token fixtures that a stranded, never-merged commit (28fa905e) once addressed
When same-line gitleaks:allow comments are added to each currently-flagged line, following the established pattern rather than reapplying the stale patch verbatim
Then a gitleaks --no-git scan of packages/core/tests reports zero findings in these two files

### AC-2: Fix the finding-routing.test.ts placement bug
Given finding-routing.test.ts has a gitleaks:allow comment on line 245, one line above the actual match on line 246
When the comment is moved to a trailing position on line 246 itself
Then gitleaks no longer flags line 246 in a --no-git scan

### AC-3: Annotate the missed recommendations.test.ts occurrence
Given recommendations.test.ts:30 has an unannotated fake AWS key distinct from the already-correct annotations at lines 150 and 257
When a same-line gitleaks:allow comment is added to line 30
Then gitleaks no longer flags line 30 in a --no-git scan

### AC-4: Annotate the remaining unannotated fixtures
Given security-audit.test.ts (lines 9, 12, 246) and redact.test.ts (lines 6, 32, 47, 53, 59, 84, 90, 96, 102) have unannotated fake-secret fixtures
When same-line gitleaks:allow comments are added to each
Then a gitleaks --no-git scan of packages/core/tests reports zero findings across the whole tree

### AC-5: Suppress the 22 historically-flagged commits
Given all 22 findings from the 2026-09-14 schedule run (34828882922) trace to historical commits whose diffs predate any annotation and can never be retroactively fixed by editing HEAD
When a .gitleaksignore file is added at the repo root listing each finding's exact captured fingerprint
Then a local full-history gitleaks detect run against the repo (after AC-1..AC-4's edits are in place) reports zero findings, down from 22

**As built:** the DRAFT's prescribed `git cat-file -e` commit-resolvability check was dropped from the final test. The whole-branch review caught that `.github/workflows/ci.yml` checks out with the default shallow depth (unlike `security.yml`, which explicitly sets `fetch-depth: 0`) -- a commit-resolvability assertion passes locally (full clone) but fails on every CI run (shallow clone), since none of `.gitleaksignore`'s 4 historical commits are reachable in a depth-1 checkout. The narrower, CI-safe invariant (fingerprint well-formedness + uniqueness) covers AC-5's coverage-gate requirement; the real proof that suppression works remains the manual full-history `gitleaks detect` run recorded in this task's verify step, not something a vitest assertion can safely re-derive under a shallow clone.
