# 304-01 — profileRemediationHint enumerates reachable profile x tier cells via effectiveGateSet, packs-aware

## Objective

Phase 302 made assessGateReachability's profile-blocked VERDICT pack-aware (routed through effectiveGateSet), but profileRemediationHint (doctor/run.ts) still hardcodes each gate's reachable profile x tier cells as a two-branch prose string derived from raw DELTAS only. A pack that adds a gate (e.g. security-audit) at a (profile, tier) cell absent from raw DELTAS makes that cell genuinely reachable, but doctor's remediation text still tells the operator to switch to the old DELTAS-only cell. Make profileRemediationHint enumerate reachable cells dynamically via effectiveGateSet across all 3 profiles x 3 tiers (packs-aware), replacing the hardcoded branches.

## Acceptance Criteria

### AC-1: given a known reachable-cell set, the remediation text follows a fixed, testable ordering and template
Given a gate's reachable `(profile, tier)` cells as computed by enumerating `effectiveGateSet` across all 3 profiles × 3 tiers (packs-aware) — grouped by profile in the fixed order `['strict', 'standard', 'auto']`, tiers within a profile in the fixed order `['quick-fix', 'standard', 'complex']`
When the reachable-cell set has exactly one cell total
Then the text is the single-cell sentence ("override profile: to '<profile>' at tier: <tier> — <gate>'s only reachable profile×tier cell")
And when the reachable-cell set has two or more cells
Then the text is the multi-cell sentence ("override profile: in a DRAFT's frontmatter to '<profile>' (tier: <tiers joined by ' or '>) or '<profile>' (tier: ...) ... to include <gate> in the gate set"), profiles and tiers in the fixed order above

**`softCap` decision (`auto`×`complex`), recorded per `dec-20260822-028`:** that decision already established softCap is a confirmation gate, not an enforcement exemption — a pack-contributed gate at `auto`×`complex` fires identically to any other cell once the operator passes `--allow-auto-complex`. So the enumeration treats `auto`×`complex` as an ordinary reachable cell, no special-casing or caveat text — it is a real place to switch to, not a dead end.

**Implementation note, not to be "simplified" away:** the enumeration must call `effectiveGateSet` with a `draft: { profile, tier }` override for every one of the 9 combinations (never with `config`'s own profile substituted in its place) — `effectiveProfile(config, draft)` does `if (draft?.profile) return draft.profile`, a truthy check, so passing the loop's `profile` value via `draft` is what actually varies the result across all 9 calls; passing it via `config` instead would silently collapse every combination onto one profile.

### AC-2: with no resolvedPacks, the two existing gates' remediation text reflects the same raw-DELTAS cells as before, in the new deterministic order
Given `resolvedPacks: []` (today's real-world state — no pack declares `gates[]` yet)
When `checkConductionReachability` computes remediation for a profile-blocked `code-review` or `security-audit`
Then `code-review`'s text names all three of its raw-DELTAS cells across two profiles (`strict`×`standard`, `strict`×`complex`, `standard`×`complex`) in the new order — i.e. `'strict' (tier: standard or complex) or 'standard' (tier: complex)` (this is a genuine ordering change from today's `'standard' ... or 'strict' ...` text — the two existing assertions at `packages/core/tests/doctor/run.test.ts:601-602` are updated to match, not preserved verbatim: dec-anchored ordering rule beats reverse-engineering the old prose's implicit order, which does not match any of `GATE_PROFILES`, `DELTAS` key order, or the type declaration order), and `security-audit`'s single-cell text (`'strict' at tier complex`) is unchanged since it was already the single-cell case

### AC-3: a pack-added cell for a still-blocked gate appears in the remediation text (the actual bug this phase fixes)
Given a resolved pack whose manifest adds `security-audit` at a (profile, tier) cell absent from raw DELTAS (e.g. `standard` × `complex`), and the gate is still profile-blocked under the project's *current* configured profile (e.g. `auto`, which has no `security-audit` cell at all, with or without packs)
When `checkConductionReachability` computes the remediation for that still-blocked gate
Then the remediation text names *both* the pack-added cell and the original raw-DELTAS cell (`strict` × `complex`) as places the operator could switch to — proving the hint is no longer matrix-blind to packs
