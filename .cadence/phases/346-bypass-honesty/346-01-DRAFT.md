# 346-01 — Bypass honesty: a bypassed failing suite or coverage gap is recorded, shown and graded

## Objective

A settle that lets a failing test suite through with --allow-failing-build or --force, or real coverage gaps through with bare --force, must leave a loud, durable trace: the operator sees which tests failed, and SUMMARY.gateBypasses records the bypass so assurance cannot grade strong over a red suite. Today the build-test-must-pass bypass branch writes nothing to stderr, the test runner discards all output (stdio ignore), the bypass reaches gates[] only as a skipped entry and never SUMMARY.gateBypasses, and coverage's bypass flag is false when only --force overrode real gaps (rec-20260806-006, rec-20260726-005, dec-20261030-002; operator decisions 2026-11-12: severity error, output tail carried in the gateBypasses entry).

## Acceptance Criteria

### AC-1: the test runner captures a bounded output tail without changing the verdict
Given verification.testCommand is configured and runTestCommand runs it
When the command exits non-zero, exits zero, is killed by a signal, fails to spawn, or writes far more output than any fixed buffer holds
Then the exit code alone decides ok, exactly as today: a zero exit is ok true with no outputTail, a non-zero exit is ok false with its exitCode, a signal kill or a spawn error is ok false with exitCode 1, and output far larger than 1 MiB never flips the verdict; a failing run's outputTail holds at most the last 40 lines and at most 8 KiB of the command's combined stdout and stderr, lines split on LF with a trailing CR stripped, a final unterminated line counted, ANSI escape sequences removed, stdout and stderr chunks kept in arrival order; the command still runs through a shell in the same cwd with the same env, no timeout, and stdin ignored; nothing it prints reaches cadence's own stdout

### AC-2: the gate writes one loud bypass notice, and every refusal shows the tail
Given the build-test-must-pass gate runs and the test command fails
When the gate is unsealed and --allow-failing-build, bare --force, or both are set; or no bypass flag is set; or the gate is sealed
Then on a bypass the gate itself writes exactly one stderr notice naming the gate, the flag that fired, the command, its exit code and the output tail, where the flag that fired is --allow-failing-build whenever it is set and --force otherwise (the registry.ts rule); on any refusal, sealed or not, the gate's existing stderr lines are followed by the output tail, while its refusal reason string and its outcome stay byte-identical; a passing run and a ran:false run write nothing new

### AC-3: a bypassed failing suite is an error-severity gateBypasses entry that caps assurance
Given settle completes after build-test-must-pass was bypassed on a failing suite
When the SUMMARY is written
Then SUMMARY.gateBypasses holds exactly one entry with gate build-test-must-pass, a flag equal to the flag the gate's notice and gates[] skip reason name, a reason naming the command and exit code, severity error, and detail holding the output tail; because that entry is error severity, the existing D-S rule caps assurance.overall at mixed, shown by a settle that would grade strong without the entry; the settle-written SUMMARY.md and `cadence summary render` list the entry and show its detail as an indented block, while a SUMMARY with no detail on any entry renders byte-identically to today (so summary hashes of existing records do not change); the build-test-bypassed anomaly's context carries flag, command and exitCode, and the tail appears nowhere in the anomaly event (its message or its context); a settle whose suite passed records no such entry and its grade is unchanged

### AC-4: a bare --force pass over real coverage gaps is recorded with the flag that fired
Given the test-coverage gate runs in assertion mode, unsealed, with real coverage gaps
When settle runs with bare --force and without --allow-missing-coverage
Then the gate marks coverage as bypassed, gates[] records it as skipped naming --force, and SUMMARY.gateBypasses carries a test-coverage entry with flag --force and severity warn, the same severity the coverage bypass has today; --allow-missing-coverage behaves exactly as today and stays the named flag whenever it is set; with no gaps, with the gate sealed, in mention mode, or on the malformed-id phase-qualified path, behavior is unchanged

### AC-5: schemas stay backward compatible and docs match
Given SUMMARY.json files and anomaly logs written before this phase
When they are parsed with the new schemas, and the docs and help text are checked
Then GateBypassZ's new detail field, TestRunResult's outputTail and GateFlags.buildTestBypass are optional, every committed SUMMARY.json under .cadence/phases still parses, the new build-test-bypassed anomaly type is accepted alongside the existing ones, docs/concepts.md and the anomaly table in DESIGN.md describe both bypasses as recorded in gateBypasses with their severities, the --allow-failing-build help in settle and docs/reference/commands.md say the bypass is recorded at error severity and caps assurance at mixed, and a changeset covers cadence-core and cadence-types

## Boundaries

- Do NOT change a refusal's reason string or outcome, sealed or not; a refusal only gains the output tail after its existing stderr lines.
- Do NOT change what decides pass or fail: the test command's exit code alone sets ok; capture is observation only.
- Do NOT print test output to stdout. stdout is the `--json` and MCP contract; every notice goes to stderr.
- Do NOT change the severity, flag or wording of any other existing gateBypasses entry (settle --force, deep-verify, soft-cap, checkpoint-stop, skill-audit, pack-resolution, code-review and security-audit findings).
- Do NOT change --allow-missing-coverage behavior, coverage mention mode, or the malformed-id phase-qualified --force path.
- Do NOT put the output tail in an anomaly message or any notifier transport payload beyond the anomaly context; it belongs in gateBypasses.detail.
- Do NOT add a runtime dependency; capture with node:child_process.
- Do NOT rewrite committed SUMMARY.json files or other phases' artifacts; old records keep their old shape.
- Do NOT touch the host adapters, host-toolkit, testkit's published surface, or the Release workflow.
