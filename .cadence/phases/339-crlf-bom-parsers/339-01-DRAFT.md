# 339-01 — DRAFT/SPEC/UI-SPEC parsing and draft mutation tolerate CRLF, lone CR and a UTF-8 BOM

## Objective

A DRAFT.md, SPEC.md or UI-SPEC.md saved on Windows parses and edits correctly. Such files often carry a UTF-8 BOM (PowerShell's default), CRLF line endings, or, rarely, lone-CR endings. Today they still fail with misleading errors: "missing frontmatter", "draft status is unknown, not PENDING", or "DRAFT.md missing a ## Acceptance Criteria section". The fix has two parts:
- **Parsing:** one shared, pure normalizer strips a single leading BOM and turns CRLF and lone CR into LF. Every parse entry point and `frontmatterStatus` run it first.
- **Mutation:** `draft set-objective`/`add-ac`/`add-task` splice on normalized text, then write the file back in its detected style. This was the operator's choice, 2026-10-29. A pure-CRLF file stays CRLF, a BOM is kept, and a pure-LF file is byte-identical to today's output, so an edit to a pure-style file changes only the edited bytes. A mixed-ending file is written back as all-CRLF.

This covers rec-20260918-005, rec-20260918-006 and rec-20260918-007. It also covers the same bug in `frontmatterStatus`, which the recs do not name.

## Acceptance Criteria

### AC-1: One pure normalizer reports and removes BOM and line-ending style
Given any input string
When it is passed to the new shared normalizer in `packages/core/src/parse/`
Then:
- it returns the text with exactly one leading U+FEFF removed, if present;
- it replaces every `\r\n` with `\n` first, and only then every remaining lone `\r` with `\n`, so `\r\n` never becomes `\n\n`;
- it also returns the detected style: `bom: true` when a leading U+FEFF was removed, and `eol: 'crlf'` when the input contained at least one `\r\n`, otherwise `'lf'`;
- an LF-only, BOM-less input comes back unchanged with `{ bom: false, eol: 'lf' }`.

A companion inverse, given LF text and a style, returns the text with every `\n` turned into `\r\n` when `eol` is `'crlf'` and U+FEFF prepended when `bom` is true. Re-applying a pure-CRLF or BOM+CRLF input's detected style to its normalized text reproduces that input byte for byte.

### AC-2: parseDraftMd accepts BOM, BOM+CRLF and lone-CR drafts
Given a well-formed DRAFT.md saved four ways: with a UTF-8 BOM and LF, with a BOM and CRLF, with lone-CR endings, and with plain LF. The fixture must have:
- at least two ACs, one with a multi-line Given;
- at least two tasks, one with `depends:` and `stop:`;
- a non-empty Boundaries list.

When each is parsed by `parseDraftMd`
Then:
- all four produce field-for-field identical `Draft` objects, with non-zero AC, task and boundary counts;
- no string field contains `\r` or U+FEFF;
- a DRAFT.md whose frontmatter is genuinely missing or malformed still throws the existing `CadenceError('DRAFT.md missing frontmatter')` in every one of those encodings.

### AC-3: parseSpecMd and parseUiSpecMd accept CRLF, BOM and lone-CR files
Given a well-formed SPEC.md (at least two ACs, one multi-line) and a well-formed UI-SPEC.md (at least one component with `####` subsections), each saved with CRLF, with a BOM and CRLF, with lone-CR endings, and with plain LF
When each is parsed by `parseSpecMd` or `parseUiSpecMd`
Then:
- every variant parses to the same object as its LF form, with non-empty AC or component lists;
- no string field contains `\r` or U+FEFF;
- a genuinely missing frontmatter block still throws each parser's existing "missing frontmatter" `CadenceError`, with its current message unchanged. `parseUiSpecMd`'s says `SPEC.md missing frontmatter`, and that message stays as it is.

### AC-4: frontmatterStatus reads status through CRLF and a BOM
Given a DRAFT.md, SPEC.md or UI-SPEC.md whose frontmatter `status:` is set, saved with CRLF and/or a leading BOM
When `frontmatterStatus` reads it
Then it returns the same status as for the LF equivalent. As a result:
- `cadence draft add-ac` no longer refuses a PENDING CRLF+BOM draft with "draft status is unknown, not PENDING". `set-objective` and `add-task` share the same guard (`services/draft-mutate.ts`), so the `add-ac` case covers it.
- `cadence draft new` seeds its ACs from an `APPROVED` CRLF+BOM SPEC.md, exactly as it does from the LF equivalent.

### AC-5: Draft mutations succeed on CRLF/BOM drafts and write back in the detected style
Given a PENDING DRAFT.md saved with CRLF, with a BOM and CRLF, with a BOM and LF, or with mixed line endings
When `setObjective`, `addAcceptanceCriterion` or `addTask` edits it
Then the edit succeeds and the output is written in the input's detected style:
- **CRLF input:** every line break in the output is `\r\n`; there is no bare `\n` and no `\r\r`.
- **BOM:** present in the output exactly when it was present in the input.
- **Mixed-ending input:** written back as all-CRLF.
- **Lone-CR-only input:** written back as LF, since its detected `eol` is `'lf'`.
- **Equivalence:** normalizing the output gives exactly the text the same mutation produces on the LF, BOM-less equivalent.
- **Inserted text:** the mutation's payload strings (objective text, AC name/given/when/then, task fields) pass through the same normalizer before splicing. A payload carrying `\r\n` therefore never yields `\r\r\n` in a CRLF file or a stray `\r` in an LF file.
- **LF input with an `\r`-free payload:** output is byte-identical to today's.

> **As built (2026-10-29).** The "Inserted text" clause is narrower in the code than written above. Payload strings fold only their line endings (CRLF, then lone CR, to LF) through `foldLineEndings` in `parse/text-normalize.ts`. They do not go through the full `normalizeText`. A payload's leading U+FEFF is kept as content, not stripped as an encoding marker, so an LF draft edited with a `\r`-free payload stays byte-identical to before, as the Boundaries require. Running payloads through `normalizeText` would have dropped a payload's leading U+FEFF and changed LF bytes. Task `done` ids are not folded: they are validated against the draft's existing AC ids first, so one containing `\r` is refused as unknown.

## Boundaries

- Do NOT change any parser's error messages, section regexes, or the shape of the parsed objects; only input normalization changes.
- Do NOT change the bytes written for an LF, BOM-less DRAFT.md by any mutation whose payload contains no `\r`. Payloads that do contain `\r` are now normalized, which is the one intended LF-path change.
- Do NOT change `spec-approve.ts`'s `status: PENDING → APPROVED` rewrite. Its multiline regex already keeps CRLF and the BOM.
- Do NOT add a runtime dependency.
- Do NOT touch other text consumers: `summary-writer.ts`, `retro-writer.ts`, the handoff parser/validator, or the checkpoint package's private `stripBom` copies. File a recommendation if one turns out to need the same fix.
- Do NOT fix rec-20260805-003 (task `action:` multi-line truncation), even though it lives in `draft-parser.ts`.
- Do NOT deduplicate the copied `parseFrontmatter`/`extractSection` helpers across the three parsers. That is a separate refactor.
