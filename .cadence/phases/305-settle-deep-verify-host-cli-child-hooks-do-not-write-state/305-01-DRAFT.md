# 305-01 — settle deep-verify host-cli child hooks do not write state

## Objective

Fix GitHub issue #500: `cadence settle run --deep` can never commit in a project that has CADENCE's own Claude Code hooks installed. Settle reads `state.json` at revision N, then the `host-cli` provider spawns `claude -p` in the project directory; that child session fires the project's `UserPromptSubmit` hook, whose `handleUserPrompt` bumps the telemetry-only `session.tokenUtilization` through the compare-and-swap `backend.commit(state)` path, advancing the on-disk revision to N+1, so settle's own commit at the end refuses with `StateConflictError` on every attempt. The issue's own isolation experiment shows `UserPromptSubmit` is the only hook that writes during a verifier run (`SessionStart` and `Stop` leave the revision unchanged). This is the same class as issue #234 (phase 194), which moved the telemetry-only `subagentSpawns` counter onto the revision-exempt `bumpSessionCounter` path but left `tokenUtilization` behind — a value `dec-20260815-003` already records as a fake signal nothing structural depends on. This phase moves `tokenUtilization` onto that same revision-exempt path, clamped to its schema's `[0, 1]` range, which also stops any user prompt in an ordinary interactive session from invalidating a long-running command's snapshot. Retry-on-conflict inside settle was considered and rejected: it would silently paper over a genuine concurrent writer, the exact case `commit()`'s guard exists to refuse. A broader hardening — marking host-cli verifier children with an environment variable so every CADENCE hook no-ops inside them, covering the other committing handlers (`PostToolUse` edits, `SubagentStop`, first-time `Skill` invocations) that a verifier child does not fire in the reported scenario — is deliberately out of scope: it depends on an unverified premise (that Claude Code and Codex pass inherited environment variables through to hook subprocesses) and a silent hook no-op would also disable edit-time boundary enforcement. It is filed as its own recommendation instead.

## Acceptance Criteria

### AC-1: the user-prompt telemetry bump never advances the state revision
Given a `state.json` at revision N with `telemetry.tokenUtilization` enabled
When `handleUserPrompt` runs
Then the on-disk `revision` is still N, `session.tokenUtilization` on disk has increased by 0.01, and a separate caller still holding the revision-N snapshot can `commit()` without a `StateConflictError`

### AC-2: the revision-exempt tokenUtilization bump stays inside the schema range
Given a `state.json` whose `session.tokenUtilization` is already `1` (or within 0.01 of it)
When the revision-exempt bump for `tokenUtilization` runs
Then `state.json` is written with `session.tokenUtilization` equal to `1` and no schema-validation error is thrown, while the existing `subagentSpawns` bump keeps its `>= 0` floor and has no upper clamp

## Boundaries

- DO NOT change `commit()`'s compare-and-swap semantics or add retry-on-conflict to `settle run` — a real concurrent writer must still be refused.
- DO NOT add a host-cli child environment marker or any hook no-op path — that is the filed follow-up recommendation, not this phase.
- DO NOT change the `CLAUDECODE`/Codex self-invocation guard in `host-cli-client.ts`.
- DO NOT touch the host adapters (`packages/host-claude-code`, `packages/host-codex`) or `packages/host-toolkit`.
- DO NOT change how settle builds `ctx.diff()` — that is issue #501, a separate phase.
- DO NOT move any structural (non-telemetry) field onto the revision-exempt path.
- DO NOT remove or weaken existing tests to make the new ones pass.
