# 337-01 — doctor and onboard check that the host-cli binary exists

## Objective

Stop `cadence doctor` and `cadence onboard` from calling a `host-cli` verifier ready when its binary is not installed (rec-20261027-001, medium). Today `assessReadiness` (`packages/core/src/activate/assess.ts`) says "deep-verify uses host-cli with credentials present" purely from config: `credsPresent('host-cli')` is unconditionally `true` (phase 165), and `resolveHostCliCommand` (`verify/win32-command.ts`) only searches PATH on win32 — on POSIX the bin name passes straight through. Observed 2026-10-27 in a Claude Code cloud session (cadence 1.71.0) on a consumer repo whose `CADENCE_HOST_CLI_BIN` was `codex`: onboard and doctor both reported ready while `codex` was not installed, so every host-cli gate would have fallen back to mock at settle. The spawn-time fallback is loud and recorded, but the readiness surface the operator checks first said the opposite; `docs/providers.md`'s "Readiness reporting caveat" documents the gap. The fix is pure core plus impure shell, and **additive**: (1) a new pure `hostCliBinaryResolves(bin, facts)` in `verify/host-cli-presence.ts` — POSIX searches PATH for a runnable regular file (an explicit path is checked as given, never PATH-searched, the current directory never searched), win32 reuses the existing two-pass `.com`/`.exe` then `.bat`/`.cmd` search via a newly exported `locateHostCliBinary`; plus `hostCliBin(env, cwd)` (`CADENCE_HOST_CLI_BIN` from env or `.env`, default `claude`, the verifier factory's rule) and a best-effort `realHostCliPresenceFacts()` whose probe never throws. (2) `VerifierReadiness` gains `seamsUnresolvable` (every `host-cli` seam when that binary does not resolve) and `hostCliBin`; `assessReadiness` takes an optional injectable presence probe (default real); `ready` is false and `reason` names the binary when deep-verify itself is unresolvable, and a resolvable host-cli reason names the binary and says its login is checked only when a review runs — no more "credentials present" for host-cli. (3) doctor's `verification-readiness` warns on unresolvable seams, naming the binary, the seams and the fix. Login and reachability stay lazily checked at spawn; `credsPresent`, `seamsDowngraded`, `cadence activate` and the spawn path are unchanged. Patch changeset for cadence-core.

## Acceptance Criteria

### AC-1: the presence probe resolves binaries like the spawn path does
Given a bin name or path and injected facts (platform, env, a runnable-file check)
When `hostCliBinaryResolves` runs
Then on POSIX a bare name resolves only when some non-empty PATH entry holds a runnable regular file of that name (a directory, a non-runnable file, an unset or empty PATH, or a file only in the current directory all resolve false); a bin containing `/` is checked as given and never PATH-searched; on win32 the answer matches `locateHostCliBinary` (the spawn resolver's own search) for bare names, `.cmd` shims and explicit paths; and a facts check that throws makes the answer false instead of throwing

### AC-2: assessReadiness reports unresolvable host-cli seams
Given a config whose deep-verify seam and one other seam use `host-cli`, and an injected presence probe
When `assessReadiness` runs with the probe reporting the binary missing (one case) and present (a second case)
Then in the missing case `seamsUnresolvable` lists both host-cli seams in `VERIFIER_SEAMS` order, `hostCliBin` is the effective binary (`CADENCE_HOST_CLI_BIN` from env or `.env`, else `claude`), `ready` is false, and `reason` names the binary and says host-cli reviews will fall back to mock; in the present case `seamsUnresolvable` is empty, `ready` is true, and `reason` names the binary and says its login is checked only when a review runs, without the words "credentials present"; and a config with no host-cli seam never calls the probe

### AC-3: doctor warns when a host-cli binary will not resolve
Given an initialized repo whose deep-verify seam uses `host-cli` and whose `CADENCE_HOST_CLI_BIN` points at a path that does not exist
When `checkVerificationReadiness` runs
Then the check is a `warning` whose detail names the binary and every unresolvable seam and carries `MOCK_VERIFIER_CAPABILITY`, and whose remediation says to install the binary, point `CADENCE_HOST_CLI_BIN` at it, or switch those seams' provider; and with `CADENCE_HOST_CLI_BIN` pointing at an existing runnable file (`process.execPath`) the pre-phase `ok` results for an all-host-cli config still hold

### AC-4: onboard's verifier line tells the truth
Given an initialized repo whose deep-verify seam uses `host-cli`
When `cadence onboard --skip-host-wire --json` runs with `CADENCE_HOST_CLI_BIN` set to a missing path (one case) and to `process.execPath` (a second case)
Then the missing case's `verifier.ready` is false, `verifier.seamsUnresolvable` includes `verifier`, and its `reason` names the missing binary; the present case's `verifier.ready` is true; and neither output contains "credentials present"

### AC-5: credential semantics and activate are unchanged
Given every pre-phase `credsPresent` and `seamsDowngraded` expectation in `tests/activate/assess.test.ts` and the activate test suite
When they run against the phase's code
Then `credsPresent('host-cli', …)` still returns true with any env, `seamsDowngraded` still never lists a host-cli seam, and every activate test passes unedited

### AC-6: docs describe the binary check
Given `docs/providers.md`'s "Readiness reporting caveat" and `docs/reference/commands.md`'s `verification-readiness` row
When a doc test reads them
Then the caveat says readiness now confirms the host-cli binary resolves (PATH or configured path) while login and reachability are still only discovered when a review runs, and the row says the check warns when a host-cli seam's binary cannot be found
