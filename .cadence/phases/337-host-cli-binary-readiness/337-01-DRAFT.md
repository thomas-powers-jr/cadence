# 337-01 — doctor and onboard check that the host-cli binary exists

## Objective

Stop `cadence doctor` and `cadence onboard` from calling a `host-cli` verifier ready when its binary cannot be launched (rec-20261027-001, medium). Today `assessReadiness` (`packages/core/src/activate/assess.ts`) says "deep-verify uses host-cli with credentials present" purely from config: `credsPresent('host-cli')` is unconditionally `true` (phase 165), and on POSIX `resolveHostCliCommand` (`verify/win32-command.ts`) passes the bin name straight to `spawn`. Observed 2026-10-27 in a Claude Code cloud session (cadence 1.71.0) on a consumer repo whose `CADENCE_HOST_CLI_BIN` was `codex`: onboard and doctor both reported ready while `codex` was not installed, so every host-cli gate would have fallen back to mock at settle. The spawn-time fallback is loud and recorded, but the readiness surface the operator checks first said the opposite; `docs/providers.md`'s "Readiness reporting caveat" documents the gap. The fix is pure core plus impure shell, and **additive**: (1) a new pure `hostCliBinaryResolves(bin, facts)` in `verify/host-cli-presence.ts` that mirrors what `makeRealSpawn` (`host-cli-client.ts`) will actually do — on POSIX, libuv's execvp-style search (an empty PATH segment means the process cwd, an unset PATH means `/usr/bin:/bin`, a bin containing `/` is checked as given), accepting only a runnable regular file; on win32, the spawn path's own resolver, `resolveHostCliCommand(bin, facts)`, called inside try/catch, so an ENOENT **and** a refused `.cmd` launcher both mean "won't launch"; plus `hostCliBin(env, cwd)` (`CADENCE_HOST_CLI_BIN` from env or `.env`, default `claude` — the verifier factory's rule) and a best-effort `realHostCliPresenceFacts()` whose checks never throw. `win32-command.ts` is not edited. (2) `VerifierReadiness` gains `seamsUnresolvable` (every `host-cli` seam when that binary won't launch) and `hostCliBin`; `assessReadiness` takes an optional injectable presence probe (default real); `ready` is false and `reason` names the binary when deep-verify itself is unresolvable, and a resolvable host-cli reason names the binary and says its login is checked only when a review runs — no more "credentials present" for host-cli. (3) doctor's `verification-readiness` warns on unresolvable seams, ahead of the `seamsDowngraded` warning and naming both lists when both apply, so the binary-specific fix is never hidden. (4) onboard's `--json` `verifier` payload gains `seamsUnresolvable`. Login, reachability and the self-invocation guard stay checked at spawn; `credsPresent`, `seamsDowngraded`, `cadence activate` and the spawn path are unchanged. Patch changeset for cadence-core.

## Acceptance Criteria

### AC-1: the presence probe answers "will spawn launch this?"
Given a bin name or path and injected facts (platform, env, cwd-relative runnable-file check, file read, execPath)
When `hostCliBinaryResolves` runs
Then on POSIX a bare name resolves only when a PATH entry holds a runnable regular file of that name, searched in order with an empty segment meaning the current directory and an unset PATH meaning `/usr/bin:/bin` (a directory or non-runnable entry is skipped in favour of a later runnable one; a non-runnable-only match resolves false); a bin containing `/` is checked as given and never PATH-searched; on win32 a native `.exe` on PATH and a canonical npm `.cmd` shim resolve true, while a missing binary and a non-canonical or escaping `.cmd` shim (one `resolveHostCliCommand` refuses) resolve false; and a facts check that throws makes the answer false instead of throwing

### AC-2: assessReadiness reports unresolvable host-cli seams
Given a config whose deep-verify seam and one other seam use `host-cli`, and an injected presence probe
When `assessReadiness` runs with the probe reporting the binary missing (one case) and present (a second case)
Then in the missing case `seamsUnresolvable` lists both host-cli seams in `VERIFIER_SEAMS` order, `hostCliBin` is the effective binary (`CADENCE_HOST_CLI_BIN` from env or `.env`, else `claude`), `ready` is false, and `reason` names the binary and says host-cli reviews will fall back to mock; in the present case `seamsUnresolvable` is empty, `ready` is true, and `reason` names the binary and says its login and the self-invocation guard are checked only when a review runs, without the words "credentials present"; and a config with no host-cli seam never calls the probe

### AC-3: doctor warns when a host-cli binary will not launch
Given an initialized repo whose deep-verify seam uses `host-cli` and whose `CADENCE_HOST_CLI_BIN` points at an absolute path that does not exist
When `checkVerificationReadiness` runs
Then the check is a `warning` whose detail names the binary and every unresolvable seam and carries `MOCK_VERIFIER_CAPABILITY`, and whose remediation says to install the binary, point `CADENCE_HOST_CLI_BIN` at it, or switch those seams' provider; when a keyless `anthropic` seam is also present, the same warning names that seam too; and with `CADENCE_HOST_CLI_BIN` set to `process.execPath` the pre-phase `ok` results for an all-host-cli config still hold

### AC-4: onboard's verifier payload tells the truth
Given an initialized repo whose deep-verify seam uses `host-cli`
When `cadence onboard --skip-host-wire --json` runs with `CADENCE_HOST_CLI_BIN` set to a missing absolute path (one case) and to `process.execPath` (a second case)
Then the missing case's `verifier.ready` is false, `verifier.seamsUnresolvable` includes `verifier`, and its `reason` names the missing binary; the present case's `verifier.ready` is true and `verifier.seamsUnresolvable` is empty; and neither output contains "credentials present"

### AC-5: credential semantics are unchanged
Given the probe reporting a host-cli binary missing
When `credsPresent('host-cli', …)` and `assessReadiness` run
Then `credsPresent` still returns true with any env, and `seamsDowngraded` still never lists a host-cli seam (only `seamsUnresolvable` does)

### AC-6: docs describe the binary check
Given `docs/providers.md` and `docs/reference/commands.md`
When a doc test reads them
Then the providers.md "Readiness reporting caveat" says readiness confirms the host-cli binary will launch (PATH or configured path) while login, reachability and the self-invocation guard are only discovered when a review runs; the providers.md activation paragraph says `ok` also requires a host-cli binary to be found; the commands.md `verification-readiness` row says the check warns when a host-cli seam's binary cannot be found; and the commands.md onboard `--json` shape lists `seamsUnresolvable`

## Boundaries

- Do NOT edit `src/verify/win32-command.ts`, `host-cli-client.ts`, `verifier-factory.ts`, `cadence activate`, `credsPresent`, or `seamsDowngraded`'s membership rule.
- Do NOT replace or change `doctor/run.ts`'s `commandOnPath`.
- Do NOT probe login or network reachability, or spawn the host CLI, during readiness — whether spawn would find a launchable file only.
- Dropped, not deferred: detecting the self-invocation guard (`CLAUDECODE=1` with a `claude`-family bin) in readiness. `conduction-reachability` (phase 251) reports it for code-review and security-audit only; for deep-verify and the other seams, the readiness reason and the providers.md caveat (AC-6) say plainly that the self-invocation guard, like login, is only discovered when a review runs.
- Do NOT add a config field or a runtime dependency; do NOT touch `packages/testkit/**`.
- Do NOT make any test depend on whether `claude` or `codex` is installed on the machine running it.
