# 344-01 — Host-cli review agents are spawned with isolation flags, recorded on the gate entry

## Objective

The host-cli review agents are spawned with no isolation (`codex exec --json --skip-git-repo-check -`, `claude -p --output-format json`), so the reviewer loads the operator's own MCP servers, plugins, hooks and global instruction files, and shares their blind spots (rec-20261030-010). A probe on the operator's PC (`probe/PROBE-RESULTS.md`, codex-cli 0.156.1, Claude Code 2.1.330) measured what each candidate flag does. This phase passes the strongest measured variant that keeps login working: `--ignore-user-config` for the codex family and `--setting-sources project --strict-mcp-config` for the claude family; records the flags passed on the SUMMARY's gate entry; adds `verification.hostCliIsolation: "on" | "off"` (absent means on) as the way to turn it off; and reports it in `cadence doctor`. The claim is narrow: these flags are passed and recorded. The global `AGENTS.md` and `CLAUDE.md` still reach the reviewer (measured), and project-level files and hooks still apply because the child runs in the project directory (rec-20260916-004); both are documented, not fixed.

## Acceptance Criteria

### AC-1: the codex family is spawned with --ignore-user-config
Given the binary name `codex` and isolation on
When `hostCliJSON` spawns it through an injected spawn, once with no model and once with model `gpt-5`
Then the argv is `['exec','--json','--skip-git-repo-check','--ignore-user-config','-']` and `['exec','--json','--skip-git-repo-check','--ignore-user-config','-m','gpt-5','-']`; the prompt is still written to stdin; and through `makeRealSpawn` the spawn options are still `{ stdio: ['pipe','pipe','pipe'] }` with no `env` key

### AC-2: the claude family is spawned with --setting-sources project --strict-mcp-config
Given the binary name `claude` and isolation on
When `hostCliJSON` spawns it through an injected spawn, once with no model and once with model `opus`
Then the argv is `['-p','--output-format','json','--setting-sources','project','--strict-mcp-config']` and `['-p','--output-format','json','--setting-sources','project','--strict-mcp-config','--model','opus']`; a binary named `my-reviewer` (not containing `codex`) gets the same claude argv, as the existing family rule already treats it

### AC-3: verification.hostCliIsolation "off" restores today's argv
Given `verification.hostCliIsolation: "off"` in `config.json`
When the code-review host-cli verifier selected by `selectCodeReviewVerifier` and the deep-verify host-cli verifier selected by its factory each make a call through an injected spawn, for `codex` and for `claude`
Then the argv is `['exec','--json','--skip-git-repo-check','-']` for codex and `['-p','--output-format','json']` for claude; with the key absent or `"on"` the same two verifiers produce the AC-1 and AC-2 argv. The key is an optional enum: a `config.json` holding `{}` loads through `loadConfig` with the key absent, it is absent from `defaultConfig` and from a fresh `cadence init`'s `config.json`, and `"Off"`, `true` and `null` are rejected by `loadConfig`

### AC-4: a CLI that rejects an isolation flag fails loudly and is not retried without it
Given an injected spawn that exits 2 with stderr `error: unexpected argument '--ignore-user-config' found` for `codex`, and one that exits 1 with stderr `error: unknown option '--setting-sources'` for `claude`
When the code-review host-cli verifier selected by `selectCodeReviewVerifier` makes one call, under the default fallback and under `fallback: 'refuse'`
Then the injected spawn was called exactly once in each case; under the default the stderr notice contains `falling back to mock provider for this call` and the hint `this CLI did not accept the isolation flag "--ignore-user-config"; update it, or set verification.hostCliIsolation to "off"` (for claude, the same hint naming `"--setting-sources"`); under refuse the thrown `VerifierFallbackRefusedError`'s message contains the same hint. The hint is added only when the child's stderr contains one of the isolation flags that were passed: a `nonzero-exit` with stderr `not authenticated` carries no hint

### AC-5: the gate entry records the isolation flags that were passed
Given `runSettleGates` runs deep-verify and code-review with host-cli verifiers on an injected spawn, binary `claude`, isolation on
When the gates pass
Then the `deep-verify` and `code-review` entries each carry `hostCliIsolation: ['--setting-sources','project','--strict-mcp-config']` (for binary `codex`: `['--ignore-user-config']`); the same holds for a `security-audit` entry produced by a host-cli security-audit verifier. The field is absent when isolation is off, when the provider is mock, and when the call fell back to mock. `GateProvenanceZ` accepts the field as an optional string array, a SUMMARY written before this phase (no such field) still parses, and `summary verify` reports a matching content hash for a SUMMARY whose gate entries carry the field. Not covered: `per-task-verify` entries, the plan-review, spec-review and ui-spec-review sidecars, and a `refused` entry whose verifier threw

### AC-6: cadence doctor reports the isolation the configured binary gets
Given a config whose `verifier.provider` is `host-cli`
When `cadence doctor` runs with `CADENCE_HOST_CLI_BIN=codex`, with it unset (binary `claude`), and with `verification.hostCliIsolation: "off"`
Then a check with id `host-cli-isolation` reports: for codex, pass with `host-cli reviews run "codex" with --ignore-user-config; the global AGENTS.md still reaches the reviewer`; for claude, pass with `host-cli reviews run "claude" with --setting-sources project --strict-mcp-config; the global CLAUDE.md still reaches the reviewer`; with `"off"`, warn with `host-cli isolation is off (verification.hostCliIsolation): reviews inherit the user's own configuration`. With no provider set to `host-cli` the check passes with `no review gate uses host-cli`. The check never spawns the binary

### AC-7: the docs state what is passed, what was measured and what still reaches the reviewer
Given `docs/providers.md`, `docs/reference/config.md`, `docs/reference/commands.md` and the changeset
When phase 344 ships
Then the host-cli section of `providers.md` contains both new command lines (`codex exec --json --skip-git-repo-check --ignore-user-config -` and `claude -p --output-format json --setting-sources project --strict-mcp-config`), states that `--ignore-user-config` keeps `config.toml` out and the global `AGENTS.md` still reaches the reviewer, that the claude flags stop user-level hooks, user plugins and MCP servers and the global `CLAUDE.md` still reaches the reviewer, that project-level instruction files and hooks still apply, and names `verification.hostCliIsolation` as the way to turn the flags off; `config.md` documents the key with its two values and that absent means on; `commands.md` lists the `host-cli-isolation` doctor check; a minor changeset for cadence-core and cadence-types says the same; and a doc-content test asserts these

## Boundaries

- Do NOT set `CODEX_HOME`, `CLAUDE_CONFIG_DIR` or any other environment variable for the child, and do NOT copy any credentials file: the probe showed a login-only `CODEX_HOME` works, and the operator chose not to ship it.
- Do NOT pass `--bare` or any flag the probe did not measure.
- Do NOT add a retry of a failed host-cli call, with or without the isolation flags.
- Do NOT change the fallback decision: a `nonzero-exit` is still a loud mock fallback by default and a refusal under `verification.fallback: "refuse"`.
- Do NOT change the self-invocation guard, the stdin prompt path, the win32 command resolver, the timeout handling or the family rule (`codex` in the binary name, else claude).
- Do NOT claim in docs, help or the changeset that the reviewer is fully isolated: the global `AGENTS.md` and `CLAUDE.md`, and project-level files and hooks, still reach it.
- Do NOT edit an existing test beyond the two named edits (argv pins in `host-cli-client.test.ts`; the codex command-line substring in `providers-host-cli-windows.test.ts`).
- Do NOT add a CLI flag, an environment variable or an MCP parameter for the setting, and do NOT add a runtime dependency.
- Do NOT touch `per-task-verify`'s PROGRESS records or the plan-review, spec-review and ui-spec-review sidecars.
