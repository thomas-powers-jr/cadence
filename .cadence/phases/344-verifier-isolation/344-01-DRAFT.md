# 344-01 — Host-cli review agents are spawned with isolation flags, recorded on the gate entry

## Objective

The host-cli review agents are spawned with no isolation (`codex exec --json --skip-git-repo-check -`, `claude -p --output-format json`), so the reviewer loads the operator's own MCP servers, plugins, hooks and global instruction files, and shares their blind spots (rec-20261030-010). A probe on the operator's PC (`probe/PROBE-RESULTS.md`, codex-cli 0.156.1, Claude Code 2.1.330) measured what each candidate flag does. This phase passes the strongest measured variant that needs no copy of the login and no environment change: `--ignore-user-config` for the codex family and `--setting-sources project --strict-mcp-config` for the claude family; records the flags passed on the SUMMARY's gate entry; adds `verification.hostCliIsolation: "on" | "off"` (absent means on) as the way to turn it off; and reports it in `cadence doctor`. The claim is narrow: these flags are passed and recorded. The global `AGENTS.md` and `CLAUDE.md` still reach the reviewer (measured), and project-level files and hooks still apply because the child runs in the project directory (rec-20260916-004); both are documented, not fixed.

## Acceptance Criteria

### AC-1: the codex family is spawned with --ignore-user-config
Given the binary name `codex` and isolation on
When `hostCliJSON` spawns it through an injected spawn, once with no model and once with model `gpt-5`
Then the argv is `['exec','--json','--skip-git-repo-check','--ignore-user-config','-']` and `['exec','--json','--skip-git-repo-check','--ignore-user-config','-m','gpt-5','-']`; the prompt is written to stdin as before; and through `makeRealSpawn({ platform: 'linux', spawn })` the spawn options are `{ stdio: ['pipe','pipe','pipe'] }` with no `env` key

### AC-2: the claude family is spawned with --setting-sources project --strict-mcp-config
Given the binary name `claude` and isolation on
When `hostCliJSON` spawns it through an injected spawn, once with no model and once with model `opus`
Then the argv is `['-p','--output-format','json','--setting-sources','project','--strict-mcp-config']` and `['-p','--output-format','json','--setting-sources','project','--strict-mcp-config','--model','opus']`; a binary named `my-reviewer` (its basename does not contain `codex`) gets the same claude argv, under the existing family rule

### AC-3: hostCliIsolation "off" restores the pre-phase argv, for all seven selectors and call sites
Given `hostCliIsolation: 'off'` passed in `VerifierSelectOptions`, with an injected `spawnImpl`
When each of the seven selectors (`selectVerifier`, `selectPerTaskVerifier`, `selectCodeReviewVerifier`, `selectSecurityAuditVerifier`, `selectPlanReviewVerifier`, `selectSpecReviewVerifier`, `selectUiSpecReviewVerifier`) makes one call, for binary `codex` and for binary `claude`
Then the argv is `['exec','--json','--skip-git-repo-check','-']` for codex and `['-p','--output-format','json']` for claude; with the option absent or `'on'` the same selectors produce the AC-1 and AC-2 no-model argv. Each of the seven call sites that pass `fallback` (`services/settle.ts` for deep-verify, code-review and security-audit; `gates/draft-context.ts`; `gates/build-context.ts`; `services/spec-approve-ports.ts` for spec-review and ui-spec-review) also passes `verification.hostCliIsolation` from the loaded config when it is set. The key is an optional enum: a `config.json` holding `{}` loads through `loadConfig` with the key absent, it is absent from `defaultConfig` and from a fresh `cadence init`'s `config.json`, and `"Off"`, `true` and `null` are rejected by `loadConfig`

### AC-4: a CLI that rejects an isolation flag fails loudly and is not retried without it
Given an injected spawn that exits 2 with stderr `error: unexpected argument '--ignore-user-config' found` for `codex`, and one that exits 1 with stderr `error: unknown option '--setting-sources'` for `claude`
When the code-review host-cli verifier selected by `selectCodeReviewVerifier` makes one call, under the default fallback and under `fallback: 'refuse'`
Then the injected spawn was called once in each of the four cases; under the default the warning passed to `warn` contains `falling back to mock provider for this call` and the hint `this CLI may not accept the isolation flag "--ignore-user-config"; update it, or set verification.hostCliIsolation to "off"` (for claude, the same hint naming `"--setting-sources"`); under refuse the thrown `VerifierFallbackRefusedError`'s message contains the same hint. The hint is added only when the child's stderr contains a `--`-prefixed isolation flag that was passed, and names the first such flag in `hostCliIsolationFlags(family)` order: a `nonzero-exit` whose stderr is `not authenticated` or `no project found` carries no hint, and with isolation off no hint is added. Not covered: a CLI that accepts the flags but fails because the user configuration it now skips held something it needed (a model provider, a proxy, an API-key helper); that failure is loud; whether it carries the hint depends only on whether its stderr names a passed flag, and this AC does not assert it. Also not covered: a wrapper that echoes its own command line on stderr before failing for another reason; the hint then names a flag it should not, which is why it says `may`

### AC-5: the gate entry records the isolation flags that were passed
Given `runSettleGates` runs deep-verify and code-review with host-cli verifiers on an injected spawn, binary `claude`, isolation on, `CLAUDECODE` stubbed empty
When the gates pass
Then the `deep-verify` and `code-review` entries each carry `hostCliIsolation: ['--setting-sources','project','--strict-mcp-config']` (for binary `codex`: `['--ignore-user-config']`), and so does a `security-audit` entry produced, under the same conditions, by a host-cli security-audit verifier that spawned its child. The list is `hostCliIsolationFlags(inferFamily(bin))`, the same helper `buildInvocation` uses, and is attached only on the path that called `hostCliJSON`. The field is absent: when isolation is off; when the provider is mock; when the call fell back to mock; when the host-cli verifier returned without spawning (no ACs; no files and an empty diff); on a deep-verify entry whose verifier threw and `--allow-verifier-failure` recorded the failure; and on a code-review or security-audit entry whose verifier threw and was bypassed. `GateProvenanceZ` accepts the field as an optional string array, a SUMMARY written before this phase (no such field) still parses, and `summary verify` reports a matching content hash for a SUMMARY whose gate entries carry the field. Not covered: `per-task-verify` entries and the plan-review, spec-review and ui-spec-review sidecars. A `refused` entry, and a code-review or security-audit entry whose `providerSelection` is `empty-diff`, carry the field exactly when their host-cli child was spawned with isolation on; this AC does not assert either

### AC-6: cadence doctor reports the isolation the configured binary gets
Given a config whose `verifier.provider` is `host-cli`
When the doctor checks run with `CADENCE_HOST_CLI_BIN=codex`, with it unset (binary `claude`), with `CADENCE_HOST_CLI_BIN=/opt/bin/my-reviewer`, and with `verification.hostCliIsolation: "off"`
Then a check named `host-cli-isolation` reports: for codex, severity `ok` with `host-cli reviews run "codex" with --ignore-user-config; the global AGENTS.md still reaches the reviewer`; for claude, `ok` with `host-cli reviews run "claude" with --setting-sources project --strict-mcp-config; the global CLAUDE.md still reaches the reviewer`; for `/opt/bin/my-reviewer`, the claude message quoting that value verbatim; with `"off"`, severity `warning` with `host-cli isolation is off (verification.hostCliIsolation): reviews inherit the user's own configuration`. When no seam's configured provider is `host-cli` (the rule `assessReadiness` uses) the check is `ok` with `no review gate uses host-cli`, whatever `hostCliIsolation` says. The check takes `env` as an argument and uses no spawn function

### AC-7: the docs state what is passed, what was measured and what still reaches the reviewer
Given `docs/providers.md`, `docs/reference/config.md`, `docs/reference/commands.md`, `docs/concepts.md` and the changeset
When phase 344 ships
Then the host-cli section of `providers.md` contains both command lines (`codex exec --json --skip-git-repo-check --ignore-user-config -` and `claude -p --output-format json --setting-sources project --strict-mcp-config`) and states: for codex, about what the flag skips, only what `--help` says (`config.toml` is not loaded; auth still uses `CODEX_HOME`) and that the global `AGENTS.md` was measured to still reach the reviewer, with no claim that MCP servers, plugins or hooks were measured as dropped; for claude, that the flags were measured to stop a user-level hook, the user's installed plugins and the MCP servers, and that the global `CLAUDE.md` still reaches the reviewer; that project-level instruction files and hooks still apply; that a model or effort level chosen in user configuration is expected no longer to apply, with `<seam>.model` and `verification.hostCliIsolation: "off"` named as the remedies, and that sign-in settings kept in user configuration are expected to be skipped too, both stated as inferred from what the flags skip and not measured. `config.md` documents the key with its two values and that absent means on. `commands.md` lists the `host-cli-isolation` doctor check with its severities and says the `"off"` warning has no automatic fix. `concepts.md`'s gate-provenance field list gains `hostCliIsolation`. A minor changeset for cadence-core and cadence-types names both flag sets, `verification.hostCliIsolation`, and that the global `AGENTS.md`/`CLAUDE.md` and project files still reach the reviewer. A doc-content test asserts these

## Boundaries

- Do NOT set `CODEX_HOME`, `CLAUDE_CONFIG_DIR` or any other environment variable for the child, and do NOT copy any credentials file: the probe showed a login-only `CODEX_HOME` works, and the operator chose not to ship it.
- Do NOT pass `--bare` or any flag the probe did not measure.
- Do NOT add a retry of a failed host-cli call, with or without the isolation flags.
- Do NOT change the fallback decision: a `nonzero-exit` is still a loud mock fallback by default and a refusal under `verification.fallback: "refuse"`.
- Do NOT change the self-invocation guard, the stdin prompt path, the win32 command resolver, the timeout handling or the family rule (`codex` in the binary's basename, else claude).
- Do NOT claim in docs, help or the changeset that the reviewer is fully isolated, or that anything was dropped that `probe/PROBE-RESULTS.md` did not measure.
- Do NOT edit an existing test beyond the two named edits (the nine argv pins in `host-cli-client.test.ts`; the codex command-line substring in `providers-host-cli-windows.test.ts`).
- Do NOT add a CLI flag, an environment variable or an MCP parameter for the setting, and do NOT add a runtime dependency.
- Do NOT touch `per-task-verify`'s PROGRESS records or the plan-review, spec-review and ui-spec-review sidecars.
