# 317-01 — Hook Blocking via JSON Decisions

## Objective

Every `ok: false` a CADENCE hook handler returns is delivered to the host as a per-event JSON decision on stdout, exit `0` (`dec-20260925-001`) — a transport that does not depend on exit-code propagation — replacing the `process.exitCode = 2` transport that checkpoint Phase 0.4a proved collapses to a non-blocking `1` on Windows when a hook is spawned through `powershell.exe`.

## Acceptance Criteria

### AC-1: PreToolUse deny shape — explicit per-site assertion matrix required
Given each of `handlePreToolEdit`'s three `ok: false` sites individually — `handlers.ts:177` (boundary block), `:230` (redundant-work block), `:256` (build-gate block) — dispatched from the abstract event `pre-tool-edit`, which `packages/core/src/hooks/dispatcher.ts:31-32` routes to the `handlePreToolEdit` handler and which `packages/host-toolkit/src/routing.ts:69-77`'s `EVENT_TABLE` maps from the real host event `PreToolUse` (two distinct mappings, in two different files — not one step),
When each site's handler returns `ok: false`,
Then stdout carries exactly one well-formed JSON document `{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"deny","permissionDecisionReason":<blockMessage>}}` and the process exits `0`. (Shape verified verbatim against the raw hooks doc, `curl -sL https://code.claude.com/docs/en/hooks.md`, 2026-09-25.)

**Coverage requirement, not optional:** under this repo's `coverageMode: assertion`, one test that merely contains the `AC-1` token would satisfy the gate while exercising only one of the three sites. The DRAFT's tasks must require **one asserting case per site** (three cases minimum), or — preferably, matching the house pure-core/impure-shell pattern — extract a pure `renderHookResult(event, result): string` function that `hook.ts` calls to build its stdout, and assert that pure function once per input shape (`PreToolUse`-deny, `Stop`/`SubagentStop`-block, `ok:true`+`contextPayload`, combined). The renderer approach collapses "one chokepoint, tested once per shape" into a single well-covered unit, which is both cheaper and harder to under-cover than three separate integration tests through the full handler stack.

### AC-2: Stop / SubagentStop top-level block shape
Given `handleSessionStop`'s one `ok: false` site (`handlers.ts:297`, dispatched from `session-stop` ← real `Stop` event, per `EVENT_TABLE` in `packages/host-toolkit/src/routing.ts:69-77` — not `dispatcher.ts`, which maps the *abstract* event to its handler function, a separate mapping; see Constraints) or `handleSubagentResult`'s one `ok: false` site (`handlers.ts:368`, dispatched from `subagent-result` ← real `SubagentStop` event, same table),
When the handler returns `ok: false`,
Then stdout carries the top-level `{"decision":"block","reason":<blockMessage>}` document — the raw doc states `SubagentStop` "use[s] the same decision control format as Stop hooks" verbatim — and the process exits `0`.

> **As built (2026-09-26, settle of 317-01):** this caveat and the Constraints' "only four are reachable" count describe this phase's own base. Phase 318 (`rec-20260926-001`, PR #540), stacked on this branch and merging after it, makes `routing.ts` forward `agentId`/`agentType`, so once 318 lands Claude Code's `SubagentStop` block path (`handlers.ts:368`) is reachable through a real host and five sites are reachable. Codex's declared gap is unaffected (`rec-20260926-003`). 317's DRAFT and tests treat the direct `SubagentStop` unit test and its exclusion from AC-4 as scope, not as a reachability claim.

**Reachability caveat, `Stop` vs. `SubagentStop` differ, and Claude Code vs. Codex differ too (`dec-20260926-001`, `ev-20260926-002`):** `Stop`'s block path is live and reachable through a real host today. `SubagentStop`'s is **not**, but for two *different* reasons per host:

A real, pre-existing bug, filed as `rec-20260926-001`.
- **Codex**: has its own separate `routeHookEvent` (`packages/host-codex/src/shim.ts`, not shared with `host-toolkit`) which never attempts to extract `agentId`/`agentType` at all — matching `capabilities.ts:35`'s explicit `agentIdentification: false` declaration. This is a **declared, loudly-notified gap** (`handlers.ts`'s `noticeIfAgentIdentificationUnsupported` fires correctly), not a defect.

This phase still specifies and tests `SubagentStop`'s shape — the JSON transport fix is correct and forward-compatible regardless — but the asserting test for it **constructs `handleSubagentResult`'s `ok: false` result directly** (a pure unit test of `hook.ts`'s transport layer), not through a real shim/stdin fixture the way `Stop`'s half of this AC and AC-4 do. Do not claim or imply real-host reachability for `SubagentStop` in the DRAFT or in evidence capture until `rec-20260926-001` ships. Codex's gap is declared and loudly notified today (correct, no fix needed to keep working as designed) — but the *reason* given for declaring it (`capabilities.ts`'s comment that agent-identity fields are "undocumented" for Codex's `SubagentStop`) is now stale: Codex's current docs (`developers.openai.com/codex/hooks.md`) do document `agent_id`/`agent_type` as `SubagentStop` input fields, meaning the gap is closable, not permanent. Filed as `rec-20260926-003` — not this phase's scope either way.

### AC-3: Runner control — the collapse is real on the CI/dev box, not assumed
Given a fixture that spawns `powershell.exe` directly as the executable — never via Node's `spawn(..., { shell: true })` on win32, which resolves to `cmd.exe`, not PowerShell, and would test nothing — with `args: ['-NoProfile', '-Command', "node -e 'process.exit(2)'"]` (the un-wrapped form; no trailing `exit $LASTEXITCODE`),
When the fixture runs on Windows,
Then the observed exit code is `1`, not `2` — reproducing checkpoint 0.4a's finding and this SPEC's own independent reproduction (2026-09-25: exactly this command, run directly, observed `$LASTEXITCODE` = `1`; appending `; exit $LASTEXITCODE` to the `-Command` string restores `2`). If a given runner's PowerShell does *not* collapse the code, the fixture must fail loudly (not silently pass) — a control that never triggers proves nothing about AC-4.

### AC-4: The fix, proven on the same runner, through the real chain — three named, reachable cases
Given the **actual command a real `install --local` writes into `settings.json`** — captured by running `cadence-host-claude-code install --local` against a scratch project and reading the installed hook entry back out, never a hand-written equivalent. host-claude-code's `resolveLocalPaths()` (`packages/host-claude-code/src/locate-self.ts:16`) is a thin wrapper around host-toolkit's `resolveAdapterLocalPaths()` (`packages/host-toolkit/src/locate-self.ts:25-33`), which returns **absolute** paths (`resolve(distDir, 'cli.js')`), so the real command is machine-absolute, not the relative `packages/...` form; the fixture must use whatever `install --local` actually produced on the runner it's executing on. No event name is ever passed as a CLI argument — the shim reads `hook_event_name` from stdin JSON and only then spawns core's `cadence hook <abstractEvent>` as its own child with `stdio: ['pipe','inherit','inherit']`, relaying core's exit code unchanged (confirmed by direct read of `packages/host-claude-code/src/cli.ts:90-158`) — spawned via `powershell.exe -NoProfile -Command "<that captured command>"` (the same outer form AC-3 proved collapses; note this is 0.4a's confirmed reproduction shape, not a confirmed statement of Claude Code's own exact invocation form — see Constraints),

**this AC requires exactly three named, real, state-driven cases** (a handler cannot be "forced" inside a real three-process chain — the state has to actually put it there). **The `:256` case below is not hypothetical — it has already been run for real, end-to-end, and captured as `317-01-red-state-capture.md`** in this phase directory: a real `install --local`, its real installed command read back out of `settings.json` (confirmed absolute paths, not the relative form an earlier draft assumed), spawned via `powershell.exe -NoProfile -Command` with a real `PreToolUse`/`Write` payload piped to real stdin (a separate probe first confirmed piped stdin survives this exact spawn form — also in that file). Observed: exit code `1` (not `2`), empty stdout, the real `blockMessage` on stderr — the collapse, reproduced on the actual production code path, not inferred from checkpoint 0.4a's `Stop`-only reproduction.
1. **`handlers.ts:256`** (`handlePreToolEdit`'s build-gate block) — reached by `config.hooks.preToolUseBuildGate: true` with `loopPosition` anything but `BUILD`, then a `PreToolUse` edit. **Already captured red** (see above); post-fix, the same setup and spawn must instead observe the JSON deny document on stdout and exit `0`.
2. **`handlers.ts:230`** (`handlePreToolEdit`'s redundant-work block) — reached by setting up a phase with `redundantWorkEnforcement: block`, a task already `DONE`, and a `PreToolUse` edit touching that task's declared file. This is the **only** reachable site whose `blockMessage` contains non-ASCII text (an em dash) as written today — required in addition to case 1, specifically to prove the UTF-8-survives-the-pipe claim (measured 2026-09-25: `e2 80 94`/`e2 86 92` survive this exact spawn form — see Constraints) on a real end-to-end path, not just the isolated `emit.js` probe.
3. **`handlers.ts:297`** (`handleSessionStop`) — reached by setting `loopEnforcement: strict` with an open draft, then dispatching `Stop`. ASCII-only message; proves the top-level `decision:block` shape end-to-end. (Non-ASCII is already proven by case 2 — this case doesn't need to repeat it.)

When each hook runs end-to-end (the fixture's outer `powershell.exe -NoProfile -Command` wrapper — the reproduction form, not a claim about Claude Code's own invocation, see Constraints — → the shim → core, all three hops real processes),
Then the **outer** process's stdout is exactly one well-formed JSON document matching that case's shape (AC-1 for cases 1–2, AC-2 for case 3), byte-for-byte for case 2's non-ASCII text, and the outer process exits `0`. This also proves the host-claude-code shim's relay is correct end-to-end for both shapes, without a separate assertion. `handlers.ts:368` (`SubagentStop`) is explicitly excluded from this AC, per AC-2's reachability caveat.

### AC-6: Combined `ok: false` + `contextPayload` — PreToolUse only; no documented combined shape for Stop/SubagentStop
Given a `PreToolUse`-dispatched handler returning both `ok: false` and a `contextPayload` — **a contract case: no handler in `handlers.ts` returns both today** (confirmed by direct read of all five `ok: false` sites), so this AC covers a combination the current code never produces but the new transport's design must not break if a future handler does,
When such a handler runs,
Then stdout is exactly one JSON document: `{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"deny","permissionDecisionReason":<blockMessage>,"additionalContext":<contextPayload>}}` — the raw doc's `PreToolUse` decision-control field table documents `additionalContext` as "ignored when `permissionDecision` is `defer`" (implying honored for every other value, `deny` included), pinned by a test that constructs the case directly.

**Stop/SubagentStop have no *documented* combined shape — that is the precise claim, not "cannot combine."** The raw doc presents `additionalContext` as the non-blocking alternative to `decision:"block"` for these two events (the summary table's phrasing, and the `Stop` section's "unlike `decision: block` it is shown... as hook feedback rather than a hook error"), and shows no example combining them. That is evidence of *no documented support*, not proof of an *enforced prohibition* — the doc simply never demonstrates or claims the combination works. (An earlier draft of this SPEC overstated this in the opposite direction, wrongly claiming a doc-verified combined shape based on `UserPromptSubmit`'s genuinely-combined example, which doesn't extend to `Stop`/`SubagentStop`.) Since neither of our real `Stop`/`SubagentStop` sites (`handlers.ts:297`, `:368`) produces a `contextPayload` today, this phase does not attempt the combination either way: if a future `Stop`/`SubagentStop` handler ever needs both, that needs its own verification (a live test against a real host, since the doc doesn't settle it), not an assumption in either direction.

### AC-7: `doctor` reports hook-transport posture — a new, concretely-scoped check, Claude Code only, sharing `host-hooks`'s own install-state classification
Given a new `doctor` check, `hook-transport` (naming convention matches existing checks like `host-hooks`, `codex-hooks` in `packages/core/src/doctor/run.ts`) — **scoped to `.claude/settings.json` only**, since the `shell: "bash"|"powershell"` field and its Git-Bash-detection fallback rule are Claude Code-specific protocol details (confirmed against the raw hooks doc); Codex's own hook-spawning mechanism and `.codex/hooks.json` format are different and not known to share this specific behavior, so this check does not attempt to interpret them. `runDoctor` (`run.ts:2657-2686`) calls each check independently in sequence — `checkHostHooks` does not hand its `DoctorCheck` result to any other check — so `hook-transport` does not read `host-hooks`'s output; instead, `checkHostHooks`'s install-state classification (`run.ts:400-455`: missing file, invalid JSON, missing managed entries, stale scope, no managed entries, or genuinely present-and-complete — six real branches, not the two this SPEC's first two drafts assumed) is extracted into a shared, pure helper function both checks call independently, so the two never disagree about which state the install is in,
When `cadence doctor` runs, `hook-transport` returns one concrete `DoctorCheck` per classification (never an "omitted" non-result — every doctor check returns a `DoctorCheck`):
- **Missing file** → `pass('hook-transport', 'Not applicable — no .claude/settings.json here.')`, mirroring `host-hooks`'s own wording for the same state.
- **Invalid JSON, missing managed entries, stale scope, or no managed entries at all** (the four states `host-hooks` itself reports as warning/error) → `pass('hook-transport', 'Not applicable — host-hooks reports an install problem; fix that first.')`. This is a concrete, deliberate result — not a silent skip and not a second, confusingly-reassuring informational line sitting next to a real warning.
- **Genuinely present and complete** (`host-hooks`'s only real `pass`, `run.ts:433-437`) → proceed to the `shell`-field outcomes below.

**Mixed `shell` settings across the installer's multiple managed entries:** `install.ts` builds one `command` string and reuses it verbatim across every managed hook entry (`plain()`/`matched()`, `install.ts:81-90`) — under CADENCE's own installer, every entry's `shell` field (or absence of one) is always identical, so there is no real "mixed" case to handle *from an unmodified install*. If an operator hand-edits `settings.json` afterward to diverge entries' `shell` fields, `hook-transport` inspects only the first managed CADENCE entry it finds and states that scope explicitly in its output ("checked the first managed hook entry; hand-edited divergence across entries is not detected") — reconciling hand-edited divergence is `host-hooks`'s completeness-checking territory, not this check's.
- **Rule stated, not measured** — no `shell` field set on that entry: report "no `shell` field is set on the installed hook command — per Claude Code's own docs this defaults to `bash`, or to `powershell` on Windows when Git Bash isn't installed; CADENCE blocks via a JSON decision on stdout regardless of which shell runs it, so this is informational, not a warning." This is the documented *rule*, not a measurement — no attempt is made to detect which shell a given machine will actually resolve to, since that's not observable from `settings.json` alone (`dec-20260926-002`).
- **Configured value reported** — `shell: "powershell"` or `shell: "bash"` explicitly set on that entry: report that literal configured value instead of the inferred rule.
- **Unsupported value** — the `shell` key is present on that entry but its value is anything other than the exact strings `"bash"` or `"powershell"` (e.g. `"zsh"`, `"pwsh"`, `""`, `null`, a number): return `fail('hook-transport', 'warning', <detail>, <remediation>)` (the existing helper in `packages/core/src/doctor/model.ts:52-60`; there is no `warn()` helper) whose detail names the literal value as found (JSON-serialized, so `null` and `""` are distinguishable), states that Claude Code documents only `"bash"` and `"powershell"` for this field (raw doc, line ~460), and whose remediation is "remove the `shell` field or set it to `\"bash\"`/`\"powershell\"`, or re-run `cadence-host-claude-code install`." A present-but-`null` key is this case, not the "no `shell` field" case above — only an absent key takes the rule-stated path.

`docs/reference/commands.md`'s doctor table gains the `hook-transport` row in the same commit.

## Constraints

- **Decisions recorded:** `dec-20260925-001` (D-BN — JSON decision on stdout, exit `0`, per event; not JSON+exit-2, undocumented interaction; not exit-2-only with a forced installer shell, which makes every CADENCE gate depend on Git Bash being installed — the same environmental assumption that just failed silently). `dec-20260926-002` (D-BP — `doctor` states the rule, doesn't claim to measure the resolved shell). `dec-20260926-003` (D-BO — `doctor` posture now, settle-time anomaly filed as `rec-20260926-002` not built here). `dec-20260926-001` (correction: the `SubagentStop`-unreachable bug is Claude-Code-specific; Codex's inertness is a declared, correctly self-reported gap, not a defect).
- **`-NoProfile -Command` is checkpoint 0.4a's confirmed reproduction shape, not a confirmed statement of Claude Code's own exact hook-spawn invocation.** AC-3/AC-4's fixtures mirror what 0.4a's probe used and what this SPEC independently reproduced — they are not asserting that Claude Code itself spawns hooks with exactly these flags, only that this invocation form (which a real host-spawned hook plausibly matches, per the raw doc's "PowerShell when Git Bash isn't installed" shell-form description) collapses exit codes the way 0.4a observed.
- **Shapes verified against the raw doc, not a summarizer** (`curl -sL https://code.claude.com/docs/en/hooks.md`, 2026-09-25 — a summarizing fetch mis-stated this exact page during checkpoint 0.4a). `PreToolUse` → `hookSpecificOutput.permissionDecision` (doc line ~217). `Stop` (line ~2622), `SubagentStop` (line ~2417, "same decision control format as Stop hooks"), `ConfigChange` (line ~2779), `TaskCreated` (JSON alternative to exit 2, line ~2467) → top-level `{"decision":"block","reason":...}`.
- **Corrected handler/event breakdown** (the originating handoff did not give per-handler counts; verified here by direct read): all **three** of this repo's `handlePreToolEdit` `ok: false` sites use the `PreToolUse` shape (AC-1). The remaining **two** sites — one each in `handleSessionStop` (`Stop`) and `handleSubagentResult` (`SubagentStop`) — use the top-level shape (AC-2). Five sites total, matching the handoff's count, but 3+2 by handler, not 2+3. **Of those five, only four are reachable through a real host today** — `handleSubagentResult`'s site (`:368`) is not, per AC-2's reachability caveat and `rec-20260926-001`.
- **The `shell` hook-config field is real and documented** (raw doc, line ~460): accepts `"bash"` or `"powershell"`; defaults to `"bash"`, or to `"powershell"` on Windows when Git Bash isn't installed — and per line ~3801, that resolution prefers `pwsh.exe` (PowerShell 7+) when present, falling back to `powershell.exe` (Windows PowerShell 5.1) otherwise. This field governs *Claude Code's own* hook spawning and cannot be exercised from a CI test (Claude Code never runs in CI) — AC-3/AC-4 instead spawn `powershell.exe` directly, sidestepping the auto-detection question entirely for the fixture.
- **PowerShell 5.1 vs. pwsh 7, honestly unresolved.** This machine has no `pwsh` installed (`where pwsh` → not found; only `C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe`), so only 5.1's behavior is measured here. The raw doc (line ~1678) says Claude Code only registers the PowerShell tool when Git Bash is undetected, and checkpoint 0.4a's session had Git Bash undetected — but that says nothing about *which* PowerShell executable was present on 0.4a's machine, and this SPEC has no way to confirm whether it was the same box. Treat 0.4a's finding and this SPEC's own reproduction as two independent 5.1 measurements, not one machine's result counted twice. Whether `pwsh` 7 exhibits the same `-Command` exit-code collapse is **not tested by this SPEC or by 0.4a** — genuinely open. It does not change this phase's design: AC-3/AC-4 target `powershell.exe` directly because that is the confirmed-broken, still-commonly-present executable, independent of what a user's default shell resolution happens to prefer.
- **The collapse mechanism** (reproduced independently on this box, 2026-09-25, beyond the 0.4a report): `powershell.exe -NoProfile -Command "<command>"` does not propagate a wrapped native command's real exit code as its own process exit code; appending `; exit $LASTEXITCODE` restores it.
- **Non-ASCII survives the pipe, measured.** `powershell.exe -NoProfile -Command "node emit.js"`, captured via a Node parent with `stdio: ['pipe','pipe','inherit']` (i.e. the way any programmatic caller, including Claude Code, would actually read a hook's stdout — never a terminal), delivers UTF-8 byte-for-byte: an em dash (`e2 80 94`) and an arrow (`e2 86 92`) round-tripped through `JSON.parse` unchanged (measured 2026-09-25). No ASCII-escaping fallback is needed in the transport design. Reproducible: `317-01-probe-emit.js` + `317-01-probe-encoding.js`, committed in this phase directory.
- **Newly-active blocking is a behavior change, not just a transport change.** On a PowerShell-default Windows install, `preToolUseBuildGate`, `boundaryEnforcement: block`, `redundantWorkEnforcement: block`, and `loopEnforcement: strict`'s `Stop` block have all been silently inert (the edit/stop proceeds regardless of config). After this phase, they will actually block for the first time on that platform. This is a fix, not a regression, but it changes observable behavior for anyone currently relying on the inert state — the changeset must say so explicitly.
- **Host-honoring proof is not a numbered AC.** That the host itself actually refuses the edit or the stop cannot be a CI assertion — this repo forbids tests that depend on a live host. AC-1 through AC-4 assert only the transport (stdout shape, exit code). A real Claude Code session's transcript + `hooks.jsonl`, captured manually pre- and post-fix, is committed as evidence in the phase directory and cited in the DRAFT/SUMMARY — not linked to a coverage-gated AC token (`rec-20260907-006` is the open, adjacent problem: deep-verify cannot accept command output as evidence).
- **The installer** (`packages/host-claude-code/src/install.ts`) registers hook entries as `{ type: 'command', command }` with no `shell` field today — confirmed by direct read, not grep alone (grep for `shell:`/`command:` under-matched due to object-literal line spacing).
