# 317-01 — Hook Blocking via JSON Decisions

## Objective

Every `ok: false` a CADENCE hook handler returns is delivered to the host as a per-event JSON decision on stdout, exit `0` (`dec-20260925-001`), honored regardless of which shell the hook runs under — replacing the `process.exitCode = 2` transport that checkpoint Phase 0.4a proved collapses to a non-blocking `1` on Windows when a hook is spawned through `powershell.exe`.

## Acceptance Criteria

### AC-1: PreToolUse deny shape
Given any of `handlePreToolEdit`'s three `ok: false` sites (`handlers.ts:177` boundary block, `:230` redundant-work block, `:256` build-gate block — confirmed by direct read, all three in this one function, all dispatched from the `pre-tool-edit` abstract event which `dispatcher.ts` maps to the real `PreToolUse` hook),
When the handler returns `ok: false`,
Then stdout carries exactly one well-formed JSON document `{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"deny","permissionDecisionReason":<blockMessage>}}` and the process exits `0`. (Shape verified verbatim against the raw hooks doc, `curl -sL https://code.claude.com/docs/en/hooks.md`, 2026-09-25.)

### AC-2: Stop / SubagentStop top-level block shape
Given `handleSessionStop`'s one `ok: false` site (`handlers.ts:297`, dispatched from `session-stop` ← real `Stop` event) or `handleSubagentResult`'s one `ok: false` site (`handlers.ts:368`, dispatched from `subagent-result` ← real `SubagentStop` event — both mappings confirmed directly in `packages/host-toolkit/src/routing.ts`'s `EVENT_TABLE`, not inferred),
When the handler returns `ok: false`,
Then stdout carries the top-level `{"decision":"block","reason":<blockMessage>}` document — the raw doc states `SubagentStop` "use[s] the same decision control format as Stop hooks" verbatim — and the process exits `0`.

### AC-3: Runner control — the collapse is real on the CI/dev box, not assumed
Given a fixture that spawns `powershell.exe` directly as the executable — never via Node's `spawn(..., { shell: true })` on win32, which resolves to `cmd.exe`, not PowerShell, and would test nothing — with `args: ['-NoProfile', '-Command', "node -e 'process.exit(2)'"]` (the un-wrapped form; no trailing `exit $LASTEXITCODE`),
When the fixture runs on Windows,
Then the observed exit code is `1`, not `2` — reproducing checkpoint 0.4a's finding and this SPEC's own independent reproduction (2026-09-25: exactly this command, run directly, observed `$LASTEXITCODE` = `1`; appending `; exit $LASTEXITCODE` to the `-Command` string restores `2`). If a given runner's PowerShell does *not* collapse the code, the fixture must fail loudly (not silently pass) — a control that never triggers proves nothing about AC-4.

### AC-4: The fix, proven on the same runner, through the real chain
Given the exact command `install.ts` registers for a local build — `node packages/host-claude-code/dist/cli.js hook --cadence "node packages/core/dist/cli/index.js"` (confirmed via `locate-self.ts`'s `shimCli`/`coreCli` resolution; no event name is ever passed as a CLI argument — the shim reads `hook_event_name` from stdin JSON and only then spawns core's `cadence hook <abstractEvent>` as its own child with `stdio: ['pipe','inherit','inherit']`, relaying core's exit code unchanged — confirmed by direct read of `packages/host-claude-code/src/cli.ts:90-158`, mirroring `host-codex/src/cli.ts` exactly) — spawned via `powershell.exe -NoProfile -Command "<that command>"` (the same outer form AC-3 proved collapses), with realistic Claude-Code-shaped stdin JSON (`hook_event_name`, `tool_name`, `tool_input`, etc.) piped to it, and a handler forced to return `ok: false` with a `blockMessage` containing non-ASCII text (an em dash and an arrow, matching this codebase's own message style),
When the hook runs end-to-end (Claude Code's outer PowerShell spawn → the shim → core, all three hops real),
Then the **outer** process's stdout is exactly one well-formed JSON document matching AC-1 or AC-2's shape, with the non-ASCII text intact byte-for-byte (measured 2026-09-25: UTF-8 multi-byte sequences for `—` (`e2 80 94`) and `→` (`e2 86 92`) survive this exact spawn form unmangled when the parent captures stdout via a pipe — see Constraints), and the outer process exits `0`. This also proves the host-claude-code shim's relay is correct end-to-end, without a separate assertion.

### AC-5: Byte-identical non-block paths
Given a handler returning `ok: true` with a `contextPayload`,
When the hook runs,
Then stdout is byte-identical to the pre-change output. Capture the fixture before touching any transport code — this is the regression bar.

### AC-6: Combined `ok: false` + `contextPayload`
Given a handler returning both `ok: false` and a `contextPayload` — **a contract case: no handler in `handlers.ts` returns both today** (confirmed by direct read of all five `ok: false` sites), so this AC covers a combination the current code never produces but the new transport's design must not break if a future handler does,
When such a handler runs,
Then stdout is one well-formed JSON document the host accepts, pinned by a test that constructs the case directly (not one that waits for a real handler to need it) — never two concatenated fragments. Today's ordering bug (`contextPayload` prints at `hook.ts:32`, before the `ok` check at `hook.ts:33`) is what this AC closes off for good.

### AC-7: `doctor` reports hook-shell posture

When `cadence doctor` runs,
Then it reports the resolved-or-inferred hook-shell posture and states that CADENCE blocks via JSON decisions, not exit codes — and says explicitly whether that posture is measured or inferred (per D-BP, still open). `docs/reference/commands.md`'s doctor table gains the row in the same commit.

### AC-8: `windows-latest` CI leg runs the real fixture, not skipped
Given AC-3 and AC-4's fixtures,
When the CI suite runs on the `windows-latest` leg,
Then both execute (neither skipped nor `continue-on-error`) and AC-3's control genuinely trips there too — if it doesn't (e.g. a future runner image changes PowerShell's behavior), the leg's result is not treated as a pass. Asserting test: a vitest spec that runs unconditionally on `process.platform === 'win32'`, not gated behind a Git-Bash-presence check — this repo's own CI runners have Git Bash on PATH by default (confirmed via CI run `36069320374`, job `test (windows-latest, 22)`: `git version 2.55.0.windows.5`), which is exactly why AC-3/AC-4 spawn `powershell.exe` directly instead of depending on the host's own shell-resolution.

### AC-9: A Codex-originated block is delivered in a form Codex's current docs treat as blocking
Given `host-codex`'s own hook shim relays core's child stdout/exit code transparently (`stdio: ['pipe','inherit','inherit']`, `process.exitCode = code ?? 0` — confirmed by direct read, mirroring `host-claude-code`'s own shim exactly),
When a handler returns `ok: false` for a Codex-originated hook call (identifiable via `ctx.raw.hostCapabilities`, already read at `handlers.ts:29` for `agentIdentification`),
Then the block is emitted in whichever form Codex's *current, freshly re-checked* documentation (not the dated `.cadence/research/codex-hooks.md` alone) states it treats as blocking — exit code `2`, the JSON decision, or both — pinned by a test in `packages/host-codex`. Whether that form is uniform with Claude Code's or host-specific is a DRAFT-time design choice (Open Questions); this AC only requires that whichever form is chosen is the one actually proven to block, not assumed to.

### AC-10: Accurate transport comment
Given `hook.ts:36`'s current comment `// Exit 2 = blocking per Claude Code hook protocol; stderr surfaces to the model.`,
When this phase lands,
Then the comment states the actual transport (per-event JSON decision on stdout, exit 0, host-aware per AC-9's resolution) and cites the checkpoint 0.4a finding it replaces. ## Constraints

- **Decision recorded:** `dec-20260925-001` settles D-BN — JSON decision on stdout, exit `0`, per event. Not JSON+exit-2 (undocumented interaction, unproven per-event). Not exit-2-only with a forced installer shell (makes every CADENCE gate depend on Git Bash being installed — the same environmental assumption that just failed silently).
- **Shapes verified against the raw doc, not a summarizer** (`curl -sL https://code.claude.com/docs/en/hooks.md`, 2026-09-25 — a summarizing fetch mis-stated this exact page during checkpoint 0.4a). `PreToolUse` → `hookSpecificOutput.permissionDecision` (doc line ~217). `Stop` (line ~2622), `SubagentStop` (line ~2417, "same decision control format as Stop hooks"), `ConfigChange` (line ~2779), `TaskCreated` (JSON alternative to exit 2, line ~2467) → top-level `{"decision":"block","reason":...}`.
- **Corrected handler/event breakdown** (the originating handoff did not give per-handler counts; verified here by direct read): all **three** of this repo's `handlePreToolEdit` `ok: false` sites use the `PreToolUse` shape (AC-1). The remaining **two** sites — one each in `handleSessionStop` (`Stop`) and `handleSubagentResult` (`SubagentStop`) — use the top-level shape (AC-2). Five sites total, matching the handoff's count, but 3+2 by handler, not 2+3.
- **The `shell` hook-config field is real and documented** (raw doc, line ~460): accepts `"bash"` or `"powershell"`; defaults to `"bash"`, or to `"powershell"` on Windows when Git Bash isn't installed — and per line ~3801, that resolution prefers `pwsh.exe` (PowerShell 7+) when present, falling back to `powershell.exe` (Windows PowerShell 5.1) otherwise. This field governs *Claude Code's own* hook spawning and cannot be exercised from a CI test (Claude Code never runs in CI) — AC-3/AC-4 instead spawn `powershell.exe` directly, sidestepping the auto-detection question entirely for the fixture.
- **PowerShell 5.1 vs. pwsh 7, honestly unresolved.** This machine has no `pwsh` installed (`where pwsh` → not found; only `C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe`), so only 5.1's behavior is measured here. The raw doc (line ~1678) says Claude Code only registers the PowerShell tool when Git Bash is undetected, and checkpoint 0.4a's session had Git Bash undetected — but that says nothing about *which* PowerShell executable was present on 0.4a's machine, and this SPEC has no way to confirm whether it was the same box. Treat 0.4a's finding and this SPEC's own reproduction as two independent 5.1 measurements, not one machine's result counted twice. Whether `pwsh` 7 exhibits the same `-Command` exit-code collapse is **not tested by this SPEC or by 0.4a** — genuinely open. It does not change this phase's design: AC-3/AC-4 target `powershell.exe` directly because that is the confirmed-broken, still-commonly-present executable, independent of what a user's default shell resolution happens to prefer.
- **The collapse mechanism** (reproduced independently on this box, 2026-09-25, beyond the 0.4a report): `powershell.exe -NoProfile -Command "<command>"` does not propagate a wrapped native command's real exit code as its own process exit code; appending `; exit $LASTEXITCODE` restores it.
- **Non-ASCII survives the pipe, measured.** `powershell.exe -NoProfile -Command "node emit.js"`, captured via a Node parent with `stdio: ['pipe','pipe','inherit']` (i.e. the way any programmatic caller, including Claude Code, would actually read a hook's stdout — never a terminal), delivers UTF-8 byte-for-byte: an em dash (`e2 80 94`) and an arrow (`e2 86 92`) round-tripped through `JSON.parse` unchanged (measured 2026-09-25). No ASCII-escaping fallback is needed in the transport design.
- **Newly-active blocking is a behavior change, not just a transport change.** On a PowerShell-default Windows install, `preToolUseBuildGate`, `boundaryEnforcement: block`, `redundantWorkEnforcement: block`, and `loopEnforcement: strict`'s `Stop` block have all been silently inert (the edit/stop proceeds regardless of config). After this phase, they will actually block for the first time on that platform. This is a fix, not a regression, but it changes observable behavior for anyone currently relying on the inert state — the changeset must say so explicitly.
- **Host-honoring proof is not a numbered AC.** That the host itself actually refuses the edit or the stop cannot be a CI assertion — this repo forbids tests that depend on a live host. AC-1 through AC-4 assert only the transport (stdout shape, exit code). A real Claude Code session's transcript + `hooks.jsonl`, captured manually pre- and post-fix, is committed as evidence in the phase directory and cited in the DRAFT/SUMMARY — not linked to a coverage-gated AC token (`rec-20260907-006` is the open, adjacent problem: deep-verify cannot accept command output as evidence).
- **The installer** (`packages/host-claude-code/src/install.ts`) registers hook entries as `{ type: 'command', command }` with no `shell` field today — confirmed by direct read, not grep alone (grep for `shell:`/`command:` under-matched due to object-literal line spacing).
- **The Codex relay is transparent, confirmed by direct read** (`packages/host-codex/src/cli.ts:141-152`, identical pattern in `packages/host-claude-code/src/cli.ts:134-151`): `spawn(exe, [...baseArgs, 'hook', abstractEvent], { stdio: ['pipe', 'inherit', 'inherit'], ... })` and `process.exitCode = code ?? 0`. This means whatever core emits, both shims forward unchanged — the relay itself is not the risk.
- **Whether Codex *honors* the new shape is genuinely unresolved (AC-9).** `.cadence/research/codex-hooks.md` (2026-05-13) documents exit `2` as Codex's explicit, table-level block mechanism and separately documents a JSON stdout shape as "Optional" — it does not state that `{"decision":"block"}` on exit `0` actually blocks a Codex `Stop` (as opposed to merely adding context). That research file predates this phase by four months and is not a substitute for re-checking Codex's current docs. Core already has the plumbing to branch by host (`ctx.raw.hostCapabilities`, `handlers.ts:29`) if the answer is "no."
- `host-codex`'s own child-spawn on Windows uses `shell: process.platform === 'win32'`, which Node resolves to `cmd.exe`, not PowerShell — a different hop from the one this phase fixes, and not known to share the collapse bug; whether *Codex's own* outer invocation of its shim has an equivalent Windows shell-collapse issue is unverified and out of scope here (file separately if discovered).
- No `PreCompact` handler (unauthorized, checkpoint arc Phase 4). No checkpoint `Stop` gate (unauthorized, checkpoint arc Phase 3 — direction recorded as an Open Question only).
- Tier **complex**: real `deep-verify` and `code-review` required; do not force-settle.
- **This project's `.cadence/config.json` configures `specReview.provider: "mock"`, `uiSpecReview`/`planReview`/`securityAudit` likewise — `verifier`, `perTaskVerifier`, and `codeReview` are the three configured `"host-cli"`.** `CADENCE_HOST_CLI_BIN=codex` only selects the binary *within* an already-`host-cli`-configured gate; it cannot upgrade a gate whose provider is literally configured as `mock`. This SPEC's own `spec approve` ran against that config and recorded a `mock`/`abstained` verdict in `317-01-SPEC-REVIEW.json` — not a real review. A manual, independent Codex review was run separately and committed as `317-01-SPEC-REVIEW-codex.md` in this phase directory; that file, not the sidecar, is this SPEC's actual review record. At BUILD time, `code-review` and the two verifier gates *are* configured `host-cli` — `CADENCE_HOST_CLI_BIN=codex` matters there and must be set.

## Open Questions

D-BN is decided (`dec-20260925-001`, see Constraints). The rest stay open — not settled — until the DRAFT is authored; record each with `cadence decision add` before BUILD starts, not after.

- **D-BO** — What, if anything, records a blocked-but-ignored hook? Options: (a) nothing, since JSON removes the failure mode; (b) `cadence doctor` reports the hook-shell posture (AC-7 already covers a version of this); (c) a settle-time anomaly if a block was emitted for an edit that landed in the diff anyway. (c) needs a state-schema change and is likely its own future phase — file it, don't build it here.
- **D-BP** — Can `doctor` observe the *actual* resolved hook shell, or only state the rule? If only inferable (no direct signal available), AC-7's doctor output must say it's stating the rule, not a measured fact.
- **D-BQ** — The checkpoint arc's future Phase 3 will add a `Stop` hook that blocks via JSON; after this phase, CADENCE's own `Stop` handler also blocks via JSON. Should Phase 3's hook be a separate registered entry, or a branch inside the existing `handleSessionStop`? The latter avoids two block decisions racing on one event. Direction only — do not build Phase 3 in this phase.
- Does `pwsh` (PowerShell 7) exhibit the same `-Command` exit-code collapse as Windows PowerShell 5.1? Untested by this SPEC (no `pwsh` on this box). Worth a follow-up probe on a machine or CI image that has both, since it affects which users the *old* transport was actually broken for — it does not affect this phase's fix.
- **Does Codex honor an exit-0 JSON `decision:block`, or only exit code 2?** (AC-9.) Resolve by re-fetching Codex's current hook docs directly — do not trust `.cadence/research/codex-hooks.md` as-is, it's four months old and was written when exit-2 was believed sufficient. If the answer is "exit 2 only," record a decision to make core's transport host-aware (via `ctx.raw.hostCapabilities`) rather than uniform, and file a separate recommendation for the Codex-specific follow-up work — this phase's non-goal is *building* that branch speculatively, not investigating whether it's needed.
- Does `host-codex`'s own outer invocation (Codex spawning its shim) share a Windows shell-collapse issue independent of the relay AC-9 verifies? Investigate during DRAFT/BUILD if time allows; file a separate recommendation if so — do not fix it here.
