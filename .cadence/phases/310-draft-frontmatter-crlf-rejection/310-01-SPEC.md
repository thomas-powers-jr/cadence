# 310-01 — DRAFT frontmatter parser rejects CRLF line endings

## Objective

`parseDraftMd` normalizes CRLF line endings before parsing so a DRAFT.md written or rewritten on Windows parses correctly instead of failing with a misleading "missing frontmatter" error.

## Acceptance Criteria

### AC-1: CRLF-terminated DRAFT.md parses identically to its LF equivalent
Given a well-formed DRAFT.md (valid frontmatter, Objective, Acceptance Criteria, Tasks, Boundaries sections) saved with `\r\n` line endings
When it is parsed by `parseDraftMd` (directly, or via `cadence draft check`)
Then parsing succeeds — no "missing frontmatter" error — and the resulting `Draft` object is field-for-field identical to parsing the same content saved with `\n` line endings, with no stray `\r` characters left in any string field (objective, AC given/when/then, task action/verify/files, boundaries)

### AC-2: A genuinely malformed frontmatter delimiter still fails loud
Given a DRAFT.md whose frontmatter delimiter is actually missing or malformed (e.g. no closing `---`), regardless of line-ending style
When it is parsed by `parseDraftMd`
Then parsing still throws the existing "DRAFT.md missing frontmatter" `CadenceError` — CRLF normalization must not mask a real structural problem

## Constraints

- Fix is scoped to `packages/core/src/parse/draft-parser.ts`'s parse path (normalize once at the top of `parseDraftMd`, before any section/frontmatter regex runs) — do not touch the DRAFT writer/serializer (`draft-mutate.ts` or equivalent), which already emits `\n` and is out of scope.
- Do not bundle `rec-20260805-003` (task `action:` field truncates multi-line content) — same parser file, different bug, tracked separately per operator decision.
- `cadence spec check`/`ui-spec-parser.ts` have the identical `^---\n(...)\n---\n` frontmatter pattern; this phase does not need to fix those (no rec covers them), but the DRAFT fix's approach (normalize-at-entry) should not preclude reusing it there later.

## Open Questions

- None — the leading empty-string-replace normalization is a single well-understood change; no design ambiguity blocking DRAFT authoring.
