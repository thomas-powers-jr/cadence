# 316-01 — Checkpoint validator and cadence handoff generator agree on the section schema, pinned by drift tests

## Objective

Checkpoint arc Phase 1.5 (`docs/handoffs/HANDOFF-checkpoint-arc-phase-2.md` §4). The private `packages/checkpoint` validator requires eight sections, but `cadence handoff`'s generator (`packages/core/src/handoff/render-session.ts`) emits six, so every real SESSION doc fails today. Verified before this phase, at the worktree base f553841d: both `SESSION-2026-09-22-pr521-merged-checkpoint-proposal-dropped.md` and `SESSION-2026-09-23.md` exit 2 with `SECTION_MISSING [Acceptance criteria touched]` + `SECTION_MISSING [Open decisions]`. The operator picked the D-BI **hybrid**: the generator starts emitting `## Open decisions`; `## Acceptance criteria touched` becomes optional (validated only when present); and drift tests make the two sides unable to diverge silently. Because every existing handoff lacks `Open decisions`, the schema is **version-gated** on the frontmatter `cadence_handoff:` field the generator already writes (`1` today, read by nothing in `src`). v1 docs validate against the frozen six-section list the generator emits today. The generator moves to `cadence_handoff: 2`. v2 docs, and docs with no frontmatter, validate against the new list. Known gap, recorded for Phase 3 rather than closed here: an agent could downgrade a v2 doc to `cadence_handoff: 1` to skip `Open decisions`. Harmless while no gate consumes the validator. Phase 3's Stop gate must close it. Tier `complex` is declared up on purpose so `deep-verify` and `code-review` actually fire: phases 311–314 all ran at standard tier, where neither gate fires, and all four graded `mixed`. This phase is verification-critical, because its whole product is two lists that must agree.

## Acceptance Criteria

### AC-1: A real v1 handoff and a freshly generated handoff both validate
Given the tracked handoff `.cadence/handoff/SESSION-2026-09-22-pr521-merged-checkpoint-proposal-dropped.md` copied verbatim into `packages/checkpoint/tests/fixtures/real-v1-session-2026-09-22.md`, and a document freshly rendered by core's `renderSession()` from a fixed input
When `validate()` runs on each, and `checkpoint validate <file>` runs on each via the CLI
Then both return `{ ok: true, diagnostics: [] }` and the CLI exits 0 (the pre-change exit-2 output for both live SESSION docs is captured in the phase report as red evidence)

### AC-2: The required-section schema is selected by the frontmatter cadence_handoff version
Given handoff documents whose frontmatter carries `cadence_handoff: 1`, `cadence_handoff: 2`, frontmatter with no `cadence_handoff` key, no frontmatter at all, an unsupported value (`cadence_handoff: 3`, or a non-numeric value), and a CRLF-line-ended `cadence_handoff: 1` document
When `validate()` runs
Then v1 (LF or CRLF) requires exactly the six sections the generator emitted before this phase, in order; v2, keyless-frontmatter, and frontmatter-less documents (the last two read as the latest version) require those six plus `Open decisions` (between `Carry-forward gotchas` and `Next action`); `Acceptance criteria touched` is optional in both versions, keeps its order slot, and keeps its AC-id checks when present; and an unsupported version returns a single named diagnostic `HANDOFF_VERSION_UNSUPPORTED` instead of being validated against a guessed schema

### AC-3: cadence handoff emits a v2 document with an Open decisions section
Given `renderSession()` in `packages/core/src/handoff/render-session.ts`
When it renders a SESSION doc
Then the frontmatter carries `cadence_handoff: 2`, and a `## Open decisions` section sits between `## Carry-forward gotchas` and `## Next action` with a `<!-- … FILL IN … -->` marker instructing the writer to list unresolved decisions or write `None`; and `findUnfilledSections()` / `cadence handoff --check` report `Open decisions` while that marker is unreplaced

### AC-4: A section drift test pins the validator's v2 schema to the generator's emitted headers
Given a checkpoint test that renders a document with core's `renderSession()` (imported by relative source path, test-only), extracts its `## ` header labels with the validator's own decoration-stripping rule, and compares them to the validator's exported v2 required-section list
When the two sides agree
Then the test passes; and when either side is desynchronized (a header removed from the renderer, or an entry removed from the validator's v2 list) the test fails naming the mismatch, with both red runs captured verbatim in the phase report before being reverted

### AC-5: An AC-id grammar drift test pins checkpoint's AC-id acceptance to core's and types'
Given one shared corpus of AC ids (at minimum `AC-1`, `AC-12`, `AC-01`, `AC-1a`, `AC-a1`, `AC-` with no digits, and `AC-1` followed by a space before the colon)
When each id is run through core's `parseDraftMd()` as a `### AC-<id>:` heading (rejected means it throws), types' `AcceptanceCriterionZ` id schema, and checkpoint's `validate()` as a `- AC-<id>:` bullet under `Acceptance criteria touched` (rejected means a named AC diagnostic, never a silent skip)
Then all three agree on accept/reject for every corpus entry; an AC-looking bullet that checkpoint previously skipped silently (e.g. `- AC-: x`, `- AC-1 : x`) is now flagged with a named diagnostic; and the test states explicitly that duplicate-id detection is out of scope (a whole-list property, and core has no duplicate-AC check to pin against)

### AC-6: Every pre-existing fixture keeps its intended diagnostic outcome, except the ones D-BI changes
Given the 27 fixtures in `packages/checkpoint/tests/fixtures/` (none carries frontmatter, so all validate as v2)
When the checkpoint suite runs
Then every fixture resolves to the same result and diagnostic codes as before this phase, except `missing-section-ac.md`, which moves from `SECTION_MISSING [Acceptance criteria touched]` to valid because that section is now optional; the test for it asserts the new outcome, and the phase report lists every changed fixture with its reason

### AC-7: cadence resume replays a v2 document carrying the new section without error
Given a v2 SESSION doc (`cadence_handoff: 2`) that contains a filled `## Open decisions` section
When `cadence resume` runs in brief mode and with `--full`
Then both replay the document without error; `--full` output includes the `Open decisions` section; and brief output is unchanged in shape (the `extractBriefSections` prefix list is not modified, so `Open decisions` is left out of the brief exactly as other non-brief sections are)

### AC-8: Docs match the new generator output
Given `docs/reference/commands.md`'s description of the `cadence handoff` narrative zone, and the phase report `docs/checkpoint/REPORT-checkpoint-phase-1.5.md`
When the doc-content test suite runs
Then a test asserts the narrative-zone description names open decisions alongside TL;DR, what landed, gotchas, and next action; and a test asserts the report exists and carries a named `##` heading for each required item — red-before evidence, section drift desync runs, AC-grammar drift desync runs, changed fixtures, provisional-schema resolution, and Phase 3 preconditions (the version-downgrade vector and the unfilled-placeholder gap)
