# 356-01 — MCP tool results keep stderr notices

## Objective

Stop the MCP server from dropping a tool's stderr notices whenever the tool also wrote to stdout (rec-20260822-002). `buildCadenceMcpServer` in `packages/core/src/mcp/server.ts` builds every tool result's text as `(io.stdout() || io.stderr()).trimEnd()`, so on a success path that prints a stdout line (settle always prints `Settled <id>`) the `||` short-circuits and the stderr notice vanishes: a zero-AC settle reaches an MCP client as `Settled 01-01` with no word of phase 288's "zero acceptance criteria" notice, which the CLI prints. A plain concatenation is not the fix, because several tools take `json: true` and print a JSON report on stdout that a client may parse. After this phase a pure `toolResultContent(stdout, stderr, exitCode)` in a new `packages/core/src/mcp/tool-content.ts` builds the result's `content` array: the first text item is exactly today's text, and a second text item carries the stderr notices when the tool also wrote to stdout. Refusal paths, which write stderr only, keep their single item.

Definitions used by AC-1 to AC-6. A text item is `{ type: 'text', text }`. The first item's text is `(stdout !== '' ? stdout : stderr).trimEnd()`, or `ok` (exit code 0) or `failed` (otherwise) when that is empty, exactly as today. The second item is present when `stdout !== ''` and `stderr.trimEnd() !== ''`, and its text is `stderr.trimEnd()`. The zero-AC fixture: a CADENCE project (`tempRepo({ initialized: true })`) whose DRAFT `01-01` in phase `01-foundation` has empty `## Acceptance Criteria` and `## Tasks` sections, written with the body `packages/core/tests/cli/settle-zero-ac.test.ts`'s `seedZeroAcDraft` writes, approved with the built CLI's `draft approve 01-foundation 01` (which needs no MCP grant), and then given a trust grant for `cadence_settle` alone, written with `writeTrustLedger` as `packages/core/tests/mcp/mcp-server.test.ts`'s `grantApprovalBypass` writes one.

## Acceptance Criteria

### AC-1: Two items when the tool wrote to both streams
Given `toolResultContent(stdout, stderr, exitCode)` from `packages/core/src/mcp/tool-content.ts`
When it is called with the two inputs named below
Then (a) `('Settled 01-01\n', 'settle: notice\n', 0)` returns `[{ type: 'text', text: 'Settled 01-01' }, { type: 'text', text: 'settle: notice' }]`; (b) `('\n', 'warn\n', 0)` returns `[{ type: 'text', text: 'ok' }, { type: 'text', text: 'warn' }]`.
Not covered: stdout of several lines, which is trimmed at the end only, as today.

### AC-2: One item otherwise
Given `toolResultContent` as in AC-1
When it is called with the four inputs named below
Then (c) `('', 'refused: reason\n', 2)` returns `[{ type: 'text', text: 'refused: reason' }]`; (d) `('{"a":1}\n', '', 0)` returns `[{ type: 'text', text: '{"a":1}' }]`; (e) `('', '', 0)` returns `[{ type: 'text', text: 'ok' }]`; (f) `('', '', 1)` returns `[{ type: 'text', text: 'failed' }]`.
Not covered: a whitespace-only stderr with empty stdout, which gives `ok` or `failed` as today; `isError` and `structuredContent`, which the server still sets from the exit code and `data`.

### AC-3: A zero-AC settle over MCP carries its notice
Given the zero-AC fixture and an in-memory MCP client connected to `buildCadenceMcpServer`
When the client calls `cadence_settle` with `{ auto: true }`
Then the result has `isError: false` and exactly two content items, the first's text is `Settled 01-01` and the second's text contains `zero acceptance criteria`.
Not covered: the second item's other lines (a no-test-command notice also lands there in this fixture); other tools' success paths with notices, which the shared builder handles the same way but this phase does not exercise one by one.

### AC-4: A JSON report keeps a parseable first item
Given a fresh CADENCE project (`tempRepo({ initialized: true })`) and an in-memory MCP client connected to `buildCadenceMcpServer`
When the client calls `cadence_status` with `{ json: true }`
Then `JSON.parse` of the first content item's text succeeds and yields an object with a `loopPosition` key equal to `IDLE`.
Not covered: this AC pins existing behaviour as a regression guard, so its test passes before T2's change; a JSON report whose tool also writes a stderr notice, where the notice arrives as the second item.

### AC-5: Docs and changeset
Given AC-1 to AC-4
When the docs test reads the repository
Then the `docs/mcp.md` slice from `## Tools` to `## Resources`, with runs of whitespace collapsed to one space, contains `second text item`; and `.changeset/mcp-stderr-notices.md` matches `/^---\r?\n"@thomas-powers-jr\/cadence-core": patch\r?\n---\r?\n/`.
Not covered: `docs/reference/commands.md`, which documents CLI behaviour; the tool count in `docs/mcp.md`, which another doc test asserts; CHANGELOG.md, which the release writes.

### AC-6: Records
Given AC-1 to AC-5
When the docs test reads `.cadence/ROADMAP.md` and `.cadence/MILESTONES.md`
Then `ROADMAP.md` contains a line starting `### Phase 356` and `MILESTONES.md` a line starting `- **Phase 356**`.
Not covered: the wording of those entries beyond their headings; the rec ledger, which `recommendation promote` updates at settle.
