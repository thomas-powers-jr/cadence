# 355-01 — build task names an upstream-failed base

## Objective

Make `build task`'s record-time boundary/redundancy check say what actually happened when the merge-base of `origin/<integrationRef>` and `HEAD` cannot be computed (rec-20261125-003). Since phase 351, `collectUnscopedTouchedFiles` reports that case as `baseSource: 'upstream-failed'` (with a `shallow` flag), but `deriveTaskTouchedFiles` passes on only `baseRefResolved`, so `packages/core/src/services/build-task.ts` cannot tell it from a missing git repository: with no working-tree changes visible it prints `git unavailable` in a repository where git works, and with changes visible it silently checks working-tree changes only. After this phase `deriveTaskTouchedFiles` also returns `baseSource` and `shallow`; a pure `touchedFilesNotice` in `packages/core/src/build/task-touched-files.ts` chooses the stderr line; and `build task` prints it. For `upstream-failed` the line names the merge-base failure and, in a shallow clone, the same `git fetch --unshallow origin` / `--deepen=<n>` fix the settle-time `boundary-scan` gate's refusal names; the `none` case keeps today's `git unavailable` line. What the check records and refuses stays as today.

Definitions used by AC-1 to AC-6. For an integration ref `R`, the base clause is `the merge-base of origin/R and HEAD could not be computed`, followed, in a shallow clone, by `, and this is a shallow clone (run git fetch --unshallow origin, or --deepen=<n>)`. The skipped line is `build task: boundary/redundancy check skipped: <base clause>; no working-tree changes are visible — falling back to the self-reported touchedFiles`. The partial line is `build task: <base clause>; the boundary/redundancy check sees working-tree changes only`. The git-unavailable line is today's text, `build task: boundary/redundancy check skipped: git unavailable (no base ref resolved and no working-tree changes visible) — falling back to the self-reported touchedFiles`. The orphan-upstream repository: a git repository with at least one commit on its current branch and `refs/remotes/origin/main` pointing at an orphan commit (`git commit-tree` of the empty tree) with no common history with `HEAD`; the branch name is not significant.

## Acceptance Criteria

### AC-1: The notice for seven named inputs
Given `touchedFilesNotice({ baseSource, shallow, deltaEmpty, integrationRef: 'main' })` from `packages/core/src/build/task-touched-files.ts`
When it is called with the seven inputs named below
Then (a) `upstream-failed`, `shallow: false`, `deltaEmpty: true` returns the skipped line for `R` = `main` without the shallow suffix; (b) `upstream-failed`, `shallow: true`, `deltaEmpty: true` returns the skipped line with the shallow suffix; (c) `upstream-failed`, `shallow: false`, `deltaEmpty: false` returns the partial line without the suffix; (d) `none`, `shallow: false`, `deltaEmpty: true` returns the git-unavailable line; (e) `none`, `shallow: false`, `deltaEmpty: false` returns `null`; (f) `upstream`, `shallow: false`, `deltaEmpty: true` returns `null`; (g) `upstream-failed`, `shallow: true`, `deltaEmpty: false` returns the partial line with the shallow suffix.
Not covered: `local`, which returns `null` as `upstream` does; the trailing newline, which `build task` adds when printing; `deltaEmpty` meaning no newly attributable change rather than no visible change (files already attributed to earlier tasks are subtracted first), which the skipped line inherits from today's line.

### AC-2: The derived result carries the base source
Given the orphan-upstream repository with a clean working tree
When `deriveTaskTouchedFiles(root, 'main', new Set())` runs
Then it returns `{ delta: [], baseRefResolved: false, baseSource: 'upstream-failed', shallow: false }`.
Not covered: a shallow clone, whose `shallow: true` is phase 351's `resolveMergeBase` result and is covered by its tests; the `delta` computation, which does not change.

### AC-3: build task names the upstream failure
Given a CADENCE project in the orphan-upstream repository, with draft `01-01` approved and no untracked or modified file outside `.cadence/` (the fixture writes no scratch file into the project root)
When `cadence build task T1 --status=DONE` runs
Then it exits 0, prints `Recorded T1: DONE`, and its stderr contains the skipped line for `R` = `main` without the shallow suffix and does not contain `git unavailable`.
Not covered: the partial line on a run with working-tree changes, which AC-1 (c) covers at the function level; a shallow clone run through the CLI.

### AC-4: build task without git keeps its notice
Given a CADENCE project in a directory with no `.git`, with draft `01-01` approved
When `cadence build task T1 --status=DONE` runs
Then it exits 0 and its stderr contains the git-unavailable line.
Not covered: phase 280's existing looser assertions on this case, which stay as they are.
