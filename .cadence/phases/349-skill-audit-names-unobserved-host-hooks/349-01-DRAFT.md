# 349-01 — Skill-audit names unobserved host hooks

## Objective

When skill invocations cannot be observed because the host hooks never fired (rec-20261117-001's real cause: a cloud session started in `/home/user`, the parent of the repo, so Claude Code never loaded the repo's committed `.claude/settings.json`; live evidence 2026-11-22: `skillAudit.invoked: []` and `session.tokenUtilization: 0` after several prompts, while the same shim fed a `Skill` payload by hand recorded `phase-build` correctly), CADENCE says so out loud at three points — when a task is recorded, in `cadence doctor`, and in the settle skill-audit refusal or bypass reason — instead of producing a plain "required skill(s) not invoked" miss that reads as if the agent skipped the skill; the skill-audit requirement itself, its refuse outcome, and `--allow-skill-audit-miss` are unchanged.

## Acceptance Criteria

### AC-1: Hook events stamp a liveness time
Given a repository with a `.cadence/state.json`
When the hook dispatcher handles a `user-prompt`, `post-tool-edit` or `skill-invoke` event
Then `state.session.lastHookEventAt` is set to the current time as an ISO-8601 string through a revision-exempt backend write (the state `revision` is unchanged, the same discipline as `bumpSessionCounter`), whatever the `config.telemetry` settings are; the write is skipped when the existing stamp is less than 60 seconds old; a write failure never fails the hook; and a `state.json` with no `lastHookEventAt` key (every pre-349 state) still parses, because the field is `.optional()` with no `.default(...)`.

### AC-2: Recording a task without live hooks is flagged on the row and on stderr
Given the loop is in BUILD, and a pure `isHookLive(lastHookEventAt, now)` in `packages/core/src/hooks/liveness.ts` returns true only when the stamp is present, parses as a date, and is at most `HOOK_LIVENESS_WINDOW_MS` (a constant of 30 minutes, not config) before `now`
When `cadence build task <id> --status=<status>` writes that task's PROGRESS.json row
Then the row carries `hooksObserved: true` when `isHookLive` is true and `hooksObserved: false` otherwise; when false, exactly one line is written to stderr: `build task: no host hook event in the last 30 minutes, so skill invocations in this session are not being recorded. Check that the session started in the repository root, where .claude/settings.json is loaded.`; stdout is byte-identical to today's for the same input; and rows written before this phase (no `hooksObserved` key) still read back.

### AC-3: Settle names the tasks recorded without live hooks
Given settle finds one or more required skills missing from `state.skillAudit.invoked`
When at least one PROGRESS.json task row of the settling draft has `hooksObserved: false`
Then the text `; host hooks were not observed when task(s) <ids> were recorded, so skill invocations in that session could not be recorded` is inserted directly after the missing-skill list in both the refusal line on stderr (before its `. Invoke them, or pass --allow-skill-audit-miss to override.` tail) and, on the `--allow-skill-audit-miss` path, the bypass reason recorded in `SUMMARY.gateBypasses` (at its end), where `<ids>` are those task ids in draft order joined by `, `; the outcome is unchanged (refuse without the flag, pass with the bypass recorded with it); and when no row has `hooksObserved: false` (all true, or the key absent on pre-349 rows), both the refusal line and the bypass reason are byte-identical to today's.

### AC-4: Doctor reports host-hook liveness during BUILD
Given `cadence doctor` runs
When the loop is in BUILD
Then a check named `host-hooks-liveness` (complementing the existing `host-hooks` check, which proves the hooks are installed, not that they fire) reports severity `warning` when `isHookLive(state.session.lastHookEventAt, now)` is false, with a message that names the last stamp (or says none was recorded) and says to start the session in the repository root so `.claude/settings.json` loads, and severity `ok` when it is true; when the loop is not in BUILD the check reports `ok` with a "not in BUILD" message; the check never reports severity `error`, and an unreadable state degrades to `ok` with a "not determinable" message rather than throwing.

### AC-5: Docs, changeset and doc test record the behavior
Given the behavior in AC-1 to AC-4
When the phase settles
Then `DESIGN.md` §11 describes the `lastHookEventAt` stamp, the 30-minute window and the three places the condition is reported; `docs/concepts.md`'s required-skill note says a miss names the tasks recorded without live hooks; `docs/reference/commands.md` documents the `build task` notice and the `host-hooks-liveness` doctor check; a `.changeset/*.md` bumps `@thomas-powers-jr/cadence-core` and `@thomas-powers-jr/cadence-types` by minor; and a doc-content test under `packages/core/tests/docs/` asserts that each of those three docs mentions `lastHookEventAt` or `host-hooks-liveness`, as appropriate.

## Boundaries

- Do NOT change the skill-audit outcome: a shortfall still refuses without `--allow-skill-audit-miss`, and the bypass is still recorded. The new text only explains; it never turns a miss into a pass.
- Do NOT add a `cadence skill record` command, an MCP recording tool, or any other path for an agent to record its own skill invocations (option 2 of the rec, not chosen).
- Do NOT change `.claude/settings.json`, the host installer, or the host shim; the cause is the session's start folder, not the hook wiring.
- Do NOT change `SummaryZ` or the SUMMARY hash inputs; the explanation travels in the existing free-text bypass reason.
- Do NOT add a config knob for the 30-minute window or the 60-second throttle (constants; YAGNI).
- Do NOT add a runtime dependency.
- Do NOT stamp `lastHookEventAt` through `backend.commit` (it would advance `revision` mid-settle; see phase 305 / issue #500).
