# 332-01 — Code-review and security-audit findings bypasses reach gateBypasses

## Objective

When `cadence settle run` goes past a failing code-review (HIGH findings) or security-audit (CRITICAL findings), the SUMMARY records the gate as `status: 'ran'` with no `gateBypasses` entry, so phase 283's D-S cap never applies and the phase can be graded `strong` (331-01 is the known case; `rec-20261016-002`). This phase records every such findings bypass as one `error`-severity `gateBypasses` entry per gate, whether `--allow-code-review-failure`, `--allow-security-audit-failure` or bare `--force` waved it through. It does this by a direct `GateBypass` push driven by a new gate-result flag that carries what the gate itself printed (D-CA, `dec-20261016-004`), the same shape `pack-resolution`, `skill-audit` and the evidence floor already use, because gate-emitted anomalies never reach `anomalyToGateBypass` (`settle.ts`'s `emit.anomalies` is a no-op). The recorded `flag` names what the gate's own stderr line printed (D-CB, `dec-20261016-005`), security-audit is fixed alongside (D-CC, `dec-20261016-006`), and `deriveAssuranceRecord` is not changed: the existing D-S cap does the grading.

## Acceptance Criteria

### AC-1: --allow-code-review-failure on a failing code-review records a gateBypasses entry
Given a settle whose code-review verifier (a non-mock provider stub) returns a HIGH finding
When `settleService` runs with `allowCodeReviewFailure: true`
Then the settle exits 0 and `SUMMARY.json.gateBypasses` contains exactly one entry with `gate: 'code-review'`, `flag: '--allow-code-review-failure'` and `severity: 'error'`, whose `reason` names the bypassed finding count and the highest bypassed severity, and the test fails against the pre-change code because the entry is absent

### AC-2: the recorded bypass alone caps an otherwise-strong grade
Given the AC-1 scenario configured with a real-provider code-review verifier and an `ai-verified` AC
When the settle finalizes
Then `assurance.overall` is `mixed`, the SUMMARY carries no error-severity `gateBypasses` entry other than the `code-review` one, re-deriving the same SUMMARY with `deriveAssuranceRecord` after removing that one entry gives `strong`, `packages/core/src/gates/assurance-record.ts` is unchanged by this phase's diff, and `packages/core/tests/gates/assurance-record.test.ts` (including the phase-233 gate-agnostic tripwire for `dec-20260728-001` and `deriveAssuranceRecord bypass cap is gate-agnostic (phase 283-01, T2, AC-4)`) passes unmodified

### AC-3: a --force findings bypass is recorded under the flag the gate printed
Given a settle whose code-review verifier returns a HIGH finding and no structural, deep or interactive failure exists
When `settleService` runs with `force: true` alone, and separately with both `force: true` and `allowCodeReviewFailure: true`
Then each SUMMARY carries exactly one `code-review` gateBypasses entry whose `flag` is `--force`, matching the gate's stderr line `code-review: --force set; proceeding past ...`, neither SUMMARY carries a `force-used` (`gate: 'settle'`) entry, and the `force: true`-alone case fails against the pre-change code because nothing is recorded

### AC-4: a clean review records nothing new
Given a settle whose code-review verifier returns no HIGH finding, run once with no bypass flag and once with `force: true` set for no reason
When the settle finalizes under an injected fixed clock
Then neither SUMMARY has a `gateBypasses` key, and the no-flag SUMMARY.json equals a golden fixture captured from the pre-change code under the same clock, with `contentHash`, temp-root paths and `stateAtSettle` normalized by name in the test

### AC-5: the bypass is recorded even where anomaly-notify is not in the gate set
Given a strict profile × standard tier settle, whose active gate set includes `code-review` and does not include `anomaly-notify`
When a HIGH finding is bypassed with `allowCodeReviewFailure: true`
Then the test asserts `anomaly-notify` is absent from the active gate set and the `code-review` gateBypasses entry is present

### AC-6: security-audit findings bypasses are recorded the same way
Given a strict profile × complex tier settle whose security-audit verifier returns a CRITICAL finding and whose code-review is clean
When `settleService` runs with `allowSecurityAuditFailure: true`, and separately with `force: true` alone
Then each SUMMARY carries exactly one `security-audit` gateBypasses entry with `severity: 'error'` and `flag` `--allow-security-audit-failure` and `--force` respectively, and the `allowSecurityAuditFailure` case fails against the pre-change code

### AC-7: the rendered SUMMARY shows a code-review bypass beside the grade with no render change
Given a synthetic SUMMARY whose only `gateBypasses` entry is an error-severity `code-review` entry with flag `--allow-code-review-failure`
When it is rendered to Markdown through the existing summary writer
Then the output lists the `code-review` bypass with its flag and the assurance section shows `bypassed: 1 gate(s) (severity: error)`, and `packages/core/src/parse/summary-writer.ts` is unchanged by this phase's diff

### AC-8: docs state that findings bypasses are recorded and cap the grade
Given `docs/concepts.md`'s gate table and `docs/reference/commands.md`'s `settle run` flag rows for `--allow-code-review-failure` and `--allow-security-audit-failure`, plus their hand-kept mirrors, the `settle run --help` option descriptions and `docs/cli.md`'s bypass table
When a doc-content test reads them
Then all four state that a findings bypass is recorded in `gateBypasses` at `error` severity and caps `assurance.overall`, and the existing doc-content suites pass

*As built (2026-10-16): the `--help` descriptions and `docs/cli.md` were added to this AC and to T5 after the T4–T6 review found them out of step with `commands.md`. Phase 311 had edited all three together. Operator re-approved.*

### AC-9: a pre-fix SUMMARY re-derives unchanged; the same record with the entry caps
Given a SUMMARY shaped like 331-01's (a real-provider `code-review` gate recorded `status: 'ran'`, an `ai-verified` AC, and no `gateBypasses` key)
When `deriveAssuranceRecord` re-derives it as `assurance report` does, and again after adding the `code-review` entry this phase records
Then the first derivation is `strong` (the corpus report cannot see a pre-fix findings bypass, D-CD, `dec-20261016-007`) and the second is `mixed`
