# 307-01 — settle review diff covers the phase's committed range

## Objective

Fix GitHub issue #501: settle's shared `ctx.diff()` is `git diff --no-color HEAD -- <declared files>`, i.e. uncommitted working-tree changes only, so any phase whose tasks were committed as they landed hands the `deep-verify` verifier a diff with none of its implementation in it, and every AC is rejected; `code-review` and `security-audit` read the same `ctx.diff()` and have the same blind spot. This phase changes the diff basis, not its scope: `ctx.diff()` becomes `git diff --no-color <merge-base> -- <declared files>`, where the merge-base is resolved against `origin/<phaseGuard.integrationRef>` and then the local `<integrationRef>` — the same resolution order the settle-time `boundary-scan` gate already uses — so the diff covers the phase's committed-since-divergence changes plus uncommitted working-tree changes to tracked files. When no base resolves inside a git work tree, settle falls back to today's `HEAD` diff and prints a loud stderr notice naming the integration ref, rather than silently reproducing the bug; outside a git work tree the diff stays empty as before, with no notice. Two further silent-empty paths also get a notice, printed only when a gate actually reads `ctx.diff()`: a resolved merge-base that still yields an empty diff (the phase's commits are already on the integration ref, e.g. work committed on `main` and pushed), and a git failure while diffing (for example the 16MB `maxBuffer` overflowing, newly reachable because a multi-commit range diff is larger than a working-tree diff). `code-review` and `security-audit` read `ctx.diff()` uncapped (only `deep-verify` applies `verifier.diffCapBytes`), so the broader basis also grows what those two gates send a real provider; that is expected and not capped here. Scope stays the union of the DRAFT's declared `files:` (an incomplete `files:` list still yields a partial diff; that is not this bug). The build-time per-task `diff(files)` in `gates/build-context.ts` stays on `HEAD`, because it runs before a task's work is committed. Per the issue's second ask, a `deep-verify` refusal additionally prints the diff byte count and declared file count the verifier was given, so a diff-basis problem is visible instead of looking like genuine AC failures; the refusal `reason` string itself is unchanged, because it is persisted in SUMMARY and pinned by an existing snapshot.

## Acceptance Criteria

### AC-1: the phase diff includes committed-since-divergence and uncommitted changes to the declared files
Given a git repo whose `main` branch has a base commit, and a feature branch with one commit changing declared file A, an uncommitted change to already-tracked declared file B, and a committed change to an undeclared file C
When the phase diff is collected for declared files A and B against integration ref `main`
Then the diff contains A's committed change and B's uncommitted change, does not contain C, and reports that a merge-base basis was used

### AC-2: an unresolvable base falls back to the HEAD diff and says so
Given a git repo with no `origin/<ref>` and no local `<ref>` for the configured integration ref
When the phase diff is collected
Then it returns exactly the `git diff --no-color HEAD -- <files>` content and reports that no merge-base resolved, and when settle builds `ctx.diff()` in that situation it writes one stderr notice naming the integration ref and the HEAD fallback; while a directory that is not a git work tree yields an empty diff and no notice

### AC-3: settle's review gates receive the committed phase work, and an empty or failed diff is never silent
Given settle's diff provider over a git repo on a feature branch whose declared task file changes are all committed and whose working tree is clean
When a gate reads the diff
Then the diff contains the committed change to the declared file and no notice is written; while when the merge-base resolves but the diff is empty, or git fails while diffing, exactly one stderr notice is written on first read (memoized: repeat reads write nothing more), and when no gate reads the diff no notice is written at all

### AC-4: a deep-verify refusal reports the diff the verifier was given
Given the `deep-verify` gate refuses because the verifier rejected at least one AC
When it writes its refusal to stderr
Then stderr also contains a line stating the diff byte count and the number of declared files the verifier was given, and the returned refusal `reason` string is unchanged

### AC-5: the docs describe the new diff basis
Given an operator reading the `deep-verify` row in `docs/concepts.md` and `verifier.diffCapBytes` in `docs/reference/config.md`
When they look for what diff the verifier receives
Then neither says `git diff HEAD`, and both describe the merge-base-against-integration-ref basis including committed phase work
