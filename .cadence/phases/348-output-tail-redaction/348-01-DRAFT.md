# 348-01 — Output-tail redaction: close four known shapes and let consumers hide the tail

## Objective

Phase 346 shows a failing test suite's output tail on stderr after best-effort redaction, and four known secret shapes get through it (rec-20261116-001, rec-20261117-002): a credential flag or `-u user:pw` at the very start of the captured text; a credential-named environment value that starts with `/`; a quoted auth header such as `"Authorization":"Bearer x"`; and a run of short words from a multi-word passphrase. This phase redacts those four named shapes, and adds `verification.buildTestOutputTail: "show" | "hide"` (default `"show"`) so a consumer that captures settle's stderr can hide the tail entirely (dec-20261121-001, option 2). The claim is narrow on purpose: these named shapes are redacted, redaction is documented as best-effort, and the tail can be hidden. It is not a claim that secrets cannot leak; any shape not named in an AC below is out of scope.

## Acceptance Criteria

### AC-1: a credential flag or -u at the start of the text is redacted
Given captured output whose very first characters are `--auth-token s3cretvalue99`, `--db-pass=hunter2pw` or `-u alice:hunter2pw`
When `redactOutput` runs on it
Then the output is `--auth-token [REDACTED]`, `--db-pass=[REDACTED]` and `-u [REDACTED]` respectively (the flag name is kept); the same three inputs placed after a newline or after one space are also redacted. Not covered: two or more spaces between `-u` and its value.

### AC-2: a /-prefixed credential value containing + or = is a literal secret
Given the environments `API_TOKEN=/AbCdEf123456+/xyz==` and `API_TOKEN=/AbCdEf123456/xyz==` (8 or more characters, starting with `/`, containing `+` or `=`)
When `secretValues(undefined, env)` builds the literal list and `redactOutput(text, literals)` runs on text containing the value
Then for each, the value is in the list and is replaced by `[REDACTED]` in the output; `SSH_AUTH_SOCK=/tmp/ssh-abc/agent.123`, `GIT_ASKPASS=/usr/bin/askpass`, `API_TOKEN=~/abc+def==xyz`, `API_TOKEN=./abc+def==xyz` and `API_TOKEN=C:\abc+def==` are still not literals. Not covered: a `/`-prefixed value with neither `+` nor `=`, and a value under 8 characters.

### AC-3: a quoted auth header value is redacted
Given output containing `"Authorization":"Bearer abcdef1234567890"`, `"Proxy-Authorization": "Basic dXNlcjpwYXNzd29yZA=="`, `'authorization': 'Bearer abcdef1234567890'`, `"Cookie":"sid=abcdef1234567890"`, `"SET-COOKIE" : "sid=abc; Path=/"` or `"Authorization":"Bearer a\"b-suffix"`
When `redactOutput` runs on it
Then each quoted value, an escaped quote inside it included, is replaced by `"[REDACTED]"` (double quotes, also for a single-quoted value) and the key is kept as written. A key counts only when its quoted text is one of `Authorization`, `Proxy-Authorization`, `Cookie`, `Set-Cookie`, in any letter case, with optional whitespace around the colon. Not covered, and left unchanged: other names (`"x-authorization":"Bearer abcdef1234567890"`, `"cookies":"sid=abcdef1234567890"`), an unquoted key, and an unquoted value.

### AC-4: two or more consecutive words of a passphrase are redacted
Given the literal `blue cat sat mat` from the credential-named variable `DB_PASSWORD`
When `redactOutput(text, literals)` runs on text containing `blue cat`, `cat sat mat`, the whole phrase, or `DB_PASSWORD=blue cat sat mat`
Then each substring of the literal that starts and ends on its word boundaries, spans two or more words, keeps the literal's own whitespace and is at least 8 characters long (`blue cat`, `cat sat mat`, the whole phrase) is replaced by `[REDACTED]`, longest first, and the output for `DB_PASSWORD=blue cat sat mat` contains none of `cat`, `sat`, `mat`. Runs are built only for a literal of at most 12 words. Not covered: a run under 8 characters (`cat sat` alone), one word under 8 characters on its own, the same words separated by different whitespace (`blue  cat`, a newline between them), and a literal of more than 12 words.

### AC-5: the named unrelated inputs are left unchanged
Given these inputs: text `vitest run --passWithNoTests foo`; text `--passWithNoTests foo` at the very start; env `GIT_AUTHOR_NAME=Ada Lovelace` with text `Ada Lovelace wrote this`; env `DISABLE_AUTH=true` with text `true`; text `{"author":"Ada"}`; and env `DB_PASSWORD=blue dog ran far` with text `the cat sat`
When `secretValues(undefined, env)` and then `redactOutput(text, literals)` run
Then each output is byte-identical to its input text, and `packages/core/tests/verify/test-runner.test.ts` is not edited and passes

### AC-6: with the tail hidden, stderr carries the hidden notice and none of the tail
Given `verification.buildTestOutputTail: "hide"` and a failing suite whose captured tail is the 3 lines `tail-348-a`, `tail-348-b`, `tail-348-c`
When `build-test-must-pass` refuses (unsealed, and sealed), and when it is bypassed with `--allow-failing-build`, and with `--force`
Then in each of the four cases stderr has the line `  output tail: (hidden by config; 3 lines captured)` in place of the whole tail block (its header line included) and contains none of `tail-348-a`, `tail-348-b`, `tail-348-c`; on the two bypasses `flags.buildTestBypass` has no `outputTail`, and the `build-test-must-pass` `gateBypasses` entry's `detail` reads `output tail: 3 lines captured, hidden by config (verification.buildTestOutputTail); not recorded, since test output can hold secrets`. The count is `tailLines` of the redacted tail, the number of lines `"show"` would print (at most 40), written `1 line captured` when it is 1. A suite that printed nothing keeps today's text under `"hide"`: stderr `  output tail: (no output captured)` and detail `output tail: 0 lines shown on stderr at settle; not recorded, since test output can hold secrets`.

### AC-7: without the setting, the gate's stderr, flags and detail match the phase-346 pins
Given a config with no `verification.buildTestOutputTail` key, a config with `"show"`, a null config, and a config with no `verification` object
When the config is parsed, and `build-test-must-pass` refuses or is bypassed on a failing suite
Then the key is optional: it is absent from the parsed `{}` config, from `defaultConfig` and from a fresh `cadence init`'s `config.json`, and absent behaves as `"show"`; `{}` and `{ "verification": { "testGlobs": ["x"] } }` parse; `"Hide"`, `true` and `null` for the key are schema errors; under show `flags.buildTestBypass` carries no key beyond `flag`, `command`, `exitCode` and `outputTail`; and `packages/core/tests/gates/build-test-must-pass.test.ts` and `packages/core/tests/services/settle-build-test-bypass.test.ts` are not edited and pass

### AC-8: docs say redaction is best-effort and name the setting
Given `docs/reference/config.md`, the `--allow-failing-build` rows in `docs/reference/commands.md` and `docs/cli.md`, the phase-346 bypass note in `docs/concepts.md`, the `--allow-failing-build` help text of `settle run`, and the changeset
When phase 348 ships
Then `config.md` documents `verification.buildTestOutputTail` with its two values and that absent means `"show"`; each of `config.md`, the `commands.md` row, the `cli.md` row and the `concepts.md` note contains `best-effort` and `` `verification.buildTestOutputTail` `` and says the tail is shown unless the setting is `"hide"`; the help text names `verification.buildTestOutputTail`; a minor changeset for cadence-core and cadence-types says the same; and a doc-content test asserts these

## Boundaries

- Do NOT claim or try to make redaction complete. Only the shapes named in AC-1 to AC-4 are in scope; a new shape found during BUILD or at settle is reported to the operator, not fixed here (dec-20261121-001).
- Do NOT change what is recorded: the output tail still never enters SUMMARY.json, SUMMARY.md, an anomaly event or any notifier transport.
- Do NOT change the build-test-must-pass refusal reason, the bypass notice's first line, exit codes, or the gate's pass/refuse decision.
- Do NOT change `displayCommand`, the tail's size limits (40 lines, 8 KiB), ANSI stripping, or the shared `redactSecrets` patterns.
- Do NOT widen any existing pattern beyond what AC-1 to AC-4 name; the AC-5 inputs must stay byte-identical.
- Do NOT make `"hide"` the default, and do NOT add a CLI flag, an environment variable or an MCP parameter for it.
- Do NOT add a runtime dependency.
- Do NOT edit any existing test file; new tests go in the new files the tasks name.
