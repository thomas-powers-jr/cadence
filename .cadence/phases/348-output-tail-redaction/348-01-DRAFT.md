# 348-01 — Output-tail redaction: close four known shapes and let consumers hide the tail

## Objective

Phase 346 shows a failing test suite's output tail on stderr after best-effort redaction, and four known secret shapes get through it (rec-20261116-001, rec-20261117-002): a credential flag or `-u user:pw` at the very start of the captured text; a credential-named environment value that starts with `/`; a quoted auth header such as `"Authorization":"Bearer x"`; and a run of short words from a multi-word passphrase. This phase redacts those four named shapes, and adds `verification.buildTestOutputTail: "show" | "hide"` (default `"show"`) so a consumer that captures settle's stderr can hide the tail entirely (dec-20261121-001, option 2). The claim is narrow on purpose: these named shapes are redacted, redaction is documented as best-effort, and the tail can be hidden. It is not a claim that secrets cannot leak; any shape not named in an AC below is out of scope.

## Acceptance Criteria

### AC-1: a credential flag or -u at the start of the text is redacted
Given captured output whose very first characters are `--auth-token s3cretvalue99`, `--auth-token=s3cretvalue99` or `-u alice:hunter2pw`
When `redactOutput` runs on it
Then the value is replaced by `[REDACTED]` and the flag name is kept (`--auth-token [REDACTED]`, `--auth-token=[REDACTED]`, `-u [REDACTED]`); the same three inputs after a newline or a space stay redacted as they are today

### AC-2: a /-prefixed credential value containing + or = is a literal secret
Given an environment with `API_TOKEN=/AbCdEf123456+/xyz==` (a credential-named variable whose value starts with `/` and contains `+` or `=`)
When `secretValues` builds the literal list and `redactOutput` runs on output containing that value
Then the value is in the list and is replaced by `[REDACTED]` in the output; `SSH_AUTH_SOCK=/tmp/ssh-abc/agent.123` and `GIT_ASKPASS=/usr/bin/askpass` are still not literals. Not covered: a `/`-prefixed value with neither `+` nor `=`, which is still treated as a path

### AC-3: a quoted auth header value is redacted
Given output containing `"Authorization":"Bearer abcdef1234567890"`, `"Proxy-Authorization": "Basic dXNlcjpwYXNzd29yZA=="`, `'authorization': 'Bearer abcdef1234567890'` or `"Cookie":"sid=abcdef1234567890"`
When `redactOutput` runs on it
Then each value is replaced by `"[REDACTED]"` and the key is kept. The keys covered are exactly `Authorization`, `Proxy-Authorization`, `Cookie` and `Set-Cookie`, quoted with single or double quotes, in any letter case. Not covered: any other header name, and an unquoted key

### AC-4: two or more consecutive words of a passphrase are redacted
Given the literal `blue cat sat mat` from a credential-named variable (`DB_PASSWORD`)
When `redactOutput` runs on output containing `blue cat`, `cat sat mat` or the whole phrase
Then each such run of two or more consecutive words of the literal is replaced by `[REDACTED]`. Not covered: one word of the literal on its own when it is under 8 characters (`cat` alone stays), so ordinary text is not erased

### AC-5: the fixes erase nothing they did not erase before
Given the inputs `vitest run --passWithNoTests foo`, `GIT_AUTHOR_NAME=Ada Lovelace` in the environment with output `Ada Lovelace wrote this`, `DISABLE_AUTH=true` in the environment with output `true`, `{"author":"Ada"}`, and `the cat sat` with no passphrase literal
When `secretValues` and `redactOutput` run as in AC-1 to AC-4
Then each output is byte-identical to its input, and every test in `packages/core/tests/verify/test-runner.test.ts` that existed before this phase passes unchanged

### AC-6: with the tail hidden, stderr carries no line of suite output
Given `verification.buildTestOutputTail: "hide"` and a failing suite that printed 3 lines
When `build-test-must-pass` refuses, and again when it is bypassed with `--allow-failing-build`
Then in both cases stderr has the line `  output tail: (hidden by config; 3 lines captured)` in place of the tail block and contains none of the suite's 3 lines; a silent suite still prints `  output tail: (no output captured)`; on the bypass, the `build-test-must-pass` `gateBypasses` entry's `detail` reads `output tail: 3 lines captured, hidden by config (verification.buildTestOutputTail); not recorded, since test output can hold secrets`

### AC-7: without the setting, behaviour is unchanged
Given a config with no `verification.buildTestOutputTail` key, or with `"show"`
When the config is parsed, and `build-test-must-pass` refuses or is bypassed on a failing suite whose output has none of the shapes in AC-1 to AC-4
Then the parsed value is `"show"`, a config written before this phase still parses, any value other than `"show"` or `"hide"` is a schema error, and the gate's stderr and the `gateBypasses` `detail` are byte-identical to what they are today

### AC-8: docs say redaction is best-effort and name the setting
Given `docs/reference/config.md`, the `--allow-failing-build` rows in `docs/reference/commands.md` and `docs/cli.md`, and the changeset
When phase 348 ships
Then `config.md` documents `verification.buildTestOutputTail` with its two values and default; all three docs say the redaction of the output tail is best-effort and name the setting as the way to hide the tail; a minor changeset for cadence-core and cadence-types says the same; and a doc-content test asserts these

## Boundaries

- Do NOT claim or try to make redaction complete. Only the shapes named in AC-1 to AC-4 are in scope; a new shape found during BUILD or at settle is reported to the operator, not fixed here (dec-20261121-001).
- Do NOT change what is recorded: the output tail still never enters SUMMARY.json, SUMMARY.md, an anomaly event or any notifier transport.
- Do NOT change the build-test-must-pass refusal reason, the bypass notice's first line, exit codes, or the gate's pass/refuse decision.
- Do NOT change `displayCommand`, the tail's size limits (40 lines, 8 KiB), ANSI stripping, or the shared `redactSecrets` patterns.
- Do NOT widen any existing pattern beyond what AC-1 to AC-4 name; the AC-5 inputs must stay byte-identical.
- Do NOT make `"hide"` the default, and do NOT add a CLI flag, an environment variable or an MCP parameter for it.
- Do NOT add a runtime dependency.
- Do NOT edit any existing test file; new tests go in the new files the tasks name.
