# 331-02 — Statusline sensor: a 1000 ms hold ceiling, one fewer Node start, and streamed inner stdout

## Objective

Fix the two CI defects 331-01 left on PR #571 and code-review finding 7, from measurements rather than guesses. The 250 ms recording deadline rested on a misreading: Claude Code renders a statusline only when the process exits, 300 ms is a debounce between runs, and a new trigger cancels the run in flight (https://code.claude.com/docs/en/statusline). Probe PR #573 (runs 39448948337, 39450266774, 39452805430) measured that when the machine is not busy the reading is written 17-60 ms before the inner exits on every leg, that under suite load the measured worst was +84.6 ms past the inner's exit (Windows, run 39450266774; walk p99 366 ms, one atomic write 218 ms) with 1 of 30 real-wrapper readings lost at 250 ms, and that the slower-runner tail behind #571's 11/30 misses was never captured, so its size is unknown. This slice raises the deadline to a 1000 ms statusline-hold ceiling chosen by the operator (a cap on how long a slow write may hold the statusline, not a measured tail), corrects the deadline's stated rationale, removes one Node start per invocation by having bin/checkpoint.cjs load dist/cli.js in-process instead of spawning it (the wrapper costs about 100 ms over the bare inner when idle and 2-4 s under Windows suite load, mostly process starts), writes the inner's stdout to the wrapper's stdout as each chunk arrives instead of accumulating it until exit (finding 7; the user-visible render time is unchanged because rendering waits for exit, so the gain is no whole-output accumulation in the wrapper), and brings the AC-5 concurrency test inside the shared 20 s macOS budget, whose root cause is 15 sequential wrapper invocations per writer at about 1.3 s each under suite load.
