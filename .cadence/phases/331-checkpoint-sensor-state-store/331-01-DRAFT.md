# 331-01 — Checkpoint statusline sensor records context usage to a project-keyed store; a transition table rejects every illegal move

## Objective

Checkpoint Arc A Phase 2 (`docs/handoffs/HANDOFF-checkpoint-phase-2.md` §4): build the sensor and the state store, and nothing that can block, inject, or gate. A statusline wrapper (`checkpoint statusline [--] <inner argv>`) reads Claude Code's statusline JSON from stdin, records a reading to `<project>/.cadence/checkpoint/reading.json` atomically, and passes the inner statusline's stdout through byte-for-byte. A separate machine-state file (`.cadence/checkpoint/state.json`) is written only through a transition function whose table (`idle→armed`, `armed→written`, `written→settled`, `written→armed`, `settled→reset`, `reset→resumed`, `resumed→idle`) accepts the 7 legal edges and rejects the other 29 ordered pairs of the 6 states; nothing calls it yet. Operator decisions already filed: D-BJ `dec-20261013-001` (record both units; threshold unit is percentage), D-BR `dec-20261013-002` (checkpoint depends on cadence-core for `atomicWriteText`), D-BS `dec-20261013-003` (state lives under `.cadence/checkpoint/`, project-keyed). Measured facts that move from the handoff §2: core is `1.70.0`, not `1.68.0`; core is already a checkpoint *devDependency* (phase 316) and core's public entry does not export `atomicWriteText`, so D-BR requires one additive core re-export (phase 295/308 comment style) plus moving core to checkpoint's runtime `dependencies`. Payload shape is pinned to Claude Code's documented statusline schema (fields under `context_window.*`, `exceeds_200k_tokens` top-level). Project resolution, by operator choice on 2026-10-15 interpreting D-BS: start at `workspace.current_dir` (falling back to `cwd`) and walk up to the nearest ancestor containing `.cadence/` — not `workspace.project_dir`, which the docs define as the launch directory and which in a worktree session names the primary checkout rather than the worktree whose private `.cadence/` holds the active loop; the reading records both `current_dir` and `project_dir` so Phase 3 can detect a mismatch. The inner statusline is spawned from argv with no shell (one leading `--` is dropped if present, because PowerShell 5.1 may strip a bare `--` before native executables); on Windows that means `.cmd`/`.bat` shims such as `npx` cannot be wrapped (measured: a no-shell `spawn('npx')` fails `ENOENT` on the dev box), a limitation the report records; Claude Code runs the statusline command through Git Bash on Windows when installed, otherwise PowerShell — the same fallback 0.4a measured for hooks — so transparency is proven through both `bash -c` and `powershell.exe -NoProfile -Command`. The unknown-reading predicate is unconditional: `used_percentage` of `null`, absent, or `0` is unknown, and the state file records the raw fields only — no computed fallback percentage is written. D-BJ's sentence "otherwise computes the percentage from current_usage / context_window_size" is deferred to Phase 3's threshold evaluation by operator confirmation on 2026-10-15; the report records two Phase 3 preconditions for it: the docs make `current_usage` null after `/compact`, so the fallback is unavailable exactly when the percentage is unknown, and any fallback must use the docs' input-only formula (`input_tokens + cache_creation_input_tokens + cache_read_input_tokens`). Readings and machine state are separate files so the sensor never read-modify-writes machine state; rename-atomicity prevents torn files but does not give `settled→reset` single-winner semantics, which stays a Phase 3 precondition. Tier `complex` so `deep-verify` and `code-review` fire, per the handoff's standing rule.

## Acceptance Criteria

### AC-1: The wrapper's stdout is byte-identical to the inner statusline's on both the bash path and the PowerShell path
Given an inner statusline fixture whose stdout contains UTF-8 non-ASCII text, ANSI SGR escape sequences, LF-only line endings, and no trailing newline, and a statusline payload with `context_window.used_percentage: 42` and a populated `context_window.current_usage`
When the inner command runs through a shell S, and separately `checkpoint statusline -- <inner argv>` runs through the same shell S with the same stdin, for S = `bash -c` (on win32 a resolved Git Bash, asserted by `uname -s` reporting MINGW/MSYS, never the WSL launcher) and S = `powershell.exe -NoProfile -Command` (on win32; the test spawns PowerShell itself, so the path is forced regardless of what Claude Code would detect)
Then the two stdout buffers are byte-equal in each shell; the state file carries `{ used_percentage: 42, absolute: { … }, ts: <ISO-8601> }`; the PowerShell case's only run condition is `process.platform === 'win32'` (no `skip`, no `continue-on-error`) and the local win32 verbose run reports it as run, not skipped; the argv the wrapper receives through `powershell.exe -Command` (with and without the `--` separator) is recorded; and the raw-node versus through-PowerShell inner bytes are recorded as a measured result in the phase report whatever they show (the `windows-latest` CI log evidence is a report item filled after the PR's CI run, not a settle-time condition)

### AC-2: A null used_percentage is recorded as null with any absolutes present, and fires no transition
Given a statusline payload whose `context_window.used_percentage` is `null` and whose `total_input_tokens`, `context_window_size`, and `current_usage` are present (and a second payload where `current_usage` is also `null`, as after `/compact`)
When the wrapper runs
Then `reading.json` records `used_percentage: null`, `unknown: true`, and every absolute field present in the payload (absent or null ones recorded as `null`), no percentage is computed into the file, and `state.json` is neither created nor modified

### AC-3: Null and zero used_percentage are the same unknown predicate, and idle to armed refuses an unknown reading
Given readings with `used_percentage` of `null`, absent, and `0` — including `0` arriving while machine state is `settled` or `reset` (the post-`/compact` reading 0.4a observed) and while it is `idle`
When the exported unknown-reading predicate classifies them, and `transition('idle', 'armed', { reading })` is attempted with each
Then all three classify as unknown through one predicate, a positive integer such as `7` classifies as known, and the `idle → armed` transition is rejected with a reason naming the unknown reading — as it is when no reading context is passed at all — while the same transition with a known reading is accepted

### AC-4: Every legal edge is accepted and every one of the 29 non-edges is rejected with a reason
Given the 6 states `idle`, `armed`, `written`, `settled`, `reset`, `resumed`, and the 36 ordered pairs between them (self-pairs included)
When the transition function is called for each pair, enumerated explicitly in the test file rather than sampled, with a known reading passed as context for every call (so `idle → armed` is tested as a legal edge, and AC-3 separately covers its unknown-reading refusal)
Then the 7 legal edges succeed, the 29 other pairs (including the reverse of every legal edge, every self-pair, and cross-state jumps such as `idle → settled`, `reset → armed`, `settled → written`) return a rejection whose reason names both states, the reason is also written to stderr, and the store-level transition leaves `state.json` byte-unchanged on rejection

**As built (T2):** "the reverse of every legal edge" cannot hold literally — `armed → written` and `written → armed` are both legal CMD-C edges, so each is the other's reverse. The machine was implemented exactly as CMD-C states it (no edge added or removed); the test asserts the other five reverses are rejected and pins the armed⇄written pair as legal in both directions.

### AC-5: Concurrent wrapper invocations never leave a torn reading file
Given two child processes each invoking the built wrapper repeatedly against the same project with distinct payloads, and a reader polling `reading.json` during the run
When both write concurrently
Then every successful read parses as JSON and matches one of the two payload shapes, transient Windows read errors (`EPERM`/`EBUSY`/`EACCES`/`ENOENT`) are counted separately and never counted as parses, at least one parse of each writer's payload is observed, and no `*.tmp` sibling remains after both finish

**As built (settle):** "no `*.tmp` sibling remains" is amended to "no `*.tmp` sibling remains unless that write was abandoned at the record deadline and emitted the deadline notice". The cause was settle's `code-review` (host-cli), which flagged as HIGH that the statusline waited on the reading write with no bound. The operator chose to bound the wait (`RECORD_DEADLINE_MS`, 250 ms, then flush and `process.exit`) over a bypass. A write cut off mid-rename can leave its `reading.json.<pid>.<hex>.tmp`, and cleaning up at exit cannot help in the case that hits the deadline (Windows lock contention fails the unlink too). Deep-verify then rejected the literal wording, and the operator approved this amendment. The test asserts leftover temp files ≤ deadline notices, and that every leftover is a reading temp.

### AC-6: The state schema records both units and the phase report documents it
Given D-BJ's record-both decision
When the reading schema is exported and `docs/checkpoint/REPORT-checkpoint-phase-2.md` is written
Then the schema carries `used_percentage` (integer or `null`), `unknown`, `absolute` (`total_input_tokens`, `total_output_tokens`, `context_window_size`, and `current_usage.{input_tokens,output_tokens,cache_creation_input_tokens,cache_read_input_tokens}` or `null`), `exceeds_200k_tokens`, `current_dir`, `project_dir`, and `ts`; and a doc-content test asserts the report exists with a named heading per handoff §6 report-back item, the verbatim shipped schema, the coarse-resolution rationale for keeping absolutes, and the Phase 3 preconditions (single-winner `settled→reset`, threshold evaluation, consumer `.gitignore` for `.cadence/checkpoint/`)

**As built (T3):** `used_percentage` is recorded as "number or `null`", not "integer or `null`" — the sensor records the payload value raw (any finite number), because coercing or rejecting a non-integer would be a reading the sensor invented. The docs and the 0.4a log show integers; the report documents the field as "number (integer in every observed payload) or `null`".

### AC-8: Installing the wrapper changes only the statusLine entry of a settings file
Given a `.claude/settings.json` fixture carrying a `hooks` block and either an existing simple `statusLine.command` or none
When `checkpoint statusline-install --settings <path>` runs
Then the file after differs from the file before only inside the `statusLine` value (proven by comparing the text with that value excised, byte for byte, and by asserting `hooks` deep-equal), an existing command is wrapped as `… statusline -- <original>`, an existing command containing shell metacharacters (`|`, `;`, `&`, `<`, `>`, backtick, `$(`) is refused with a message suggesting a script wrapper and the file left byte-unchanged, and the repository's own tracked `.claude/settings.json` is not modified by this phase

### AC-9: A failing state write never breaks the statusline
Given a project whose `.cadence/checkpoint/` cannot be written (a file exists at that path), and separately a project with no `.cadence/` directory in it or any ancestor, and separately stdin that is not valid JSON, and separately an inner argv whose executable does not exist
When the wrapper runs
Then in the first three cases stdout is still byte-identical to the inner statusline's, the wrapper's exit code equals the inner command's, a one-line notice goes to stderr for the write-failure and malformed-input cases, and no `.cadence/` directory is created where none existed; and in the missing-executable case the wrapper writes one stderr notice naming the executable, no stack trace, and exits nonzero

Given core's public entry re-exporting `atomicWriteText` (D-BR)
