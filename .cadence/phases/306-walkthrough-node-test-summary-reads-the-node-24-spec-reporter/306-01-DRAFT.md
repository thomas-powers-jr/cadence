# 306-01 — walkthrough node test summary reads the Node 24 spec reporter

## Objective

`cadence tutorial` and `cadence demo` each echo a one-line summary of the sandbox's real `node --test` run through a private, duplicated `showTestRun` helper that keeps only TAP-style count lines (`# tests N`, `# pass N`, `# fail N`) and otherwise prints `(no test files found)`. Node 22 emits TAP when stdout is piped, but Node 24 emits its spec reporter there too, whose count lines read `ℹ tests 1` / `ℹ pass 1`, so on Node 24 both walkthroughs print `(no test files found)` for a run that did find and execute the test. Settle's `build-test-must-pass` gate is unaffected (it enforces on exit code, and the tutorial's final settle does genuinely run and pass the test), but the visible summary is false, and `packages/core/tests/cli/tutorial.test.ts` AC-4 fails on any Node 24 machine (reproduced on Windows under Node v24.20.0, on unmodified main at `f5c998aa`); CI stays green only because it runs Node 22, while `engines` admits `>=22`. This phase extracts one pure summary parser shared by both walkthroughs that recognises both the TAP (`#`) and spec (`ℹ`) count-line prefixes, and replaces the fallback text so that when no count line is recognised the walkthrough says it could not read a summary rather than asserting that no test files exist — a claim the parser never had evidence for. The command run is unchanged (`node --test`, the same command the sandbox's `testCommand` enforces). This corrects the premise of `rec-20260916-005`, which was filed during phase 305 before the root cause was found: the tests do run on Node 24; only the echoed summary was wrong. Adding a Node 24 CI leg is out of scope.

## Acceptance Criteria

### AC-1: the summary parser reads both TAP and spec reporter count lines
Given `node --test` stdout in TAP form (`# tests 1`, `# pass 1`, `# fail 0` lines) or in Node 24 spec-reporter form (`ℹ tests 1`, `ℹ pass 1`, `ℹ fail 0` lines, with other `ℹ` lines such as `ℹ suites 0` and `ℹ duration_ms 12.3` present), with either `\n` or `\r\n` line endings
When the shared summary parser runs on it
Then it returns `tests 1  ·  pass 1  ·  fail 0` for both forms, in that order, and ignores every other line

### AC-2: an unrecognised summary is reported honestly, not as missing test files
Given `node --test` stdout that contains no recognised count line (empty output, or output in an unknown format)
When the shared summary parser runs on it
Then it returns a string that says the test summary could not be read and does not contain `no test files found`

### AC-3: both walkthroughs echo a real count summary on the Node version running the suite
Given `cadence tutorial` and `cadence demo` run end to end in their ephemeral sandboxes on the Node version executing the test suite
When each walkthrough echoes its `node --test` runs
Then the tutorial output matches `tests 0` before the fix beat and `pass 1` after it, both walkthroughs use the one shared parser rather than a private copy, and neither output contains `no test files found`

**As-built note (T1, review fix).** The independent whole-branch review ran real `node --test` on Node v24.20.0 with `FORCE_COLOR=1` and found the spec reporter wraps each count line in ANSI SGR codes (`\x1b[34mℹ tests 3\x1b[39m`), which the anchored regex rejected, so both walkthrough tests failed under that variable. The parser now strips SGR sequences before matching, with a colored-spec fixture added under `306-01/AC-1`; the tutorial and demo tests were re-run green both with and without `FORCE_COLOR=1`.
