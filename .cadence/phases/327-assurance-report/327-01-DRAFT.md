# 327-01 — cadence assurance report: corpus-wide assurance rollup

## Objective

Every phase's `SUMMARY.json` now carries a defensible account of how strongly it was verified, but no command rolls those accounts up: every portfolio number to date (0 of 121 `boundary-scan` runs in August and 32 of 39 `mixed` in August, both as reported in the 2026-10-10 handoff and not re-measured here, and the strong→mixed drift after phase 283) came from a one-off script. Add `cadence assurance report`, a read-only command that renders the corpus-wide assurance picture as text, or with `--json` as a documented machine shape that the text is derived from, optionally windowed with `--since <phase>`. The report splits every readable settled record into three named categories with their phase boundaries: **un-gradable** (no gate provenance; provenance first appears at phase 140, `140-summary-gate-provenance`), **gradable but never graded** (gate provenance, no `assurance` block), and **graded**. It reports refused settles (any gate with `status: 'refused'`) and unreadable files as their own categories. For graded records it shows the stored grade distribution, the distribution re-derived under the current `deriveAssuranceRecord` rule, and every record whose grade differs (rec-20261010-002, dec-20261010-002). It also reports per-gate ran / skipped / not-recorded counts, the `providerSelection` mix, the number of records with gate bypasses, and the evidence tally. Measured on `main` at `7d96650` (2026-10-10), the corpus is 337 records: 155 un-gradable (phases 2–139), 96 never graded (phases 140–243, including 238, 239, 240 and 243, which sit after the first graded phase 235), and 86 graded (phases 235–326). Re-derivation moves two records, `272-01` and `282-01`, from strong to mixed. Tests pin those numbers against a frozen copy of the corpus at `7d96650`, never against the live tree, which grows with every settle.

### AC-10: a refused settle is its own category, excluded from grading
Given a corpus containing a record with a gate entry whose `status` is `refused`
When the assurance report is computed over it
Then that record is counted as refused, listed by id, and excluded from the three categories (a `refused` entry is only written when a gate halts the settle, `gates/registry.ts`, so a settled record never carries one), the grade distributions, the delta, the gate rows and the evidence tally; the frozen fixture reports 0 refused

**As built (2026-10-10).** Per-task independent reviews changed five behaviors, each with a test. (1) Unreadable files were sorted by path text, so `100-a` came before `99-b`; they now sort by phase number, then path, with un-numbered entries last (AC-7). (2) A file that could not be read carried Node's error message, which embeds the absolute path; the absolute path is now replaced with the repo-relative one (AC-7). (3) `--since` also rejects values beyond JavaScript's safe-integer range, which were silently rounded (AC-4). (4) Run from a directory with no `.cadence/phases` (for example `packages/core`), the report was silently empty; it now prints a stderr note and still exits 0, per "The Quiet Fallback" (AC-6). (5) A gate row counted only a record's first entry for that gate; a record now counts once, as ran if any of its entries ran (AC-3); no record in the fixture has two entries for one gate, so no pinned number moved. A SUMMARY.json directly under `.cadence/phases/` is unreadable with an empty phase, so its file name is never read as a phase number. The AC-5 "every number in the text is in the JSON" test was strengthened with distinct sentinel values after a review showed the original would pass a renderer printing a list length; a mutation (printing `delta.length`) fails the new test. Re-derivation through `SummaryZ` gave exactly `272-01` and `282-01`, the same as the raw-JSON measurement. The four records after the first graded phase (238, 239, 240, 243) are all `schemaVersion` 1 while their graded neighbours are 2; that is consistent with a settle run by an older binary, but this phase records it only as an observation, not a cause. Before settle, the fixture was gzipped by operator decision: settle's review diff is `git diff <merge-base> -- <declared files>`, code-review sends it to the reviewer uncapped, and deep-verify caps it at 256 KB keeping the start, so the 1 MB JSON fixture would have reached Codex whole and pushed the `tests/services/*` evidence files past the deep-verify cap. It is now `corpus-7d96650.json.gz` (147 KB, deterministic level-9 gzip, a byte-identical round trip of the same JSON, still holding each record's verbatim `git show 7d96650:<path>` text); the tests gunzip it with `node:zlib`, and the review diff shows it as one binary line. The cost: secret scanning and `npm-scope-sweep.test.ts` cannot read inside it. Its content is the same text `.cadence/phases` holds in plain form, which they already scan, so T2's `npm-scope-sweep.test.ts` allowlist entry was removed again and that file ends the phase unchanged. The first settle attempt was refused by the draft-read gate, because these As-built amendments made the DRAFT newer than its approval; it wrote a refused `327-01-SUMMARY.json`. The DRAFT was re-read and re-approved (which refreshes only `draftReadAt` and leaves task records alone), with no `--allow-stale-draft`. Task records: T1 was recorded after T2 and T3 were already written, so `327-01-PROGRESS.json` credits the T1–T3 working-tree delta to T1 (as in phase 326). T1–T3 were carried out inline in the phase worktree (recorded `--isolation worktree`); T4 and T5 were dispatched to subagents working in that same worktree, without a worktree of their own (recorded `--isolation none`).
