# 351-01 — boundary-scan names its diff base

## Objective

Stop the settle-time `boundary-scan` gate from silently diffing against a stale local integration ref (rec-20261125-001). Today `resolveMergeBase` in `packages/core/src/git/boundary-diff.ts` asks git once for the merge-base of `origin/<integrationRef>` and `HEAD`, and when that answer is empty it falls back to the local `<integrationRef>` with no notice. Phase 350's first real settle, right after a worker restart, refused at boundary-scan naming seven test files from earlier phases: the upstream call failed, and the local `main` sat at a v1.72-era commit. The same dry run minutes earlier had passed, and the upstream call answered in 6 ms afterwards. After this phase the upstream call is retried once. When the remote-tracking ref exists but its merge-base still cannot be computed, the gate refuses with a named reason, and names a shallow clone when that is the cause, instead of falling back. When the remote-tracking ref does not resolve, the local fallback still happens, but the gate says so on stderr.

Definitions used by AC-1 to AC-3. A git runner is a function `(root, args) => Promise<string>` that returns git's stdout untrimmed, or `''` when git exits non-zero, times out (5 s) or cannot spawn, as `gitBestEffort` in `packages/core/src/git/worktrees.ts` does; `resolveMergeBase` trims each answer. The upstream ref is `origin/<integrationRef>`; it resolves when `git rev-parse --verify --quiet refs/remotes/origin/<integrationRef>` answers non-empty. A shallow clone is one where `git rev-parse --is-shallow-repository` answers `true`. The base source is one of `'upstream'`, `'local'`, `'upstream-failed'` or `'none'`.

## Acceptance Criteria

### AC-1: resolveMergeBase retries the upstream call and falls back to the local ref only when the upstream ref does not resolve
Given the exported `resolveMergeBase(root, integrationRef, git)` with `integrationRef` = `main` and a fake git runner whose answers are scripted per call, in six examples: (a) the upstream merge-base call answers `aaa\n`; (b) the first upstream merge-base call answers `''` and the second answers `aaa\n`; (c) both upstream merge-base calls answer `''`, the upstream-ref check answers `bbb\n`, the shallow check answers `false\n`, and a local merge-base call would answer `ccc\n`; (d) as (c) but the shallow check answers `true\n`; (e) both upstream merge-base calls answer `''`, the upstream-ref check answers `''`, and the local merge-base call answers `ccc\n`; (f) the runner answers `''` to all of its calls
When it runs on the six examples in turn
Then it returns (a) `{ base: 'aaa', source: 'upstream' }`; (b) `{ base: 'aaa', source: 'upstream' }`; (c) `{ base: null, source: 'upstream-failed', shallow: false }` and the runner received no local merge-base call; (d) `{ base: null, source: 'upstream-failed', shallow: true }`; (e) `{ base: 'ccc', source: 'local' }`; (f) `{ base: null, source: 'none' }`.
Not covered: the 5-second timeout itself; a second retry; a transient failure of the upstream-ref check, which reads as "does not resolve" and leads to the local fallback, now with the AC-2 notice; `build task`'s record-time check, which treats `upstream-failed` like `none` (working-tree files only, no new notice); the `deep-verify` diff's own resolver (`resolveMergeBaseSync`).

### AC-2: The gate names a local fallback on stderr
Given a git repository in a temporary directory with a `main` branch and no `origin` remote, a `feature` branch with one committed file declared in the DRAFT's `files:`, and a `SettleContext` built as `packages/core/tests/gates/boundary-scan.test.ts`'s `ctx()` helper builds it, with `draft.boundaryEnforcement: 'block'`
When the `boundary-scan` gate runs
Then its stderr contains the line `boundary-scan: origin/main did not resolve; diffing against the merge-base with the local main ref (<sha>)` followed by a newline, where `<sha>` is the first 7 characters of `git merge-base main HEAD` in that repository, and the gate passes.
Not covered: an `integrationRef` other than `main`, beyond the ref name being substituted; a repository where the local ref also has no merge-base, which keeps today's "could not resolve a base ref" notice.

### AC-3: The gate refuses when the upstream ref resolves but its merge-base cannot be computed
Given block-mode contexts built as in AC-2 over two repositories in temporary directories, each with a `feature` branch holding one committed file declared in the DRAFT's `files:`: (a) a full repository whose `refs/remotes/origin/main` was set with `git update-ref` to a commit with no common history with `HEAD`; (b) a shallow clone, made with `git clone --depth 1 --branch feature file://<source>` followed by `git fetch --depth 1 origin main:refs/remotes/origin/main`, where `main` in the source repository has moved on after `feature` branched
When the `boundary-scan` gate runs on (a) and on (b) with no bypass flag, and on (a) with `--allow-boundary-scan-failure`
Then (a) refuses with the reason `settle run refused: boundary-scan could not compute the merge-base of origin/main and HEAD after a retry. Re-run settle, or pass --allow-boundary-scan-failure to scan only working-tree changes.`; (b) refuses with the reason `settle run refused: boundary-scan could not compute the merge-base of origin/main and HEAD after a retry, and this is a shallow clone. Run git fetch --unshallow origin (or --deepen=<n>) and re-run settle, or pass --allow-boundary-scan-failure to scan only working-tree changes.`; and (a) with the flag passes, returns `flags: { boundaryScanBypassed: true }`, prints `boundary-scan: --allow-boundary-scan-failure set; scanning working-tree changes only.` followed by a newline, and prints no line containing `could not resolve a base ref`.
Not covered: `--force`, whose bypass line names `--force` in place of `--allow-boundary-scan-failure`; a sealed `boundary-scan`, which refuses as the gate's other sealed refusals do; a DRAFT whose declared `files:` union is empty, which still passes before this refusal is considered; a repository whose `HEAD` is unborn; a local ref that is behind `origin/<integrationRef>`, which is no longer consulted when the upstream ref resolves (the rec's "refuse when behind" idea is dropped for that reason).
