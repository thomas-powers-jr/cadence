# 323-01 — post-publish npm verification outlasts registry cache propagation

## Objective

Make the Release workflow's post-publish "verify registry" step mean something again (rec-20260802-005). The last five `Release` runs, v1.67.3 (35926962120), v1.68.0 (36057230234) and v1.69.0 (37231218286) among them, went red at `scripts/release-integrity.mjs`'s post-publish `verifyNpmPackages` with "`@thomas-powers-jr/cadence-core` is <previous> on npm, expected <new> … failed after 10 attempts" even though publish, tag and GitHub Release had all succeeded, so today a red run carries no signal and every release is verified by hand. The cause, confirmed on the v1.69.0 run (ev-20261004-013, ev-20261007-001 and its correction ev-20261007-002): the budget phase 218 set, `POST_PUBLISH_VERIFY_ATTEMPTS = 10` with `retry()`'s `1000 * attempt` linear backoff, is about 45 s of waiting (the failing step ran 20:21:26 → 20:22:17), while the registry's Cloudflare edge caches packuments for `Cache-Control: public, max-age=300` (CF-Cache-Status HIT observed). The workflow's pre-publish idempotency check (`--verify-npm`, 20:21:02) may warm that edge copy seconds before publish, and `cadence-core` became visible about 180 s after the failure, just inside 20:21:02 + 300 s. No npm client flag helps: `npm view` already hardcodes `preferOnline: true` (npm 10.9.2 and 11.19.0 `lib/commands/view.js`), so every attempt did revalidate against the registry and still got the edge's copy. The rec's own caution, "don't blanket-extend the budget for routine releases", is overridden by that run history: routine releases need a budget that outlasts the five-minute edge cache. The fix is in the script only: the post-publish poll runs on a flat 15 s interval for up to 40 attempts (at least about 10 minutes of waiting between attempts, comfortably past `max-age=300` plus propagation) and writes one stderr progress line per miss so the run log records when each package actually became visible. The pre-publish check keeps its 3-attempt fast fail. `docs/release.md` and the `release-cut` skill describe the new behaviour, the skill stops calling a red verify step "often just an npm-CDN propagation race", and it finally names all five published packages, `host-toolkit` included. `.github/workflows/release.yml` is not touched (its stale "three public packages" comment is a follow-up, not this phase).

## Acceptance Criteria

### AC-1: post-publish verification outlasts the registry edge cache lifetime
Given `runReleaseIntegrity` has created or updated the GitHub Release and now verifies npm, and `npm view <pkg> version` keeps answering with the previous version for longer than the old 10-attempt budget tolerated (for example 25 consecutive stale answers)
When the post-publish verification runs
Then it keeps polling on a flat interval of 15 s (`POST_PUBLISH_VERIFY_INTERVAL_MS`) for up to 40 attempts (`POST_PUBLISH_VERIFY_ATTEMPTS`), both exported from `scripts/release-integrity.mjs`, so that `(attempts - 1) * interval` is at least 585 000 ms (past the registry's `max-age=300`), succeeds as soon as an attempt sees the expected version, and only throws after the last attempt with an error that keeps the `failed after N attempts` prefix and names the package, the version seen, the expected version and the elapsed seconds.

### AC-2: the pre-publish idempotency check stays fast and quiet
Given `verifyNpmPublished` runs before publish to decide whether the publish step can be skipped
When a package genuinely is not yet on npm at the target version
Then it still fails after exactly 3 attempts with the existing `1000 * attempt` backoff (about 3 s), rejects with `failed after 3 attempts`, and writes no progress lines; nothing about its timing or its `npm view` arguments changes.

### AC-3: progress is visible in the run log, never on stdout
Given the post-publish verification misses on an attempt
When it schedules the next attempt
Then it writes exactly one line (one trailing newline, no embedded newlines even when `npm view`'s own failure output spans several lines) to stderr for that miss, prefixed `release-integrity:`, naming the package, the version npm returned (or the collapsed failure reason when `npm view` itself failed), the expected version, `attempt <n>/<N>` and the elapsed seconds since that package's first attempt; no stdout write from the script contains `release-integrity:` or `attempt `, so `--json` output stays a single JSON document.

**As built (2026-10-07):** "no stdout write from the script" is scoped to the verification loop (`verifyNpmPackages` / `runReleaseIntegrity`). `main()`'s pre-existing non-JSON success summary still prints `release-integrity: …` lines to stdout, unchanged by this phase; with `--json` stdout remains a single JSON document.

### AC-4: docs and the release-cut skill describe the new budget
Given `docs/release.md` and `.claude/skills/release-cut/SKILL.md`
When an operator reads them
Then `docs/release.md` states that the post-publish verification polls `npm view` on a 15 s interval for at least about `<N> minutes` (where `<N>` equals `Math.round((POST_PUBLISH_VERIFY_ATTEMPTS - 1) * POST_PUBLISH_VERIFY_INTERVAL_MS / 60000)` as exported by the script) because the registry's edge serves packuments with a five-minute cache lifetime (`max-age=300`), that the step log shows `one progress line per miss`, and contains the exact sentence fragment `a red verify step after that budget is a real mismatch to investigate, not a propagation race`. The skill's step 2 says `all five published packages` naming `host-toolkit`, its step 6 lists `npm view @thomas-powers-jr/cadence-host-toolkit version` among the commands and says `All five on npm`, and step 5 no longer contains `often just an npm-CDN propagation race` (it says the verify step now waits out propagation, so a red there deserves investigation, while `Never \`gh run rerun --failed\` on the Release workflow` and the verify-by-hand rule stand). A doc-content test pins each of these strings and computes `<N>` from the script's exports.
