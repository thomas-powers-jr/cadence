# 336-01 — checkpoint Stop gate: block once at threshold, settle on a valid handoff, record a forced release

## Objective

Build checkpoint arc Phase 3 (work order `docs/handoffs/HANDOFF-v1.71-release-335-336.md` §3): a `checkpoint stop-gate` subcommand wired as a Claude Code `Stop` hook, a `checkpoint session-start` subcommand wired as a `SessionStart` hook, and a `checkpoint hooks-install` installer, all inside `packages/checkpoint` (the ledger and loop stay core's). On `Stop` in `idle`, the gate reads `.cadence/checkpoint/reading.json` by exact name (never a `*.tmp` sibling; a reading whose `ts` is older than `--max-reading-age-s`, default 600, is absent). The effective usage is `used_percentage` when it is a non-null number; only when it is null or absent, the percentage is computed from `current_usage` with Claude Code's input-only formula (`input_tokens + cache_creation_input_tokens + cache_read_input_tokens`) over `context_window_size` (D-BJ, `dec-20261013-001`); `current_usage: null` and a post-`/compact` `used_percentage: 0` are unknown, never 0, and never block. At or above `--threshold` (percent, default 70) the gate transitions the store to `armed` first and only then prints exactly one `{"decision":"block","reason":…}` naming `cadence handoff` (D-BN transport, `dec-20260925-001`; 0.4a proved it). In `armed`, the newest `.cadence/handoff/SESSION-*.md` whose mtime is after the state's `since` is read as bytes, decoded once (strict UTF-8, BOM stripped), and that one text goes to both `validate()` and core's `findUnfilledSections` (exported from core's index this phase); it must also declare `cadence_handoff` ≥ 2. Valid → `armed → written → settled`, exit 0. Invalid → `written → armed` and a block carrying the diagnostics. No doc → the instruction is issued once per entry into `armed`, never per turn (CMD-D). A chain of consecutive blocks reaching `--ceiling` (default 3) while `stop_hook_active: true` releases instead: `{"systemMessage":…}`, `armed → settled` (a new edge, legal only with `ctx.forced`), `forced: true`, `forcedAt`, and a sticky `lastForcedAt` that no later edge clears. `SessionStart` (sources `startup`, `clear`, `compact`; not `resume`/`fork`) walks `settled → reset → resumed → idle` as a single winner via an `open(…, 'wx')` lock, and returns a stale `armed` to `idle` (a new `ctx`-guarded edge). Per D-CE (`dec-20261022-002`, option 2, superseding `dec-20261022-001`), `settle run` reads `.cadence/checkpoint/state.json` by path, best-effort, and when `lastForcedAt` is at or after the active draft's `openDrafts[].since` it passes that fact into `collectAnomalies`, which emits a `checkpoint-force-released` anomaly; a fifth `anomalyToGateBypass` arm maps it to `{ gate: 'checkpoint-stop', flag: 'ceiling-release', severity: 'error' }`, so phase 283's cap holds the phase at `mixed`. Every hook path that is not a deliberate block exits 0; any thrown error inside a hook is a stderr notice and exit 0, never a block.

## Acceptance Criteria

### AC-1: threshold crossing blocks once and arms
Given a project whose checkpoint state is `idle` and whose `reading.json` has `used_percentage` at or above the gate's threshold
When `checkpoint stop-gate` runs on a `Stop` payload with `stop_hook_active: false`
Then stdout is exactly one JSON object `{"decision":"block","reason":…}` whose reason names `cadence handoff`, the process exits 0, and the store reads `armed` with the instruction recorded as issued, written before stdout

### AC-2: an unknown reading never blocks
Given state `idle` and a reading whose `used_percentage` and `current_usage` are both null, or whose `used_percentage` is 0 with a non-null `current_usage` that would compute above the threshold
When `checkpoint stop-gate` runs
Then stdout is empty, the process exits 0, and the store bytes are unchanged

### AC-3: one instruction per entry into armed, not per turn
Given state `armed` whose instruction has not yet been issued, and no handoff doc newer than the state's `since`
When `checkpoint stop-gate` runs three consecutive times
Then exactly one of the three invocations prints a block instruction, the other two print nothing, and all three exit 0

### AC-4: a valid v2 handoff settles
Given state `armed` and a SESSION doc rendered by core's real `cadence handoff` renderer, with every placeholder filled and `cadence_handoff: 2`, written after the state's `since`
When `checkpoint stop-gate` runs
Then stdout is empty, the process exits 0, and the store reads `settled`

### AC-5: a gate-instructed doc may not downgrade the schema
Given state `armed` and a doc newer than `since` that declares `cadence_handoff: 1` and is otherwise valid under schema v1
When `checkpoint stop-gate` runs
Then it blocks with a reason containing a diagnostic named `version-downgrade`, and the store reads `armed`

### AC-6: unfilled placeholder sections block, by name
Given state `armed` and a structurally valid v2 doc from core's renderer with its `<!-- … FILL IN … -->` markers left in two sections
When `checkpoint stop-gate` runs
Then it blocks with a reason naming both sections exactly as core's exported `findUnfilledSections` returns them, and the store reads `armed`

### AC-7: a BOM never changes the verdict
Given the AC-4 doc and the AC-6 doc, each written once with a UTF-8 BOM and once without
When `checkpoint stop-gate` runs against each in `armed`
Then each BOM variant produces byte-identical stdout, exit code and resulting store state to its BOM-free twin

### AC-8: the ceiling releases and records the force
Given ceiling 3, state `armed`, and two consecutive gate blocks already in the chain
When a third `Stop` arrives with `stop_hook_active: true` and the gate would block again
Then stdout is exactly one JSON object with a `systemMessage` and no `decision`, the process exits 0, and the store reads `settled` with `forced: true`, `forcedAt`, and `lastForcedAt` equal to `forcedAt`; a `Stop` with `stop_hook_active: false` in between starts a new chain

### AC-9: a temp sibling is never a reading
Given state `idle`, no `reading.json`, and a `reading.json.<pid>.<rand>.tmp` sibling holding a reading above threshold
When `checkpoint stop-gate` runs
Then stdout is empty, the store is unchanged, and the sibling's bytes are never parsed (proven by a sibling that is not valid JSON producing no stderr)

### AC-10: a broken store never wedges a session
Given the store write throws (an injected `EACCES` from the write seam) while the gate is about to block
When `checkpoint stop-gate` runs
Then stdout is empty, the process exits 0, and stderr carries exactly one checkpoint notice line naming the error

### AC-11: SessionStart reset is single-winner
Given state `settled` and two `checkpoint session-start` handlers started concurrently with `source: "clear"`
When both complete
Then exactly one of them performed `settled → reset → resumed → idle`, the other exited 0 without writing the state file, the final store reads `idle`, and the lock file is gone

### AC-12: the installer is idempotent
Given a settings file with user-authored hooks and cadence's own `_managedBy: "cadence"` entries
When `checkpoint hooks-install --settings <path>` runs twice
Then the second run writes nothing, reports "already installed", and the file's bytes equal the bytes after the first run

### AC-13: a stale reading is absent
Given state `idle` and a `reading.json` above threshold whose `ts` is older than `--max-reading-age-s`
When `checkpoint stop-gate` runs
Then stdout is empty and the store is unchanged

### AC-14: the absolute fallback uses the input-only formula
Given state `idle` and a reading with `used_percentage: null`, a non-null `current_usage` and a `context_window_size`
When `checkpoint stop-gate` runs with a threshold just above, then just below, `(input_tokens + cache_creation_input_tokens + cache_read_input_tokens) / context_window_size × 100`
Then the first run prints nothing and leaves `idle`, the second blocks and arms, and `output_tokens` never changes either outcome

### AC-15: a force-release survives the reset and caps the grade
Given a draft opened before a ceiling force-release, followed by a `SessionStart` reset back to `idle`
When `settle run` runs for that draft
Then `SUMMARY.gateBypasses` holds exactly one entry `{ gate: "checkpoint-stop", flag: "ceiling-release", severity: "error" }`, and `assurance.overall` is `mixed`

### AC-16: an old, absent or corrupt checkpoint record changes nothing
Given a checkpoint `lastForcedAt` earlier than the active draft's `openDrafts[].since`, or no `.cadence/checkpoint/state.json`, or one that is not valid JSON

### AC-17: a new session never inherits a stale armed state
Given state `armed` left by an earlier session
When `checkpoint session-start` runs with `source` `startup`, `clear` or `compact`, and separately with `resume` or `fork`
Then the first three leave the store `idle` with the instruction flag cleared, and `resume`/`fork` leave the store bytes unchanged

### AC-18: crash leftovers are inert on Stop
Given state `written`, `reset` or `resumed`
When `checkpoint stop-gate` runs
Then stdout is empty, the process exits 0, and the store bytes are unchanged

### AC-19: a stale lock is reported, never broken
Given state `settled` and a SessionStart lock file left by a crashed handler
When `checkpoint session-start` runs with `source: "clear"`
Then it exits 0 without writing the state file, leaves the lock file in place, and prints exactly one stderr line naming the lock path and how to remove it

### AC-20: installer and cadence's own installer leave each other alone
Given a settings file after `checkpoint hooks-install`
When cadence's host installer merge (`mergeManagedHookEntries` with its default stale rule) runs over it, and when `checkpoint hooks-install` runs over a file holding cadence's entries
Then the checkpoint `Stop`/`SessionStart` entries tagged `_managedBy: "cadence-checkpoint"` survive the first, cadence's `_managedBy: "cadence"` and every user-authored entry survive the second, and the installer refuses any planned edit that changes anything outside its own entries

**As built (settle):** "refuses any planned edit that changes anything outside its own entries" is amended to "refuses any planned edit that changes any parsed value outside its own entries, as `JSON.parse` sees the file". The installer re-serializes `settings.json` (`JSON.stringify(…, null, 2)` plus a newline, the host installer's precedent; the operator approved this before BUILD). Its guard (`verifyOnlyManagedHooksChanged`) re-parses the planned text and refuses unless it deep-equals the original everywhere except the checkpoint-managed `hooks.Stop` / `hooks.SessionStart` entries. A re-serialized file can still differ outside those entries in ways parsing discards, and the guard cannot see them. The list is not exhaustive; it includes whitespace and indentation, CRLF line endings, duplicate keys (last wins, as in Claude Code), integers beyond 2^53 and other number spellings (`1.0`, `1e3`, `-0`), string-escape spellings (`é`, `\/`), and the order of integer-like keys. The pre-BUILD summary given to the operator said the guard "refuses any edit that changes anything outside its own entries", which overstated it. Deep-verify (host-cli) rejected the literal wording on settle attempt 3, and the operator approved this amendment on 2026-10-23 over a byte-preserving rework. The tests assert parsed equality outside the managed entries, refusal of 11 tampered plans, and that cadence's and user-authored entries survive in order. The limits are recorded in the `install-hooks.ts` header and the report.
