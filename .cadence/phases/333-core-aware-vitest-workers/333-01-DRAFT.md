# 333-01 — Core-aware vitest worker cap

## Objective

Stop the recurring macOS CI `Test timed out in 20000ms` failures in core's CLI-spawning tests (`rec-20261008-005`, folding in the same-class `rec-20260918-004`). Make `vitest.shared.ts`'s worker count a core-aware upper bound: an exported pure `resolveMaxWorkers(cores)` returning `Math.max(1, Math.min(12, cores))`, applied as `maxWorkers: resolveMaxWorkers(availableParallelism())`. This replaces the flat `maxWorkers: 12`.

**Root cause.** Phase 32.1 set that 12 as a cap below a 24-core dev box. vitest's own default is `availableParallelism() - 1`, so on the 3–4 vCPU CI runners the flat value *raised* the pool to 12. Every leg ran about 9.8 tests at a time, roughly 4× oversubscribed on the 3-vCPU `macos-26-arm64` runner. Each spawned `node dist/cli/index.js` costs about 370 ms even idle (about 290 ms of it is `register.js` eagerly loading 523 modules). About 49 tests make 5 or more sequential CLI calls (or loop over them) and 239 more make 3–4, so under that contention a 5-spawn test needed 10.3 s on Ubuntu and 20.1 s on macOS. The timeouts were the 20 s budget running out, not a logic bug, and splitting tests one by one would not converge.

**Measured evidence.**
- Failing runs: 39481591050 attempts 1 and 2, plus 39468308041 and 39461022835, all on 2026-10-20 and all macOS-only red on diffs that cannot touch core.
- Pre-draft probe, 2026-10-21 (throwaway PR #575, run 39613760426, same change plus a core-count log, now closed). Logged cores were macOS 3, Ubuntu 4, Windows 4, and `maxWorkers` matched them. All three legs went green.

| Leg | Concurrency (`tests`/`Duration`) | milestone.test.ts:124 | recommendation.test.ts:242 | Core-suite `Duration` |
|---|---|---|---|---|
| macOS | 9.8 → 2.5 | 20.1 s → 1.85 s | 20.0 s → 3.0 s | 572 s → 418 s |
| Ubuntu | 9.8 → 3.3 | 10.3 s → 1.6 s | 8.5 s → 2.3 s | 342 s → 241 s |
| Windows | 10.6 → 3.5 | 14.3 s → 5.1 s | 12.5 s → 7.5 s | 714 s → 874 s |

The same probe moved `rec-20260918-004`'s tests on macOS the same way: `debugging-skill-walkthrough.test.ts` 313-01/AC-2 went from 17.2 s to 3.0 s and AC-4 from 17.1 s to 3.7 s. So did `demo-gutting-coverage-scheme.test.ts`, from 24.2 s to 5.7 s. The Windows suite slows by about 160 s, because its spawns are I/O-bound and benefited from the overlap. The operator accepted that trade on 2026-10-21 over a win32-specific multiplier: one rule for every OS, and Windows still clears its 90 s budget by more than 10×.

**Why `cores` and not vitest's `cores - 1`.** Workers here mostly block on CLI child processes, and `cores - 1` would give 2 workers on the 3-vCPU macOS runner.

**What stays the same.** On a machine with 12 or more cores (the dev box has 16) the value stays 12, so local runs are unchanged. The fix is proven on CI runners, not locally. The root config is private and no published manifest changes, so there is no changeset (phase 330 precedent).

**Follow-up.** Lazy-loading CLI command modules (the ~290 ms / 523-module startup cost, which would also speed up real users' CLI) is out of scope. It is filed as its own recommendation at settle.

## Acceptance Criteria

### AC-1: resolveMaxWorkers is a core-aware upper bound of 12
Given `vitest.shared.ts`'s exported pure `resolveMaxWorkers(cores)`
When it is called with 1, 2, 3, 4, 11, 12, 13, 16 and 24 cores, and with the degenerate inputs 0 and a negative count
Then it returns the core count itself for 1 through 12 (so a 3-vCPU runner gets 3 and a 4-vCPU runner gets 4), 12 for every count above 12, and 1 for 0 or a negative count, never less than 1 and never more than 12

### AC-2: the shared config applies the helper to this machine's real parallelism
Given the default export of the root `vitest.shared.ts`, imported as a module rather than read as text
When its `test.maxWorkers` is compared with `resolveMaxWorkers(os.availableParallelism())` computed in the test process
Then they are equal, and no config-object line of the file's source sets `maxWorkers` to a flat number (matched line-anchored, as `^\s*maxWorkers:\s*\d+\s*,`, so the comment that explains the old `maxWorkers: 12` does not trip the check), so the worker count can never again silently exceed the machine's cores

### AC-3: the timeout, pool and coverage settings around the worker cap are unchanged
Given the same imported default export
When its `test.testTimeout`, `test.hookTimeout`, `test.pool` and `test.coverage.enabled` are read
Then both timeouts equal 90000 on win32 and 20000 on every other platform, `pool` is `forks`, and coverage stays enabled, so this phase moves only the worker count
