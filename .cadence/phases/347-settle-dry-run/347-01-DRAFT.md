# 347-01 — Settle dry run

## Objective

Settle is today the only way to run the real code-review and deep-verify gates, and every failing code-review run spends one of the draft's convergence attempts (config.convergence.maxAttempts, default 3) in its CODE-REVIEW.json sidecar, so the only way to learn what the configured reviewer thinks is to spend that budget; phase 346 spent three attempts across three PCs this way (rec-20261113-001). `cadence settle run --dry-run` runs what `settle run` would run with the same flags — the same preconditions, gate set, gate order, diff basis, prompts, providers and bypass flags, through the post-gate checks (AC derivation, anomaly and skill-audit checks, evidence floor) — and stops before settle's finalize step: it makes exactly the verifier calls settle would make, stops where settle stops, prints what settle would decide and why, and cadence itself writes nothing, notifies nothing and spends no convergence attempt. A dry run settles nothing, so suppressing notification does not touch D4 (anomaly-notify for the auto profile). Operator decisions 2026-11-17: the mode is a flag on `settle run`, not a new command; and it stops at the first refusal exactly as settle does.

## Acceptance Criteria

### AC-1: a dry run decides exactly what settle would decide
Given an active draft and any combination of settle run's verdict, gate and bypass flags that AC-4 does not refuse
When `cadence settle run --dry-run` runs, and `cadence settle run` with the same flags runs immediately after it on the same tree
Then the dry run checks the same preconditions, resolves the same gate set and runs the same gates in the same order through the same code (no gate, test command or verifier call is stubbed or skipped), stops at the first gate refusal as settle does, and when no gate refuses also runs AC-result derivation, the anomaly and skill-audit checks and the evidence floor; its final verdict (would pass, or would refuse at a named gate or check with settle's reason) equals the real settle's outcome, and its per-gate list (gate, status, reason, provider) equals the `gates` array of the SUMMARY or refused SUMMARY the real settle writes; when settle would prompt for AC verdicts, its outcome depends on answers a dry run cannot have, so the dry run reports the outcome settle would reach with every AC confirmed and says so on its own line (dec-20261118-001); shown for each of these fixtures: a passing settle; refusal outside BUILD; a phase-collision refusal; the auto x complex soft-cap refusal; an early-gate refusal before the AI gates; a deep-verify refusal; a code-review refusal; a bypassed code-review refusal; an `--auto` offender refusal; a skill-audit refusal; an evidence-floor refusal; and a `verification.fallback: "refuse"` refusal

### AC-2: cadence writes nothing and notifies nothing in a dry run
Given the fixtures of AC-1, with no test command or a side-effect-free one
When `cadence settle run --dry-run` runs, passing or refusing
Then cadence itself writes no file: no SUMMARY or refused-attempt SUMMARY snapshot, no RETRO, no `*-CODE-REVIEW.json` sidecar write (so the attempt count a later real settle reads is unchanged), no `state.json` or `STATE.md` change (the loop position is unchanged), no PROGRESS change, no recommendation, decision or evidence ledger change, and no anomaly-log entry; no anomaly event is dispatched to any notifier transport, the stderr transport included, the precondition and catch-block loop violations and settle's anomaly notification included; no interactive prompt or retro offer runs; the configured test command and any spawned verifier process run exactly as settle runs them, and their own writes are outside this guarantee; shown by hashing every file in the fixture repository before and after each dry run, with `notify.transport: "file"` and `anomaly-notify` in the gate set

### AC-3: the dry run reports what settle would see
Given a dry run that reaches its verdict
When it finishes
Then it writes to stdout a report, also returned as structured data, naming each gate that ran with its outcome (ran, skipped with reason, refused with reason, or bypassed with the flag) and provider; for deep-verify, each AC's verdict, reason and provider; for code-review and security-audit, each finding's severity, file where the finding carries one (security-audit findings are not per-file and show `-`), line and message and the provider and model; for code-review, the attempt this would have been (`would be attempt N of M`) and the would-be convergence verdict (pass, abstained, reloop, escalate or bypassed), a passing review being reported as consuming no attempt; each anomaly event settle would have sent (type, severity, message) under `would notify:`; when settle would walk ACs interactively, that it would prompt, on a line of its own; and a final line, with nothing appended, `settle would pass` or `settle would refuse at <gate or check>: <reason>`, which is authoritative over any gate's own refusal wording; every stderr notice settle prints before its finalize step (the mock-fallback and foreign-binary banners, diff-basis notices, bypass notices) is still printed to stderr; two consecutive dry runs report the same attempt number, and the attempt a following real settle records equals the one the dry run predicted; the exit code is 0 when settle would pass and 1 when it would refuse

### AC-4: dry-run-only rules are enforced up front
Given `cadence settle run --dry-run` with `--interactive` or `--ship-ref`, through the CLI or `settleService` directly
When it starts
Then it exits 2 with a usage error naming the flag and why (an interactive walk needs a human at a settle that records nothing; `--ship-ref` only affects the finalize step a dry run never reaches), before any precondition, gate, test command or verifier runs; a dry run never walks ACs interactively: where the gate set would prompt, it takes the gate's non-interactive path, says so on stderr and in the report; the existing settle test files (`tests/services/settle*.test.ts`, `tests/cli/settle*.test.ts`) pass unchanged

### AC-5: the dry run is documented
Given the docs, help text and changeset
When `--dry-run` ships
Then `settle run --help` and `docs/reference/commands.md` describe `--dry-run` (what it runs, that cadence writes and notifies nothing, that it spends no convergence attempt, its exit codes 0, 1 and 2, and the two refused flags), `docs/reference/exit-codes.md` lists it under exit 2, `docs/concepts.md` notes it beside the code-review convergence budget, a minor changeset for cadence-core states the same, and a doc-content test asserts these

## Boundaries

- Do NOT change what `settle run` without `--dry-run` does, prints or writes.
- Do NOT edit any file under `packages/core/src/gates/` or `packages/core/src/verify/`: the dry run reuses every gate's decision logic, prompt, diff basis, provider selection and `verification.fallback` behaviour as they are.
- Do NOT stub, skip or short-circuit any gate, test command or verifier call under `--dry-run`.
- Do NOT change convergence semantics (maxAttempts, escalation) or the sidecar format (out of scope per rec-20261113-001; rec-20260806-007 stays open).
- Do NOT add a new top-level command, an MCP tool parameter, or a dry run for `spec approve` or `draft approve` review gates.
- Do NOT add a runtime dependency.
- Do NOT persist anything from a dry run, including a cache of its findings.
