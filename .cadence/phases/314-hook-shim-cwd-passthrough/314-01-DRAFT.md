# 314-01 — Hook shim subprocess spawns don't pass the payload's cwd, so worktree-isolated hook effects land in the primary checkout

## Objective

Both host adapters' hook shims (`packages/host-claude-code/src/cli.ts` and `packages/host-codex/src/cli.ts`) spawn the `cadence hook <event>` subprocess without an explicit `cwd` option, so the child silently inherits whatever `process.cwd()` the shim process itself was launched with. This was directly observed to produce a live bug in phase 313 (`rec-20260918-003`): invoking a skill while working inside a genuinely worktree-resident session (confirmed by that session's own manual `cadence settle run --auto` and `cadence hook skill-invoke` commands, both explicitly run "from inside the worktree" and correctly reading/writing that worktree's own `.cadence/state.json`) recorded the *automatic* Skill-tool hook's invocation into the *primary checkout's* state instead. Two candidate mechanisms are both consistent with Claude Code's own hooks reference (`https://code.claude.com/docs/en/hooks`, "Common input fields" / "Worktrees are different"), which is ambiguous on this specific point across repeated readings: (a) Claude Code always launches the hook subprocess's OS-level cwd from the worktree, and CADENCE's shim would already inherit it correctly — making this fix a redundant no-op; or (b) it does not, and the shim's blind `process.cwd()` inheritance is the actual bug, matching what was observed. Neither shim reads the payload's `cwd` field today, and explicitly extracting and using it is correct under either mechanism — harmless when (a) holds, the real fix when (b) holds (which the phase-313 observation favors). T2/T4 add a one-line stderr notice whenever the payload's `cwd` differs from the shim's own `process.cwd()`, so the next worktree-isolated `phase-build` in production settles which mechanism is real, empirically, rather than leaving it an open assumption. Fix both shims to extract `cwd` from the parsed stdin payload and pass it through to `spawn()`, falling back to the shim's own `process.cwd()` when the field is absent or names a directory that no longer exists, so any hook fired while work is happening inside a worktree — skill-invoke telemetry, edit/boundary tracking, session-start context — lands in that worktree's own `.cadence/state.json` rather than the primary checkout's.

## Acceptance Criteria

### AC-1: host-claude-code's hook shim passes the payload's cwd to the spawned cadence subprocess
Given a hook JSON payload on stdin whose `cwd` field names an existing directory different from the shim process's own `process.cwd()` (e.g. a worktree)
When `cadence-host-claude-code hook` runs
Then the spawned `cadence hook <event>` child process runs with that payload `cwd`, and any state it writes lands under that directory's own `.cadence/state.json`, not the shim's own `process.cwd()`

### AC-2: host-codex's hook shim has the identical fix
Given the same payload-cwd scenario as AC-1
When `cadence-host-codex hook` runs
Then it exhibits the same corrected behavior as AC-1

### AC-3: missing or stale payload cwd falls back to the shim's own process.cwd(); a real divergence is logged
Given a hook JSON payload with no `cwd` field, or a `cwd` field naming a directory that does not exist on disk (e.g. a deleted worktree)
When either shim's `hook` command runs
Then it spawns the child with the shim's own `process.cwd()` (today's behavior) and does not throw or exit non-zero for this reason alone; and separately, given a payload whose `cwd` exists on disk but differs from the shim's own `process.cwd()`, the shim emits a one-line stderr notice naming both directories before spawning with the payload's `cwd`

- DO NOT touch `packages/host-toolkit/src/routing.ts`'s payload translation (`extractPayload`, `routeHookEvent`) — the `cwd` field already passes through untouched in `translated`; this phase only changes what the shim's `cli.ts` does with it when spawning.
- DO NOT change `packages/core/src/cli/commands/hook.ts` or `HookDispatcher`'s own `process.cwd()` resolution — once the child process is spawned with the correct `cwd`, its own `process.cwd()` is already correct by construction; no core-side change is needed.
- DO NOT attempt to fix `rec-20260917-006`'s separate finding (the `invoked` list's time-ambiguity/identity-blindness) — different rec, out of scope here.
- DO NOT add a shared cwd-resolution helper to `host-toolkit` speculatively; if the two shims' fallback logic turns out identical and small, duplicating ~3 lines is acceptable — only extract it if it grows real complexity.
- DO NOT modify any existing test file in `packages/host-claude-code/tests/` or `packages/host-codex/tests/` (event mapping, Skill/edit-tool payload extraction, adapter-conformance, prompt-parity golden fixtures) to make this phase's tests pass — this fix changes only which `cwd` the spawned subprocess runs in; if any existing test breaks, that is a signal to reconsider the fix, not to adjust the test.
