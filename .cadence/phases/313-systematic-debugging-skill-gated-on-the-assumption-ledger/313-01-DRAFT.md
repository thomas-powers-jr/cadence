# 313-01 — systematic-debugging skill gated on the assumption ledger

## Objective

Ship `.claude/skills/systematic-debugging/SKILL.md`: a debugging discipline whose hypotheses are recorded as `cadence assumption` rows tied to one anchor recommendation, and whose conclusion step is gated on the deterministic query `cadence assumption list --filter-rec <id> --filter-status open --format json` coming back empty. This gives the assumption ledger — a full `open | validated | rejected` hypothesis store with **zero callers anywhere in `.claude/`** — its first consumer, and makes a debugging session's trail inspectable after the fact rather than lost to the transcript. What separates it from prose advice is the substrate, not enforcement: CADENCE cannot refuse a conclusion the way settle refuses a phase, so the honest claim is that the skill's conclusion is gated on a ledger query the skill honors. That distinction is load-bearing and is asserted, not glossed. Source: `rec-20260918-002`.

## Acceptance Criteria

### AC-1: the skill exists and matches the house template
Given `.claude/skills/phase-build/SKILL.md` is the established shape — frontmatter `name` + `description`, then `# Title`, `## Preconditions`, `## Pipeline`, `## Known failure modes to actively watch`
When `.claude/skills/systematic-debugging/SKILL.md` is read
Then it carries all of those sections in that order, and its `description` names concrete debugging trigger phrases (the host uses `description` to decide when to invoke, so generic wording would make it unreachable)

### AC-2: a fixture debugging session leaves a complete, inspectable ledger trail
Given a fixture bug worked through the skill's pipeline against an ephemeral repo
When each hypothesis is filed with `cadence assumption add --rec <anchor> --text <falsifiable statement>` and closed with `validate` or `reject`
Then `cadence assumption list --filter-rec <anchor> --format json` reports every hypothesis tied to that one anchor, each in a terminal `validated` or `rejected` state — asserted from the JSON, never from prose

### AC-3: the conclusion gate's query discriminates, and the skill states honestly what it is
Given a session with at least one `open` assumption on its anchor
When `cadence assumption list --filter-rec <id> --filter-status open --format json` runs
Then it returns a non-empty array, and returns an empty array once every assumption is closed — so the gate the SKILL.md instructs a reader to honor is deterministic and actually discriminates the two states
And `SKILL.md` states in its own words that this is a query the skill honors rather than a gate CADENCE enforces
(Decomposed deliberately. The arc plan's wording — "it attempts to conclude, then it does not" — is a claim about whether a model obeys prose, which no test can assert; a test pretending to would be the exact self-report trust this repo exists to refuse. What IS mechanically checkable is that the query is deterministic, that it discriminates open from closed, and that the SKILL.md's framing is honest. Those are asserted here; model obedience is not, and is not claimed anywhere in this phase.)

### AC-4: a concluded session leaves no dead ledger entry
Given the anchor recommendation was filed at the start of a debugging session
When the session concludes — root cause found, or the bug proved a false alarm
Then the anchor is no longer `candidate`, having been advanced via `cadence recommendation promote`, so debugging sessions do not accumulate as abandoned rows in a ledger already holding 91 active recommendations

### AC-5: the design record states why the pack cannot declare this skill
Given `PackManifestZ` is `.strict()` with payload limited to `skillAudit.required` + `gates[].add` + `commands[]` (`dec-20260822-023`), and skills are not commands
When `docs/packs-design.md` is read
Then it records that a pack has no slot for a distributed-but-not-required skill, cites `rec-20260917-003` as the filed Slice-6 gap, and references this skill as shipping by file under `.claude/skills/` instead — declaring it via `skillAudit.required` is rejected explicitly, because that would require it on every phase

### AC-6: the skill rides the same telemetry as the other house skills
Given `telemetry.skillInvocations` is enabled and the host's `Skill` matcher is wired
When the skill is invoked
Then its name appears in `state.skillAudit.invoked`, proving it is observable to `runSkillAuditCheck` exactly like `phase-build`
(Scope, per `rec-20260917-006`: `invoked` is checkout-scoped, deduped and never reset, so this shows the skill is observable to the telemetry — not that it ran in any particular phase, and once recorded it stays recorded)

## Boundaries
