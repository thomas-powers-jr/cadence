# 343-01 — verification.fallback: "refuse" turns a silent mock downgrade into a gate refusal

## Objective

Today, when a verifier seam cannot reach its configured real provider, it prints a loud notice and continues on mock. Reasons include a host-cli binary that will not launch, the claude self-invocation guard, a timeout, a missing Anthropic key, and an unset local endpoint. So an automated consumer of cadence-core can settle on a mock by accident; Cadence Studio defends against that with a sentence in its CLAUDE.md, which is shape, not a gate (rec-20261030-004).

This phase adds an additive config setting `verification.fallback: "mock" | "refuse"`. When it is absent or `"mock"`, behaviour is byte-identical to 1.73.0. Under `"refuse"`, `createVerifierFactory` (`packages/core/src/verify/verifier-factory.ts`) never delegates to mock. It is the one place every seam's downgrade passes through, and each caller passes it the effective setting through `VerifierSelectOptions`. Instead of delegating, the verifier call throws a typed error naming the seam and the cause. Where it surfaces differs by seam:

- **deep-verify, code-review and security-audit:** each gate's existing verifier-failure path turns the error into a gate refusal. Settle exits non-zero and the refused SUMMARY records the refusal.
- **per-task-verify, plan-review, spec-review and ui-spec-review:** there is no failure path, so the error reaches the command's catch. `build task`, `draft approve` and `spec approve` then exit 1 without mutating loop state.

`doctor` reports the setting, and under `"refuse"` its readiness wording says the seams will refuse rather than fall back. A provider explicitly configured as `mock` is a choice, not a fallback, and is unaffected.

## Acceptance Criteria

### AC-1: An unlaunchable host-cli binary refuses settle under "refuse"
Given `verification.fallback: "refuse"`, `verifier.provider: "host-cli"`, `CLAUDECODE` unset, and `CADENCE_HOST_CLI_BIN` naming a path that does not exist
When `cadence settle run --auto --deep` runs on a complex draft whose tasks are all DONE
Then settle exits 1. The refused `<id>-SUMMARY.json` it writes has `acResults: []`, a `deep-verify` gate entry with `status: 'refused'` whose reason names deep-verify, says `verification.fallback is refuse`, and carries a host-cli cause, and `assurance.overall === 'unverified'`. Nothing on stderr or in that reason matches `/falling back to mock/i`. The same run with `--allow-verifier-failure` proceeds and records the verifier failure exactly as that flag does on 1.73.0.

### AC-2: The claude self-invocation guard refuses under "refuse" (the Studio case)
Given `verification.fallback: "refuse"`, a host-cli seam whose bin resolves to the claude family, and `CLAUDECODE=1`
When that seam's verifier is called
Then the call throws the typed refusal, naming the seam's label and the `self-invocation` cause, without spawning a process or calling the mock, and with no `/falling back to mock/i` text in the error. At settle, the code-review gate turns it into a refusal unless `--allow-code-review-failure` or `--force` is passed; in that case the existing `reviewVerifierFailure` bypass record applies unchanged.

### AC-3: "mock" or unset is byte-identical to 1.73.0
Given `verification.fallback` absent, or set to `"mock"`
When each downgrade path runs (host-cli `HostCliError` at call time, anthropic with no key, local with no endpoint, and the test-only family-without-a-host-cli-builder branch)
Then the same mock delegate is called, the same warning text is emitted, and the same `providerSelection` tag (`fallback`) is applied as on 1.73.0. `defaultConfig` and the config a fresh `cadence init` plans are unchanged: the key is not written.

### AC-4: A launching binary, or an explicit mock, is unaffected by "refuse"
Given `verification.fallback: "refuse"`
When a host-cli seam's binary launches and returns a valid verdict, and separately when a seam's configured provider is `mock`
Then the first returns the host-cli primary's result tagged `configured` with no warning or refusal, and the second returns the mock exactly as today, since an explicit choice is not a fallback

### AC-5: The selection-time downgrades refuse lazily under "refuse"
Given `verification.fallback: "refuse"` and a seam configured for `anthropic` with no `ANTHROPIC_API_KEY`, or for `local` with no endpoint
When the verifier is selected and not called, when it is awaited or inspected, and when one of its methods is called
Then selection, `await`, and inspection neither throw nor warn, so a gate that does not run cannot refuse. The first method call throws the typed refusal naming the seam and the missing prerequisite.

### AC-6: doctor and the config reference report the setting
Given a repo config with `verification.fallback` set to `"refuse"`, or absent
When `cadence doctor --json` runs, and when `docs/reference/config.md` and `docs/reference/commands.md` are read
Then doctor's JSON carries a `verification-fallback` check reporting the effective value. Under `"refuse"`, `verification-readiness` warnings say the affected seams will refuse rather than fall back to mock; under absent or `"mock"`, its text is unchanged. The config reference documents `verification.fallback`, its values, its default, the seven seams it governs, and the bypass flags that still apply. The commands reference lists the new doctor check. The doc-content test pair asserts all of this.

### AC-7: Seams without a gate failure path still refuse, without mutating state
Given `verification.fallback: "refuse"`, `CLAUDECODE` unset, and a host-cli `planReview` or `perTaskVerifier` seam whose `CADENCE_HOST_CLI_BIN` does not exist, under a profile and tier whose gate set fires that seam
When `cadence draft approve` (plan-review) or `cadence build task <id> --status=DONE` (per-task-verify) runs
Then the command exits 1 with a message naming the seam and the refusal, and the loop position and task record are unchanged
