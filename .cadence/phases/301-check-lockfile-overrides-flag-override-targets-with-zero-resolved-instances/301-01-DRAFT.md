# 301-01 — check-lockfile-overrides: flag override targets with zero resolved instances

## Objective

`checkOverrideCoverage` in `scripts/check-lockfile-overrides.mjs` iterates
resolved lockfile instances and only checks an override target once some
instance's package name matches it. An override target whose package name
matches **zero** resolved instances in `pnpm-lock.yaml` is therefore never
visited and the check reports `ok: true` — a vacuous pass for a key that is
either dead weight (safe to delete) or a typo silently doing nothing. Fix it
by also checking, per declared override target, whether at least one
resolved instance shares its package name; report one when none does.

**Premise correction on `rec-20260907-005`'s cited evidence:** the phase-297
fast-uri incident it names as a "demonstration" of this bug was traced (by
running `checkOverrideCoverage` against the pre-297 override `"fast-uri@3.1.2":
"^3.1.5"` and the then-current lockfile) and is **not** actually an instance of
this bug — fast-uri@3.1.5 resolved in the lockfile, matched the target by
package name, and satisfied the declared `^3.1.5` range exactly as designed;
the check correctly passed. The real problem in phase 297 was that the
override's chosen range floor (`^3.1.5`) sat below the vulnerability patch
floor (`>=3.1.6`) — a fact `pnpm audit` is responsible for catching (and did),
not this lockfile-coverage detector, which only verifies a lockfile resolution
against its own declared override range. The vacuous "zero-name-match" gap
this phase fixes is real and independently reproduced (see AC-1), just not the
mechanism that caused phase 297's CI failure. `rec-20260907-005` is still a
correct, worthwhile fix; only its motivating anecdote was wrong.

## As built

- **T1's actual test asserts the fixed behavior directly, not the two-step
  "document the bug, then flip it" shape this DRAFT described.** The shipped
  test in `checkOverrideCoverage`'s describe block ("flags an override target
  whose package matches zero resolved instances as unresolved-target",
  tokens `301-01/AC-1, 301-01/AC-2`) was written expecting the *post-fix*
  `{ ok: false, ... reason: 'unresolved-target' }` result from the start; run
  against pre-fix code it failed with `expected true to be false` — a
  standard red-then-green TDD cycle, just without a separate "assert the bug"
  intermediate test to later invert. Simpler and equally red-first; AC-1's
  Given/When/Then prose (which still describes the old two-step plan) is
  superseded by this note, not by an edit to the AC text itself.
- **Independent review (fresh-context, Opus) surfaced two real gaps, both
  fixed before settle:**
  1. `describeFailure`'s `unresolved-target` message named
     `${package}@${range}` (e.g. `vite@^7.3.5`), not the literal
     `package.json` override key (`package@sourceVersion`, e.g. `"vite@^6.0.0
     || ^7.0.0 || ^8.0.0"`) — a maintainer told to "delete it" would grep for
     the wrong string. Fixed: failures now carry `sourceVersion`, and the
     message quotes the actual key form, `"${package}@${sourceVersion}":
     "${range}"`.
  2. AC-2 claimed `describeFailure` "renders it as an actionable message" but
     nothing asserted that — `describeFailure` wasn't exported. Fixed:
     exported it (joining the other pure decision-logic exports, per this
     file's own header-comment convention) and added a direct unit test
     (`describeFailure` describe block, token `301-01/AC-2`).
  3. The review also confirmed a real, deliberate scope limit worth
     documenting rather than "fixing": the new "was this target's package
     matched" check is keyed on package *name*, not on each individual
     target. Today's real committed config has two `brace-expansion`
     targets (`brace-expansion@5.0.6` and `brace-expansion@^2.0.0`); only
     the first currently resolves, and the second is *not* flagged, because
     package-name-level matching is the only granularity compatible with
     the committed config — per-target granularity would flag
     `brace-expansion@^2.0.0` and fail `lockfile-overrides-current-state.test.ts`
     (which asserts `failures: []` against real committed state) and turn
     the Security workflow's `audit` job red. Documented in
     `checkOverrideCoverage`'s JSDoc ("Scope:" paragraph) and covered by a
     new regression test ("does not flag a package with multiple override
     targets as long as one of them is matched", token `301-01/AC-2`) so a
     future reader doesn't tighten this into a CI break.
  Verified independently: `pnpm --filter @thomas-powers-jr/cadence-core test
  -- check-lockfile-overrides` → 15/15 pass (14 after the review-driven
  additions, +1 more below);
  `lockfile-overrides-current-state.test.ts` → 2/2 pass unchanged;
  `node scripts/check-lockfile-overrides.mjs` against real committed
  `package.json`/`pnpm-lock.yaml` → exit 0, "7 override target(s), all
  resolved instances satisfied".
- **First `settle run --auto` refused**: `coverage: 301-01/AC-3 has no linked
  test` (assertion-mode + phase-qualified coverage demands a real token for
  every AC, including the "changeset exists" meta-AC — same class of gap
  phase 300's carry-forward gotcha already flagged for exactly this
  situation). Fixed the same way phase 300 did: added a direct test
  asserting the changeset file exists and mentions the package, tagged
  `301-01/AC-3`, mirroring `settle.test.ts`'s `300-01/AC-5` precedent.
