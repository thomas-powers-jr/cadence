# 326-01 — Docs name all three required status checks on main

## Objective

`main`'s branch protection requires three status checks, `ci-success`, `security-success` and `codeql-success` (live `gh api repos/thomas-powers-jr/cadence/branches/main/protection` on 2026-10-09: `required_status_checks.contexts` is `["ci-success","security-success","codeql-success"]`, `enforce_admins` on), and `docs/security/audit-exceptions.md` has recorded that list since rec-20260807-002 (2026-08-07). But eight operator-facing passages still say or imply that only `ci-success` is required: CLAUDE.md's "Land via branch + PR" workflow item, its "CI" bullet under "Enforcement layers" and its "The Direct Push" failure mode; `.claude/skills/pr-land/SKILL.md`'s frontmatter description and opening paragraph; `.claude/skills/release-cut/SKILL.md`'s step 4; `docs/release.md`'s step 5; and the comments above the `security-success` job in `.github/workflows/security.yml` and the `codeql-success` job in `.github/workflows/codeql.yml`, which still say the job "blocks nothing" because the contexts are "exactly `["ci-success"]`". The phase 323 session trusted that wording and expected a PR with a red `security-success` to be mergeable. rec-20261007-002 names the first five passages; this phase also fixes the `release-cut` line and the two workflow comments, which carry the same claim. Fix all eight, phrased as an addition (`ci-success` alongside `security-success` and `codeql-success`), and pin them with a doc-content test whose canonical list is parsed from `docs/security/audit-exceptions.md`, the one in-repo record of the protection setting, not derived from the workflows' `*-success` job names: those jobs existed for weeks before they were registered as required, which is how this drift started.

## Acceptance Criteria

Given `docs/security/audit-exceptions.md` records `main`'s `required_status_checks.contexts` as a bracketed list of quoted names (hard-wrapped prose)

Then the parse is anchored on the "`required_status_checks.contexts` is `[`" form and that form matches exactly once in the file; the parsed list has at least two names (so a parse that collapses to `["ci-success"]` fails), contains `ci-success`, and every name in it is a top-level job key in one of `.github/workflows/ci.yml`, `.github/workflows/security.yml` or `.github/workflows/codeql.yml` (a one-way check: an aggregator job that is not yet registered does not fail it); a comment in the test states that the record must be re-verified with `gh api …/branches/main/protection` whenever protection changes

### AC-4: the security.yml and codeql.yml aggregator comments say the job is required

### AC-5: a scoped recurrence guard refuses a passage that names ci-success as required without the others
Given a pure helper in the test file that takes raw (not whitespace-collapsed) text, splits it into blank-line-separated paragraphs on `/\r?\n[ \t]*\r?\n/` so a CRLF checkout splits the same as an LF one, and returns every paragraph that mentions `ci-success`, matches /requir/i, and omits at least one name from the list
When it runs over the eight-passage files of AC-2 to AC-4 (CLAUDE.md, the two skills, docs/release.md, security.yml, codeql.yml), and over synthetic fixtures
Then it returns no paragraphs for any of the six real files; it returns the paragraph for a fixture "`ci-success` is required on `main`."; it returns exactly the offending paragraph, not the whole text, for a CRLF fixture with that paragraph between two compliant ones; and it returns nothing for a fixture naming all three checks and for a fixture mentioning `ci-success` without "requir"; the guard is not applied to any other file (DESIGN.md, CHANGELOGs, `docs/handoffs/*`, ci.yml and `.cadence/**` are history or already correct)
