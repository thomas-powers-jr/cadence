# 352-01 — boundary-scan bypasses are recorded

## Objective

Make a bypassed `boundary-scan` refusal as loud and as durable as a bypassed failing test suite (rec-20261125-002). Today `--allow-boundary-scan-failure` or `--force` past a `boundary-scan` refusal reaches only stderr and gate provenance (`skipped`, `bypassed via <flag>`); no entry lands in `SUMMARY.json.gateBypasses`, so the SUMMARY cannot tell a settle that let out-of-boundary files through, or that skipped the committed-file scan because the merge-base could not be computed (phase 351), from a clean one, and the assurance grade is not capped. Separately, with both flags set the gate's stderr line names `--force` while the registry records `--allow-boundary-scan-failure`. After this phase the gate reports what it bypassed in `flags.boundaryScanBypass`, the registry takes the provenance flag from it, `collectAnomalies` turns it into a `boundary-scan-bypassed` anomaly, and settle records one error-severity `boundary-scan` entry per bypassed cause in `gateBypasses`, which caps a `strong` `assurance.overall` at `mixed` as a `build-test-must-pass` bypass already does. This follows the phase 346 `build-test-bypassed` design.

Definitions used by AC-1 to AC-4. A bypass cause is `offenders` (files outside the declared boundary were let through) or `merge-base` (an `upstream-failed` base was let through, so committed files were not scanned). The flag rule, for this gate: the flag named is `--allow-boundary-scan-failure` when that option is set, else `--force` (the rule the registry and `build-test-must-pass` already use).

## Acceptance Criteria

### AC-1: The gate reports what it bypassed and names the flag by the rule
Given `runBoundaryScanGate` in block mode, unsealed, in three examples built with real git repositories as `packages/core/tests/gates/boundary-scan-diff-base.test.ts` builds them: (a) a repository with no `origin` remote and a file `stray.ts`, outside the DRAFT's declared `files:`, committed on `feature` after it diverges from `main`, run with `allowBoundaryScanFailure: true`; (b) a repository whose `refs/remotes/origin/main` has no common history with `HEAD` and a clean working tree, run with `force: true`; (c) as (a) but run with both `force: true` and `allowBoundaryScanFailure: true`
When the gate runs on example (a), (b) and (c) in turn
Then its result's `flags` equals (a) `{ boundaryScanBypassed: true, boundaryScanBypass: { flag: '--allow-boundary-scan-failure', causes: ['offenders'], offenders: ['stray.ts'] } }`, (b) `{ boundaryScanBypassed: true, boundaryScanBypass: { flag: '--force', causes: ['merge-base'], offenders: [] } }`, (c) `{ boundaryScanBypassed: true, boundaryScanBypass: { flag: '--allow-boundary-scan-failure', causes: ['offenders'], offenders: ['stray.ts'] } }`; and in (c) the stderr bypass line reads `boundary-scan: --allow-boundary-scan-failure set; proceeding past 1 offending file(s).` followed by a newline.
Not covered: a sealed gate, which refuses and reports no bypass; a run that passes without a bypass, where `flags.boundaryScanBypass` is absent; a run that bypasses both causes at once, which reports `causes: ['merge-base', 'offenders']` and is pinned by the updated phase 351 test in the same file.

### AC-2: The registry takes the provenance flag from the gate's report
Given `runSettleGates` with opts `{ allowBoundaryScanFailure: true }` and a stubbed `boundary-scan` result whose `flags` are `{ boundaryScanBypassed: true, boundaryScanBypass: { flag: '--force', causes: ['offenders'], offenders: ['stray.ts'] } }`
When the registry builds the gate's provenance entry
Then the `boundary-scan` entry equals exactly `{ gate: 'boundary-scan', status: 'skipped', skipReason: 'bypassed via --force' }`.
Not covered: a result without `boundaryScanBypass`, which keeps today's options-based flag; provenance entries for other gates.

### AC-3: Settle records one error-severity boundary-scan entry per bypassed cause, and it caps a strong grade
Given `collectAnomalies` called with `boundaryScanBypass` set to AC-1's report (a) or (b) and `integrationRef` = `main`, the exported `gateBypassesFromAnomalies` from `packages/core/src/services/settle.ts` applied to its anomalies, and a `gates`/`acResults` pair that `deriveAssuranceRecord` grades `strong` with no bypass
When the anomalies, the bypass entries and the grade are derived
Then report (a) yields a `boundary-scan-bypassed` anomaly with severity `error` and context `{ flag: '--allow-boundary-scan-failure', cause: 'offenders', files: ['stray.ts'], integrationRef: 'main' }`, and the `boundary-scan` entries of `gateBypasses` equal `[{ gate: 'boundary-scan', flag: '--allow-boundary-scan-failure', reason: '1 file(s) outside the declared boundary: stray.ts', severity: 'error' }]`; report (b) yields `boundary-scan` entries equal to `[{ gate: 'boundary-scan', flag: '--force', reason: 'the merge-base of origin/main and HEAD could not be computed; committed files were not scanned', severity: 'error' }]`; and `deriveAssuranceRecord` grades that pair `mixed` with report (a)'s entries and `strong` without them.
Not covered: the offenders reason for several files, which joins them with `, ` in the order the gate reports them, without a cap on length; the existing warn-severity `files-outside-boundary` anomalies, which are still emitted; notifier transports, which receive the new anomaly as they receive the others; a grade that is already `weak` or `unverified`, which the cap leaves alone.
